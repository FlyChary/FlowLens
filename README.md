# FlowLens

有界内存的实时流量统计服务：接收 HTTP 访问事件，用固定内存的近似数据结构（Count-Min、HyperLogLog、DDSketch、稀疏线段树）持续维护，随时回答"最近一段时间哪些 URL / 用户最热（Top-K）、去重人数、响应字节 p95"，并支持按历史时刻回放。设计见 [docs/DESIGN.md](docs/DESIGN.md)。

![框图](docs/flowlens-architecture-v3.png)

## 快速开始

Docker（推荐，评测环境）：

```bash
docker build -t flowlens .
docker run --rm --memory=256m -p 8080:8080 flowlens
```

默认使用官方 PyPI 拉取依赖；国内网络慢时可加清华镜像源：

```bash
docker build --build-arg PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple -t flowlens .
```

没有 Docker 时用仓库内的 `run.sh`（自建 venv、装依赖、启动，固定 `PYTHONHASHSEED=0`）：

```bash
./run.sh            # 默认监听 :8080，可用 FLOWLENS_PORT / FLOWLENS_HOST 覆盖
```

> 注意：服务要求 `PYTHONHASHSEED` 固定（`run.sh` 与 Dockerfile 已固定为 0）。字符串哈希值随该种子变化，未固定时启动会打印警告。

## 架构：为什么有"接受端进程"

FlowLens 的核心是**单写者**：所有统计状态（Top-K、HyperLogLog、DDSketch、稀疏线段树）只归**引擎主进程**的一个事件循环，不加锁、不多进程分片——逻辑最简单、内存最省。但写入一条事件要先**解压 → 解析 JSON → 校验 → 归一化 URL**，这段很吃 CPU，又和"引擎每秒定稿 + 快照"排在**同一个事件循环**里。单进程下高写入速率会把主进程 CPU 打满，导致在途请求堆积、触发降级拒写。

**接受端进程**就是为解开这个结：把"收 HTTP + 解压 + 解析"这段最费 CPU 的活儿挪到若干个副本进程里做，解析完把紧凑数据丢给引擎；引擎专心去重、写桶、每秒 tick。接受端**不碰任何统计状态**。

```
                                    ┌──────────────────────┐
客户端 :8080 ──────────────────────▶│ 接受端进程 #0            │
（SO_REUSEPORT 让 N 个接受端进程      │  收 HTTP · 解压 · 解析 │──┐
  共同监听同一个端口，客户端无感知）     ├──────────────────────┤  │
                                    │ 接受端进程 #1            │  │ 解析好的紧凑数据
                                    │  收 HTTP · 解压 · 解析 │──┤ （WireBatch）
                                    ├──────────────────────┤  │
                                    │ 接受端进程 #2            │  │
                                    │  收 HTTP · 解压 · 解析 │──┘
                                    └──────────────────────┘
                                          │  写入通道（本机 Unix socket）
                                          ▼
                       ┌────────────────────────────────────────────┐
                       │         引擎主进程（唯一的统计者）           │
                       │   去重 → 写秒桶 → 每秒定稿 + 刷新快照        │
                       │   只有它持有 Top-K / HLL / DDSketch / 线段树 │
                       └────────────────────────────────────────────┘
                                          ▲
        ① 引擎每秒把一份“快照”广播回各接受端：默认窗口查询（不带 at）由接受端拿快照
           【本地直接答】，不排引擎的队；快照超过 3 秒没更新就过期、改回走 ②
        ② 其他查询（回放 at / stats / healthz / SSE）：接受端【原样转发】到引擎的
           内部 HTTP（同为本机 Unix socket，不对外）由引擎回答
```

要点：

- **同一个 8080 端口、多进程共同监听**（Linux `SO_REUSEPORT`），客户端无感知，对外接口与单进程完全一致。
- **接受端模式下引擎不再监听 TCP**：只起一个本机 Unix socket 的内部 HTTP（给接受端转发查询）+ 一条写入通道。接受端与引擎之间走 Unix socket，不走网络。
- **写入**：接受端解压、按字节预留额度、解析，把 `WireBatch` 发给引擎；引擎去重、写桶、回 ACK。去重（event_id 的 Bloom）完全在引擎侧，接受端不持有去重状态。
- **查询分两种**：默认窗口（不带 `at`）由接受端拿引擎每秒广播的**快照**本地直接答（不排引擎的队，512 MB 下默认窗口 p99 能压到 ~35 ms）；快照超过 3 秒没更新就过期、改回转发。回放（带 `at`）、stats、healthz、SSE 等**原样转发**给引擎答。
- **降级 / 额度 / 内存读数**经**共享内存**在引擎与接受端间交换，不走消息。
- 在容器里实测，**引擎每条约 2.8～3.9 μs**，单看引擎能支撑约 **26～35 万条/秒**

每个接受端是独立的 Python 解释器，常驻约 30 MB（要 import numpy 等），3 个接受端约 +90 MB 基础内存——**内存越紧越开不起**，这也是 256 MB 评测容器退回单进程的原因之一。接受端数根据内核数及内存上限自动决定。

## 运行模式

服务启动时**自动决定接受端进程数**：在 Linux、可用核数 ≥ 2、内存上限 ≥ 384 MB 时，启用 `min(3, 核数 − 1)` 个**接受端进程**——多个进程通过 `SO_REUSEPORT` 共同监听同一端口，负责接收与解析写入请求、直接回答默认窗口查询；引擎主进程只保留去重、写统计结构、每秒 tick 与降级。其余情况（含非 Linux、核数 < 2、内存上限 < 384 MB）为**单进程**。启动日志会打印实际的接受端数与原因，例如：

```
2026-10-21 07:04:59,106 INFO flowlens 前端数 0（内存上限 256 MB < 384 MB）
```

（日志与环境变量里仍叫"前端/frontends"，指的就是本文的接受端进程。）

- **256 MB 容器下为单进程模式**（内存上限 < 384 MB 自动退回，这也是评测环境实际运行的配置）。
- 想体验接受端模式，用 512 MB 启动即可（不设置 `FLOWLENS_FRONTENDS`，由服务自动判断）：

```bash
docker run --rm --memory=512m -p 8080:8080 flowlens   # 多核下自动开 min(3, 核数−1) 个接受端
```

## 配置

环境变量（均以代码中的实际默认值为准；不设置即取默认值）：

| 变量 | 说明 | 默认 |
|---|---|---|
| `FLOWLENS_FRONTENDS` | 显式指定接受端进程数（`0` 禁用）；不设置则按"运行模式"自动判断 | 自动 |
| `FLOWLENS_MAX_PENDING_BYTES` | 在途（已预留、未写完）请求体的总字节上限 | 4 MB（4194304） |
| `FLOWLENS_RAW_BUDGET_BYTES` | 正在读取/持有的原始请求体字节总上限 | 8 MB（8388608） |
| `FLOWLENS_POOLED_CHUNK_EVENTS` | 已解析写入路径（接受端架构）单次写入引擎的事件块大小 | 10000 |
| `FLOWLENS_INTERN_USER_CAP` | user 字符串驻留表上限（满则整体清空；设 `0` 关闭驻留） | 8192 |
| `FLOWLENS_INTERN_URL_CAP` | url 归一化结果驻留表上限（满则整体清空；设 `0` 关闭驻留） | 32768 |
| `FLOWLENS_DEBUG` | `1` 时开启只读调试接口 `GET /debug/structure` 与 `FLOWLENS_TEST_MEM` | 未开启 |
| `FLOWLENS_TEST_MEM` | 注入假的内存读数（`0~1` 的比例）以触发降级——**仅在 `FLOWLENS_DEBUG=1` 时生效，只用于测试** | — |

## 接口一览

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/v1/ingest` | 写入一批事件 |
| GET | `/v1/topk` | 区间 Top-K（`by`=url/user，可带 `at` 回放） |
| GET | `/v1/topk/stream` | SSE 实时 Top-K 流（可断线补帧） |
| GET | `/v1/stats` | 区间去重人数与响应字节 p95 |
| GET | `/healthz` | 健康检查与运行状态 |

### 写入事件（POST /v1/ingest）

请求体是**事件数组**（JSON 数组）或 **NDJSON**（每行一条），支持 `Content-Encoding: gzip`，单个请求解压后 ≤ 4 MB。事件字段：`event_id`、`user_id`、`url`、`ts`（epoch 毫秒）、`bytes`。

```bash
curl -X POST http://127.0.0.1:8080/v1/ingest \
  -H "Content-Type: application/json" \
  --data '[{"event_id":"e1","user_id":"u1","url":"/api/item/42","ts":1735689600000,"bytes":128},
           {"event_id":"e2","user_id":"u2","url":"/api/item/43","ts":1735689600123,"bytes":256}]'
```

返回 `202`，各计数按 event_id 去重、迟到/非法剔除：

```json
{"accepted": 2, "deduped": 0, "late": 0, "invalid": 0}
```

> 示例里的 `ts` 是固定的过去时间戳，直接照跑会被判为迟到（`late: 2`）；真实事件用**当前时刻的 epoch 毫秒**作 `ts` 会记入 `accepted`。

### 最近 60 秒 Top-K（GET /v1/topk）

`by` 取 `url` 或 `user`，`k`≤100；不带 `at` 的默认窗口直接读快照，带 `at`（epoch 毫秒）回放历史区间。

```bash
curl "http://127.0.0.1:8080/v1/topk?window=60s&k=10&by=url"
```

返回（`count` 是点估计、`err` 是 [lower, upper] 的半宽度，非采样时为严格保证）：

```json
{
  "window_ms": 60000, "from": 1735689540000, "to": 1735689600000,
  "by": "url", "k": 10, "final": false, "degraded": false, "unseen_upper": 0,
  "items": [
    {"key": "/api/item/{id}", "count": 171133, "err": 0},
    {"key": "/api/home", "count": 88210, "err": 0}
  ]
}
```

### SSE 实时 Top-K 流（GET /v1/topk/stream）

参数同 `/v1/topk`，加 `interval`（帧间隔，默认 1s）；同参数订阅者共用一份计算，断线可按 `Last-Event-ID` 补帧。每帧的 `data` 与 `/v1/topk` 完全同构。

```bash
curl -N "http://127.0.0.1:8080/v1/topk/stream?window=60s&k=10&by=url&interval=1s"
```

```
retry: 3000
id: 1735689600000
event: topk
data: {"window_ms":60000,"from":...,"to":1735689600000,"by":"url","k":10,"final":false,"degraded":false,"unseen_upper":0,"items":[{"key":"/api/item/{id}","count":171133,"err":0},...]}
```

### 区间统计（GET /v1/stats）

去重人数（HyperLogLog）与响应字节 p95（DDSketch），同样支持 `at` 回放；区间内无数据时 `approx_p95_bytes` 为 `null`（不出现 NaN）。

```bash
curl "http://127.0.0.1:8080/v1/stats?window=60s"
```

```json
{
  "window_ms": 60000, "from": 1735689540000, "to": 1735689600000,
  "approx_distinct_users": 4210,
  "approx_p95_bytes": 10240,
  "memory_bytes": 112000000, "degraded": false
}
```

### 健康检查（GET /healthz）

```bash
curl "http://127.0.0.1:8080/healthz"
```

```json
{
  "ok": true, "events_ingested": 1200000,
  "memory_bytes": 112000000, "memory_current_bytes": 168000000, "memory_limit_bytes": 268435456,
  "degraded": false,
  "degrade": {"level": 0, "sample_weight": 1, "occupancy": 0.0,
              "tick_lag_ms": 0.0, "memory_bytes": 112000000, "memory_limit_bytes": 268435456},
  "deduped": 1024, "late": 30, "invalid": 12, "tick_errors": 0, "last_tick_ms": 85.2,
  "malloc_trim": {"enabled": true, "period_sec": 10, "call_count": 60, "total_ms": 180.5,
                  "last_ms": 3.2, "last_freed_mb": 21.4, "total_freed_mb": 1024.8},
```

`memory_bytes` 是工作集（降级判断用它），`memory_current_bytes` 是原始 cgroup 读数，`memory_limit_bytes` 无上限时为 `null`。

## 实测数据

Docker 容器实测。两种配置都是容器限内存、不固定 CPU 核、不设置 `FLOWLENS_FRONTENDS`（服务自动决定接受端数）——**256 MB 就是评测环境实际跑的配置（自动退回单进程）**，512 MB 是多核下的形态（自动开 3 个接受端）。

| 指标 | 512 MB / 3 接受端 | 256 MB / 自动单进程 |
|---|---|---|
| 持续写入能扛多少（10 分钟） | **20 万条/秒**，100% 接受，只短暂进过第 1 级（共 4 秒） | **8 万条/秒**，100% 接受、不拒写；约 4 分钟后内存填满进入第 3 级（写入改成 1/2 采样，但仍全部接收）。已提交版本在同样条件下会进第 4 级、开始拒写 |
| 默认窗口查询 p99（topk + stats） | **34.8 ms**（在 20 万条/秒写入时测的，达标 < 50 ms；接受端进程直接答，不经引擎） | 没写入时 **3.4 ms**；有持续写入（每秒 3 万条以上）就 **~72-78 ms**，不达标 |
| 回放查询 p99（带 `at`） | 最低档（每秒 3 万条写入）**56.7 ms**，任何写入速率下都达不到 50 ms | 8 万条/秒写入时 **72.7 ms**，和默认窗口差不多（单进程，查询和写入排在同一个循环里） |
| 精度（每秒 3 万条写 5 分钟，抽 200 个区间和精确答案对比） | Top-K 召回 1.000（200/200）、计数误差（均值）url 0.028% / user 0.042%、真实值 100% 落在误差界内、去重人数误差 0.984%、p95 误差 0.097% | Top-K 召回 1.000（200/200）、计数误差（均值）url 0.086% / user 0.127%、真实值 199/200 落在误差界内（唯一越界区间正撞 L1/L2 采样档）、去重人数误差 0.985%、p95 误差 0.007%——L0（无降级）下与已提交版本一致，降级采样档是误差超界的来源 |
| 内存峰值（10 分钟） | 正常流量（长尾）**20 万条/秒** ×10 分钟 **379 MiB**；全随机攻击流量 **3 万条/秒** ×10 分钟 **391 MiB 封顶、不再涨**，全程不降级 | 正常流量（长尾）**8 万条/秒** ×10 分钟 **215 MiB**（就是它触到了第 3 级线）；全随机攻击流量 **3 万条/秒** ×10 分钟 **227 MiB 封顶、不再涨**（无 OOM），约 2 分钟后进第 3 级、有 7.2% 拒写（单进程写路径慢，512 MB/3 接受端下同流量 100% 接受） |
| 边界用例（19 条） | 全过 | 全过 |

两点说明：

1. **查询 p99 为什么超标**：查询本身只要几毫秒（p50），慢在排队——引擎每秒要独占事件循环做一次定稿+快照（约 85-130 ms），查询撞上就得等；单进程下写入块也排在同一个循环里，所以 256 MB 连默认窗口都超标，512 MB 只有回放查询超标（默认窗口由接受端直接答）。
2. **256 MB 为什么必然降级**：要保留 600 秒的历史，统计状态常驻约 200 MiB，持续写入 4 分钟左右就填满、触到第 3 级线。第 3 级只是采样、不拒写；这是 256 MB 的内存上限决定的，和写入速率无关。

完整数据（各写入速率的 p50/p95/p99、逐分钟内存与降级、精度明细）见 [docs/lanes/M1-notes.md](docs/lanes/M1-notes.md) 与 [docs/lanes/P2-notes.md](docs/lanes/P2-notes.md)。

## 512 MB 下每秒 20 万条的长时间稳定性测试

（20 万/秒 × 10 分钟 + 停发 60 s，自动开 3 接受端）

**内存**：10 分钟里从 ~186 MiB 涨到峰值 **379 MiB**，始终没碰到 400 MiB 的降级线；
停止写入 1 秒后就回落到 ~318 MiB——落掉的是处理请求时占用的临时内存，
剩下的都是要保留 10 分钟的历史数据，没到期不会释放。
**CPU**：主进程瞬时峰值 96.5%，但没长时间满负荷——
"解析收到的请求"这个最费 CPU 的活儿由 3 个接受端进程分担（三个加起来约占 1.2~1.6 个核）。

**降级策略**：服务每秒检查一次下面三个量，给自己打 0~4 级，级别越高省得越多。
三个输入量：

- **在途占用率** = 正在处理、还没写进统计结构的请求体字节数 ÷ 在途上限（默认 4 MB）
- **tick 延迟** = 引擎每秒一次"定稿 + 快照"实际开跑比预定时刻晚了多少毫秒
- **内存占比** = 工作集 ÷ 容器内存上限

| 级别 | 怎么进入 | 怎么退出 | 进入后怎么处理 |
|---|---|---|---|
| 0（正常） | — | — | 全速写入、全量精度 |
| 1 | 在途占用率 > 0.6，或 tick 延迟 > 1000 ms | 在途占用率 < 0.4 且 tick 延迟 < 500 ms | 历史回放查询（带 `at`）暂时返回 503；实时 Top-K 推送降频（1 秒一帧 → 5 秒一帧）。**写入不受影响** |
| 2 | 在途占用率 > 0.8 | 在途占用率 < 0.5 | 写入改带权采样：只记 1/2 事件再 ×2 放大计数（占用率 > 0.95 时记 1/4）。Top-K 名单与去重人数仍按全量算，代价是响应字节 p95 精度略降 |
| 3 | 内存占比 > 0.78 | 内存占比 < 0.70 | 在途内存额度 4 MB→2 MB、原始请求体额度 8 MB→4 MB，清查询结果缓存与 URL 归一化缓存，不再接受新的推送订阅。额度收紧后，太大的请求会暂时 503（客户端重试即可） |
| 4 | 内存占比 > 0.90 | 内存占比 < 0.82 | **写入一律 503**（读请求体之前就直接拒） |

**接受率 = 收到的事件条数 ÷ 发送的条数**，按"条"算、不按
"请求"算。服务对写入请求要么整批收下、要么整批返回 503（不会出现"收一半"）；
收到 503 的客户端会自动重试（最多 5 次），重试成功的那批照样算"接受"。本次跑里
有过 53 次"正在处理的请求队列暂满"的瞬时拒绝，全部在重试里成功写进去了，所以按条
算下来是 1.2 亿 / 1.2 亿 = 100%。

| ---------- | -------------- | -------- | ------ | ------- |
| 0          | 315.4          | 0        | 1.000  | 2.77    |
| 1          | 329.2          | 0        | 1.000  | 3.13    |

## 512 MB 下最高能承载多少每秒请求数

（512 MB、自动 3 接受端、不固定 CPU 核；每档一个干净容器）

**结论：短时长 ~22.5 万条/秒、10 分钟级 ~19.8 万条/秒；天花板是引擎主进程的单核 CPU，不是 512 MB 内存。**

| 时长 | 可持续速率 | 结果 |
|---|---|---|
| ≤60 s（25 万目标、干净容器） | **~22.5 万条/秒**（实测 224,828/s） | 100% 接受、0 拒写、**全程 0 级**、工作集峰 337 MiB、引擎 CPU 峰 92.3% |
| 10 分钟（20 万目标、干净容器） | **~19.8 万条/秒**（实测 197,844/s） | 100% 接受、仅第 1 级累计 4 s、工作集峰 379 MiB |

- **为什么短时长能比 10 分钟高**：10 分钟里 600 s 保留期被填满（20 万/秒 × 600 s = 1.2 亿条历史常驻），引擎每秒 tick + 快照的 CPU 和工作集都涨上去，稳态速率比短时长低 ~12%。
- **瓶颈是引擎单核，不是内存**：各速率档引擎主进程 CPU 都顶到 ~100%（单事件循环打满 1 核），而统计状态是**单写者**、吃不到第二个核；内存峰值才 337 MiB，远没到 512 MB 的 L3 线（400 MiB）。所以再加速率只会让引擎排队、触发 503 背压，不是内存爆掉。
- **测量口径**：压测进程在 WSL 宿主机（8 核）、容器限 512 MB；客户端自身也吃 ~6 核，20 万以上"实际发出"会被服务端 503 压回，所以高目标档"实际发出"低于目标属正常背压——判读以"该速率下是否 100% 接受 + 全程 0 级"为准。

## 已知限制

- **统计状态仍是单写者**：所有统计状态归引擎主进程的单个事件循环（不加锁、不多进程分片；性能靠按批处理 + numpy 向量化）。多核 + 内存上限 ≥ 384 MB 时 HTTP 接入与解析由接受端进程分担（见"运行模式"）；**256 MB 评测容器下自动退回单进程**，以下数字均为该配置实测（不加 CPU 固定）。
- **评测配置（256 MB）的可持续吞吐**：每秒 8 万条持续 10 分钟、100% 接受、不拒写——约 4 分钟后 600 s 保留期填满，工作集峰值 ~215 MiB 触到第 3 级线，进入第 3 级（1/2 采样、不拒写）；已提交版本在同样条件下进入第 4 级、拒绝写入。256 MB 的结构性内存墙（统计状态常驻 ~200 MiB 贴着第 3 级线）决定了 10 分钟级持续写入无法全程第 0 级。
- **评测配置的查询延迟**：无写入时，默认窗口 topk/stats 与回放 topk 的 p99 都约 3.4 ms；有持续写入（每秒 3 万条及以上）时 p99 约 72~78 ms（超过 50 ms 目标），三类查询同量级——单进程模式下都排在同一事件循环的写入块之后。**查询（含回放查询）p99 的尾主要由引擎每秒 tick 的独占时段（定稿 + 快照合计约 85~130 ms/秒）与写入块决定，而不是查询计算本身**；写入速率在 3 万~8 万/秒之间变化时 p99 基本不变。
- **512 MB（自动开 3 接受端）**：每秒 20 万条持续 10 分钟、100% 接受，默认窗口查询 p99 34.8 ms（< 50 ms 目标）；回放查询 p99 仍受同一 tick 独占时段限制（任何写入速率下 ≥ 56.7 ms）。
- 完整实测数字与分析见设计文档与 [docs/lanes/P2-notes.md](docs/lanes/P2-notes.md)。
