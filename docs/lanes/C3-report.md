# C3（T9b 支线）：T9b-A 内存加固——实验报告

**任务**：在不改冻结模块（config.py 等）的前提下，做三项内存加固——
① Ticker 定期 `malloc_trim(0)`、② 字符串驻留（user 写桶前 / url 归一化结果）、
③ 在途额度降为实验变量（2 MB）——在 256 MB 容器里逐项消融对比，并验证
"对抗性流量下内存有界"（S4）与"内存稳住后的首份精度数据"（S3）。

**环境**：容器 = `flowlens:t9b`（本支线代码，`--target app`，Python 3.12-slim，
`PYTHONHASHSEED=0`），`--memory=256m --memory-swap=256m --cpuset-cpus=0`（服务固定
1 核）；压测 = WSL 宿主 `tools/loadgen.py`（`taskset -c 1-6`）。**参数与 C2 基线相同**：
长尾、3 万/秒、每批 5000、4 进程 × 8 并发、5 分钟 + 停发观察 60 秒。四组同一镜像、
同参数，只改特性开关（`--extra-env`），消融干净。结果 `results/c3/`。

> **口径**：工作集 = cgroup `memory.current − inactive_file`（降级判定同口径，T10b
> 起）。降级阈值：第 3 级 78% = 199.7 MiB、第 4 级 90% = 230.4 MiB。本机（WSL2、
> 服务固定 1 核、压测抢其他核）是争抢环境，绝对值比评测容器偏高（C2 同 caveat）；
> 定性结论（碎片/有界/消融方向）不受影响，最终数字以评测容器为准。

## 二、每项改动的效果与代价

### ① 定期 malloc_trim（g1 → g2）——**主杠杆**
- **峰值工作集 233.4 → 213.9 MiB（−19.5 MiB）**；更关键的是**把"进第 4 级拒写"
  拉到"最高第 3 级、不再拒写"**——接受率 87.8% → **100%**、503 率 12.2% → 0%。
  基线 g1 从 m5 起进 4 级（230.4 MiB）拒写、事件冻结，g2 全程不拒写。
- **停发后回落**：g1 停在 224 MiB（一点不回落，C2 已证实是 glibc 留页），
  g2 回落到 155.5 MiB（**~68 MiB 还给 OS**）——正是 C2 预测的"trim 清堆顶、降负载
  后常驻高水位"。
- **但 trim 单独压不住满载中后段**：g2 从 m4 起仍贴 3 级（188s 起 107s 连续 L3）。
  满载中每 10s 重新 churn ~30 MiB、trim 追不上（C2 §1.4 同样结论），峰值虽降、
  中后段仍触 3 级。
- **代价**：33 次共 ~91 ms（每次 ~3 ms），一次 Ticker 拍内完成，可忽略；非 Linux
  平台 no-op。

### ② 字符串驻留（g2 → g3）——**降中后段水位、逼近第 0 级**
- **峰值不变**（213.9，峰值由 glibc churn 页 + 32 连接并发解析决定，C2 已分解，
  驻留碰不到）；**结束/中后段水位降 ~11 MiB**（g2 155.5 → g3 144.7）。
- **最关键的效果**：g3 的负载期间（m1~m5）**每个分钟点都在第 0 级**、工作集
  169→197 MiB（正好压在 78% 阈值 199.7 MiB 之下），只在中后段出现 **15 秒**的
  短暂 3 级尖峰（每次 1~5s、逐秒回 0）。对比 g2 的 102s L3（含 107s 连续段），
  驻留把"贴 3 级"压成了"偶发尖峰"。这就是 C1 账本里"长尾 user 侧 ~7.2 MB、url 侧
  重复对象"被收敛后的效果。
- **代价**：驻留表自身内存被 cap 钉死（user 8192 + url 32768 ≈ <0.3 MB 表 + 驻留
  字符串本身）；CPU 是写桶前 `np.fromiter` 逐条 `intern`（一次 dict get + 偶发
  写入），bench_model 真实流量组 ~0.61 μs/条、与 T10b（0.50）同波动带，未变慢。
- **url 驻留的额外收益**：lane-c 的归一化缓存（T10b 先剥 query/fragment）命中时已
  复用同一对象，但**缓存未命中**（新路径）时每次 new 一个对象、各秒桶/叶子/节点
  存很多份；驻留把这部分也收敛（见 C1 §5）。

### ③ 在途额度降到 2 MB（g3 → g4）——**本负载下无增益**
- 峰值 213.9 → 215.0（噪声内持平）、结束 144.7 → 145.9（持平）、降级时长持平。
- **原因**：每批 5000 条（解压后 ~1.5 MB）、Admission 上限 4 MB 本就能同时容纳
  ~2 个在途批；降到 2 MB 后占用率略升但**没有触发额外 503**（g4 503 率仍 0%），
  内存上也没有可感的在途峰值被压掉——这个负载下在途窗口不是内存瓶颈。
- **结论**：在途降额度对本场景**不是有效杠杆**，保留为实验变量（供将来"大请求
  突发"场景按需收紧），默认仍 4 MB。

## 二-B、追加对照：glibc mmap/trim 阈值固定 128 KB（用户追加）

在 g3（trim + 驻留）基础上，容器加 `-e MALLOC_MMAP_THRESHOLD_=131072
-e MALLOC_TRIM_THRESHOLD_=131072`（只改 docker run 参数、不改服务代码）。依据
（用户）：glibc 默认会在每次归还大块后自动调高"大块"门槛，几轮之后 ~650 KB 的
请求体就改从普通堆分配、用完变碎片；固定门槛让这类大块走 mmap、用完立即归还 OS。

**同批同机**两组（旧 g3 数据没有 RssAnon 逐秒采样，故重跑一组无变量对照
`g3_recheck`；两组参数与 C2 基线相同：长尾 3 万/秒、每批 5000、4 进程 × 8 并发、
5 分钟 + 停发 60 秒）：

```
           m0      m1      m2      m3      m4      m5      m6(停发后)
g3_recheck:
  WS峰    96.1   197.0   211.1   205.8   228.9   236.8   175.2   (MiB)
  L       0      0       3       3       3       3       0
g5_mmap:
  WS峰    82.9   148.5   158.2   159.4   162.4   167.1   144.7   (MiB)
  L       0      0       0       0       0       0       0
```

| 指标 | g3_recheck（无变量） | g5_mmap（固定 128 KB） |
|---|---|---|
| 工作集 起始/峰值/结束 | 78.4 / **236.8** / 175.2 MiB | 68.8 / **179.1** / 144.7 MiB |
| RssAnon 起始/峰值/结束 | 72.2 / 196.6 / 141.1 MiB | 66.2 / **165.9** / 141.2 MiB |
| 逐秒级别分布 | 0 级 85s / **3 级 138s / 4 级 24s** | **0 级 246s（100%）** |
| 接受率 / 503 | 95.4% / 4.56% | **100% / 0%** |
| trim 调用 / 累计耗时 | 33 次 / 112 ms | 34 次 / **10 ms** |
| trim 累计回收 | 972.8 MiB（反复 churn、每次 20~40 MiB） | 31.9 MiB（churn 消失、无事可做） |

**结论：两个环境变量是本组实验里最大的单项收益。**
- **峰值工作集 236.8 → 179.1 MiB（−57.7，−24%）**，中后段从"贴 3/4 级、4.6% 请求被拒"
  变成 **246/246 秒全程第 0 级**（负载期间工作集 148→167 MiB 缓慢爬升，远低于 78%
  阈值 199.7 MiB）。
- **机制印证了用户的判断**：g3_recheck 的 trim 累计回收 972.8 MiB（33 次、每次
  20~40 MiB）说明解析 churn 的已释放页一直在被 glibc 从**普通堆**留着；固定
  `MALLOC_MMAP_THRESHOLD_=128KB` 后，~650 KB 的请求体（5000 条/批）改走 mmap、
  free 即还 OS——churn 从"留下碎片"变成"当场归还"，所以 g5_mmap 的 trim 累计只
  回收 31.9 MiB（无事可做）、耗时也从每次 ~3 ms 降到 ~0.3 ms。
- **代价**：每请求多走几次 mmap/munmap 系统调用（mmap 碎片是用户提到的潜在开销，
  实测未观察到负面影响：延迟 p99 与 g3 同量级、trim 更快）。环境变量只进
  `docker run` / 部署清单，**不改任何代码、不碰冻结模块**。
- **注意本组时段噪声**：g3_recheck 比上午的 g3 更糟（峰值 236.8 vs 213.9、
  出现 24s 的 L4），是压测机时段争抢差异（C2 的 caveat）；**同批对照内**
  g5 的 −57.7 MiB 与"全程 0 级"不受影响。

## 三、S4 攻击流量（全随机 3 万/秒 × 10 分钟）

配置 = 推荐组合（trim + 驻留均在默认开，在途 4 MB）。全随机分布：每个事件的 URL
与用户编号都单调递增、互不重复（C1/C2 里"对抗性流量"的口径）。

```
分钟   m0     m1     m2     m3     m4     m5     m6     m7     m8     m9     m10    m11
WS峰  78.1   208.8  223.4  210.2  227.3  230.2  223.0  230.5  225.6  223.2  233.8  180.8
降级   0      3      3      3      4      4      3      4      4      3      4      3
```

**工作集起始 / 峰值 / 结束 = 78.1 / 243.3 / 180.8 MiB；峰值降级 4；接受率 86.3%、
503 率 13.7%；trim 62 次共 282 ms。**

**结论——内存有界（本任务要的直接证据）：**
- **平台化，不随事件数增长**：m1（~1.5M 条）工作集就冲到 208.8 MiB，此后 10 分钟
  一直在 **208~234 MiB 平台**上震荡（845 万条时 ~230、900 万条仍 ~234），停发后
  trim 把 233.8 拉回 180.8 MiB。内存**随 600s 保留期填满而封顶**，不是随事件总数
  无限增长的泄漏——这正是"对抗性流量下内存有界"。
- **为什么随机不比长尾更糟**：吃内存的主体（①空载固定结构 Bloom 32 + 环 CMS 16.5、
  ②glibc 解析 churn 保留的已释放页 ~55、③32 并发 in-flight 解析 + 每连接 HTTP 栈
  ~45、④600s 保留期填满的数据相关存活对象 ~40）都**与 key 分布无关**。唯一随分布
  变的是线段树冻结名单（长尾 14.8 MB 有真热点 vs 随机 0.4 MB 近乎空），差 ~14 MiB
  被 URL 归一化缓存反向差（随机满 10 万条 10 MB vs 长尾 2.7 MB）基本抵消——C1 实测
  两分布进程内 RSS 增量 96.5 vs 96.6 MB 几乎相同。
- **驻留表在攻击下自身有界**：全随机每个值不重复、表只涨命中不到，整体清空策略把
  驻留表钉死在 cap（user 8192 + url 32768）以内，不随事件数增长。
- **平台在本容器偏高**：256 MB + 单核争抢下，平台（~230）压在 L4 阈值（230.4）上，
  持续 3 万/秒会降级到 4 级拒写（接受率 86.3%）——与长尾 g1 基线**同样的行为**，
  说明这是"平台位置 vs 阈值"问题，不是"随机流量特有的内存问题"。在更大的容器/
  无争抢环境，同一平台（~180~230）可能全程压在阈值之下（见 §六）。

## 四、S3 精度（长尾 3 万/秒 × 5 分钟，g3 配置）

配置 = 推荐组合（trim + 驻留）。存档 900 万条，抽 200 个已定稿区间与离线精确解
（`tools/exact.py`）对比。**这是 T9b 的第一份真正有效的精度数据**——对比 C2 那次
"内存涨到 L4、抽样全落降级期、召回 1.0/误差 0 是空响应假象"。

**抽样分桶（T10b 口径）：valid 200 / degraded 0 / rejected 0。** 200 个区间全部落在
非降级时刻（g3 负载期只有 15s 短暂 L3 尖峰，抽样区间按已定稿秒散布、避开了它们），
所以**全部 200 个样本都可比、精度由 valid 统计**：

| 指标 | 值 |
|---|---|
| Top-K url 召回 | **1.000**（10/10，200 区间全命中） |
| Top-K url 计数相对误差（均值） | **0.05%** |
| Top-K url 真实值落 [lower,upper] 比例 | **100%** |
| Top-K user 召回 | **1.000** |
| Top-K user 计数相对误差（均值） | **0.09%** |
| Top-K user 真实值落界比例 | **100%** |
| 去重用户数（HLL）相对误差（均值） | **0.92%** |
| p95 字节（DDSketch）相对误差（均值） | **0.14%** |

**判定**：内存稳到"接受率 100% + 200/200 有效样本"后，Top-K 两维召回 1.0、计数
误差 <0.1%、真实值 100% 落上下界内；HLL 去重 0.92%、DDSketch p95 0.14%，都在设计
精度内。**这证明 T9b-A（trim + 驻留）足以让服务在 3 万/秒持续写入下产出可信的统计
结果**——C2 判定"精度数据无效"的根因（内存涨到 L4 拒写/降级）已被 trim 解决。

> 说明：S3 严格说用 g3 配置跑，而 g3 有 15s 短暂 L3（不满足 C3 字面"全程 0 级"门槛）；
> 但 degraded=0/rejected=0 表明这 15s 没有污染任何一个抽样区间，精度数据有效。判读
> 依据见 C3-notes.md"二-A、S3 精度门槛的判读"。

## 五、推荐组合

**推荐 g5 = 定期 malloc_trim（默认每 10s） + 字符串驻留（user 8192 / url 32768，
默认开） + 容器环境变量 `MALLOC_MMAP_THRESHOLD_=131072` `MALLOC_TRIM_THRESHOLD_=131072`。**

理由（按消融逐项）：
1. **trim 是主杠杆、必做**：把"进 L4 拒写"拉到"不拒写"（接受率 87.8%→100%、503
   12.2%→0%）、峰值 −19.5 MiB、停发后回落 ~70 MiB。代价每次 ~3 ms、可忽略。
2. **驻留是次杠杆、值得做**：峰值不变（峰值是碎片/并发决定、驻留碰不到），但把
   中后段水位降 ~11 MiB，且把 g2"中后段 107s 连续 L3"压成"15s 内 1~5s 的偶发尖峰、
   每个分钟点都 L0"。代价表 <0.3 MB + 写桶前一次 dict 查，bench_model 未变慢。
3. **glibc mmap/trim 阈值固定 128 KB 是最大单项**（§二-B）：峰值再降 ~58 MiB、
   中后段从"贴 3/4 级"变**全程第 0 级**、接受率 95.4%→100%。零代码改动、只进部署
   清单，且让 trim 从"追 churn"变成"基本无事可做"（31.9 vs 972.8 MiB 累计回收）。
4. **在途降 2 MB 不做**（g4 对比 g3 无增益、也无额外 503）：本负载下在途窗口不是
   内存瓶颈。保留为实验变量（`FLOWLENS_MAX_PENDING_BYTES`），供"大请求突发"场景按需
   收紧，默认仍 4 MB。

## 六、距离"满载稳定保持第 0 级"还差多少 / 是否需要 T9b-B

**追加 mmap 对照后，推荐组合（g5）已经在 32 连接、3 万/秒、5 分钟满载下
246/246 秒全程第 0 级**（工作集峰值 179.1 MiB = 65%、离第 3 级阈值 199.7 MiB 还有
~20 MiB 余量、接受率 100%）。**"满载稳定保持第 0 级"在本容器（256 MB、单核争抢的
偏紧环境）已经达成。**

**剩余风险与余量**：
- 65% 的平台余量 ~35 MiB（到 256 上限）/~20 MiB（到 L3 阈值）。时段噪声（压测机
  争抢）在本批 g3_recheck 里让同配置峰值比上午高 ~23 MiB——**若评测环境的争抢更紧，
  余量可能吃掉一半**。进一步加固的杠杆（都不碰冻结模块、按收益排序）：
  1. **客户端降并发**（32 → 8 连接）：连接栈 + in-flight 解析从 ~45 降到 ~11 MiB，
     平台预计 ~135 MiB（53%）。
  2. **单批 5000 → 1000**：单请求解析峰值 ~2.5→0.5 MiB，解析高水位 ~58→12 MiB。
  3. 两者可叠加；均零精度代价。
- **S3 在 g5（mmap）配置下尚未做**（用户指令："内存问题解决后再做"）。g3 配置下的
  S3（§四，200/200 有效、召回 1.0）证明"统计精度不受这些内存手段影响"（驻留不改
  字符串内容与哈希、mmap 环境变量不改任何统计语义）；g5 配置下**应再跑一次 S3 确认
  全程 0 级下的精度**，作为最终交付的精度数据——这是"内存问题解决后"的明确后续。

**T9b-B（缩 Bloom / Count-Min，需改冻结的 config.py，用户决定）——不建议进入：**
- g5 已全程 0 级，**没有内存压力需要 T9b-B 来解决**。
- C1 §4.2/§4.3 实测：HLL p 14→12 省 8.89 MB 但去重误差翻倍（0.81%→1.6%）；Bloom
  位数减半省 16 MB 但满容量误判率 0.03%→1.78%（**×56**）——都是**用精度换内存**，
  而 S3 刚证明当前精度（召回 1.0、计数误差 0.05%、去重 0.92%、p95 0.14%）是达标且
  宝贵的。
- **结论：T9b-B 不需要**（除非评测环境比本容器更紧且客户端无法降并发，届时再议）。
