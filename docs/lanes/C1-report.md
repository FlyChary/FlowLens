# C1（T9a）内存账本报告

用 `tools/mem_report.py` 在满载状态下实测"内存到底花在哪里"，为 T9b 的加固决策
提供依据。本任务只测量与分析，未改任何 `flowlens/` 代码。

**测量环境**：Windows 开发机，conda `flowlens_env`（Python 3.11.17 / numpy 2.4.6），
`PYTHONHASHSEED=0`。**代码 = lane-c（本支线工作区）的 flowlens**——`mem_report.py`
启动时显式把项目根插到 `sys.path` 最前，保证 `import flowlens` 落在本支线代码上
（**首轮曾误用主仓库 T10b 的 model.py，全部作废重跑**，见 C1-notes.md"事故记录"）。
评测标准环境是 Linux 容器（Python 3.12），本机数字仅作相对量与量级参考，最终以
T10b 的容器实测为准。

**满载口径**：`flowgen` 分布，每秒 3 万条，模拟 660 秒（11 分钟，1980 万事件）——
线段树保留期（600 s）填满、活跃环（66 s）也满、Bloom 8 代各约 204 万插入（离
`per_gen` 200 万容量不远、未 saturated）。请求按 5000 条切分（单请求解压后 < 4 MB）。
每 2 秒做一次默认窗口 topk（user 维、带 at → 回放、进结果缓存），让查询缓存处于
工作态。

## 1. 内存账本

方法：按对象 id 去重的深度遍历（`gc.get_referents`，共享 seen、先到达者记账，跨
组件共享对象只计一次）；numpy 数组按 `nbytes`；key 字符串单列。交叉核对用**纯
服务端稳态 RSS**（`probe5`，无 EventGen，避免模拟工具自身 ~30 MB 及其 churn 污染）
与 tracemalloc 活跃操作峰值。**注意三层口径**：

- **对象图（存活数据）**：逻辑上真正持有的对象总量，是"该花多少"的账。
- **纯服务端稳态 RSS 增量**：容器 `memory.current` 会看到的服务端常驻（含分配器
  保留的已释放页），**不含模拟工具**。
- **EventGen 驱动 RSS 增量**：被模拟工具 churn 污染（多 ~150 MB），不代表服务端。

### 1.3 两种流量的关键结构差异

| 观察 | 长尾 | 随机 |
|---|---|---|
| 线段树冻结名单（keys+数组） | **14.82 MB** | **0.42 MB** |
| key 字符串 | 16.72 MB（url 15.3 万重复） | 4.43 MB（无重复） |
| URL 归一化缓存 | 2.66 MB（3.1 万条） | 9.99 MB（满 10 万条） |
| 纯服务端稳态 RSS 增量 | 96.5 MB | 96.6 MB |

**线段树冻结名单由热点驱动**：`Summary._fill` 只保留 `upper > u`（缺席上界）的条目。
长尾有真热点（头部 key 计数远超堆顶 u），名单装满 14.8 MB；随机所有 key 计数≈1、
缺席上界 u≈1、没有 key 超过它，名单被截到近乎空（0.42 MB）。**HLL（11.9 MB，固定
2^14 寄存器）与流量无关，两种流量一样大**——它是线段树的内存大头且不可压缩（除非降 p）。
**纯服务端 RSS 两种流量几乎相同（96.5 vs 96.6 MB）**：常驻内存的上限由固定结构
（Bloom 32 + 环 CMS 16.5 + 各 HLL/DD/CMS 固定数组）决定，与热点程度关系不大。

## 2. 最坏情况推算与余量（256 MB 容器）

分项（长尾 = 内存上界档；单位 MB）：

| 项 | MB | 依据 |
|---|---:|---|
| ① Python 运行时与依赖（基线） | ~40 | 本机 conda 3.11 基线 38 MB；容器 3.12-slim 待 T10b 实测 |
| ② 满载常驻（纯服务端稳态 RSS 增量，含分配器保留） | ~97 | `probe5`（无 EventGen）：长尾 96.5 / 随机 96.6 |
| ③ 单个 4 MB 请求解析+写入的**瞬时**峰值 | ~+60–67 | `--peak`：tracemalloc 峰值增量 identity 62.6 / gzip 66.7 MB；处理后**只保留 2.5 MB**（40k 事件写入 1–2 个秒桶的堆/字符串），其余 ~60 MB 是 orjson 解析出的 4 万个 dict + numpy 临时列，**请求结束即释放** |
| ④ 查询临时内存 | 含在 ② 里 | 单次 topk 的 Part 数组/np.unique 瞬时、远小于 ③ |
| **稳态满载（① + ②，无在途大请求）** | **~137** | — |
| **最坏瞬时（稳态 + ③，单个 4 MB 请求在途）** | **~197–204** | Admission 在途上限 4 MB → 同时最多一个 4 MB 请求，③ 不叠加 |

对照降级阈值（上限 256 MB 的比例；第 3 级 = 78% = 199.7 MB，第 4 级 = 90% = 230 MB）：

| 状态 | 估算 | 占 256 MB | 判定 |
|---|---:|---:|---|
| 稳态满载（无在途大请求） | ~137 MB | ~54% | 安全（远低于 78%） |
| 满载 + 单个 4 MB 请求在途（**最坏瞬时**） | ~197–204 MB | **~77–80%** | **正好压在 78%（199.7 MB）第 3 级阈值上** |

**结论：正常稳态满载不会误入降级（~54%）；但"满载 + 单个 4 MB 大请求在途"的最坏
瞬时正好落在 78% 第 3 级阈值附近（77–80%），会瞬时触发第 3 级（收紧在途预算 +
清缓存），请求处理完（释放 ~60 MB）立即回落到 54%。** 这是可接受的自我保护、不是
故障，但说明**大请求的瞬时解析峰值是内存的主要风险**（比常驻结构更值得优化）。
三个不确定项会让它更容易/更难越线：
1. 容器基线若比本机高（B1b 实测容器空闲 `memory.current` 173.5 MB，但那是含页
   缓存的旧口径；T10b 改用工作集后基线应更低，需实测）——基线每高 10 MB，最坏瞬时
   就近 10 MB；
2. 分配器保留：本机 `probe6` 自洽对照（RSS 增量 110.8 / 对象图 88，差 ~23 MB 保留）；
   Linux glibc 的 mmap 归还行为与 Windows MSVC 不同，③ 的瞬时值与保留量需在容器复测；
3. URL 分布：query 重复率低时（如本测）归一化缓存不命中、key 字符串不共享，② 取上界
   （长尾对象图 117 / 随机 99）；T10b 合并后 url 共享，② 会降到更接近随机档。

**最坏瞬时离 256 MB 仍有 ~52–59 MB 余量、离 90%（230 MB）第 4 级 ~26–33 MB，不会
OOM；但会瞬时压到 78% 第 3 级——需 T10b 容器实测确认"大请求 + 满载"不是常态，而是
偶发瞬时。**

## 3. 与设计文档第 5 节估算的差异

设计 §5 估算：运行时 45 + 活跃环 34 + 线段树 30 + 字符串表上限 13 + Bloom 34 +
在途写入 20 + 查询临时/快照 20 = **195 MB**。实测（长尾对象图）：

| 设计项（估算 MB） | 实测（MB） | 偏差 | 原因 |
|---|---:|---|---|
| 活跃环 34 | 30.7（环 CMS 16.5 + 名单 12.9 + HLL 1.0 + DD 0.2） | 略高估 | 接近 |
| 线段树 30 | 35.1（冻结名单 14.8 + HLL 11.9 + 候选堆 3.5 + DD 2.6 + CMS 2.3） | **低估 ~5** | 设计未充分计入 **HLL 759 实例 × 16 KB = 11.9 MB**（叶子 600 + 各层节点 + 构建中） |
| 字符串表上限 13 | 16.7（长尾 key 字符串）| 口径不同 | **没有独立"字符串表"**；key 字符串分散在各名单。16.7 是 lane-c 原始 model.py（url 不共享）口径；T10b 合并后 url 共享，降到低个位数 MB |
| 去重 Bloom 34 | 32.0 | 接近 | bits=25、8 代 |
| 在途写入 20 | **瞬时峰值 +60–67（处理后仅保留 2.5）** | **低估 ~3×（瞬时口径）** | orjson 解析把 4 MB JSON 膨胀成 4 万个 dict + numpy 临时列，tracemalloc 峰值 62.6/66.7 MB；请求结束即释放。设计 20 MB 偏乐观 |
| 查询临时/快照 20 | 快照仅 0.04 MB；单次查询瞬时临时 << 20 | 口径不同 | 快照是**共享引用**（不复制 Part），几乎不占；"查询临时"是瞬时对象 |
| **合计 195** | **对象图 117（存活数据）/ 容器 RSS 稳态 ~137 / 最坏瞬时 ~197–204** | 存活口径高估 ~78；RSS 口径接近 | 设计把"在途 20 + 查询 20 + 字符串表 13"等**瞬时/重复/未共享**项按最坏叠加：对"存活数据"口径高估 ~78 MB（实际 117）；对"容器 RSS 最坏瞬时"口径则接近（195 vs 197–204）——设计的 195 更接近"最坏瞬时"而非"稳态常驻" |

**差异最大的三项**：① "字符串表 13" 是伪命题（无独立表，且 T10b 后 url 共享）；
② "在途写入 20" 低估了 orjson 解析的瞬时膨胀（实测瞬时峰值 +60–67 MB）——这也是
§2"最坏瞬时压到 78% 阈值"的主因；③ 线段树低估了 HLL（759 实例 × 16 KB = 11.9 MB）。

## 4. 节省方案测算与 T9b 建议

### 4.1 字符串驻留（写入端，替换 ingest 前的 batch 字符串）

| | 长尾 | 随机 |
|---|---|---|
| url 侧：不同值 / 对象 / 重复 | 1,847 / 155,083 / 153,236 | 36,830 / 36,830 / 0 |
| url 侧净省 | **9.04 MB** | **−1.97 MB**（负） |
| user 侧：不同值 / 对象 / 重复 | 2,448 / 148,994 / 146,546 | 36,835 / 36,835 / 0 |
| user 侧净省 | **7.21 MB** | **−1.97 MB**（负） |
| 驻留表自身开销（条目 × 56 B） | url 0.10 + user 0.13 MB | 各 1.97 MB |
| 写入耗时影响（微基准外推） | 1.3 ms/模拟秒 | 2.1 ms/模拟秒 |

**关键结论（见 §5 详述）**：
- **url 侧**：在 lane-c 原始 model.py 下重复 15.3 万份（9 MB），但**主线 T10b 已把
  归一化缓存键改成"先剥 query/fragment 的稳定路径"**（`model.py` 的
  `_strip_query_fragment` + `_norm_cache`）——归一化缓存本身就成了以稳定路径为键的
  驻留表，**命中时复用同一字符串对象**，url 侧驻留被 T10b **顺带免费做掉**。
- **user 侧**：T10b 不覆盖（user_id 不走 URL 归一化）。长尾下 7.34 MB 浪费，需独立
  写入端驻留表（`user_id → 字符串`），净省 7.21 MB，写入 +1.3 ms/s（可忽略），表
  开销 0.13 MB。**值得做，且只在写入端、不碰冻结模块。**
- **全随机流量**：url 与 user 都互不重复（重复 0），驻留表每条都是新值、表比省的
  还贵（净省 −1.97 MB）。**全随机下驻留表上限应设为 0（不启用）或带 LRU 淘汰**，
  否则反而增加内存。上限的取舍：长尾不同值 ~2448（user）/ 1847（url），随机 3.7 万；
  设 **8192 的 LRU**（满则整体清空，与归一化缓存同策略）即可覆盖长尾收益、限制随机
  开销到 < 0.5 MB。

### 4.2 叶子/节点 HLL p=14→12

线段树 759 实例省 **8.89 MB**（+ 活跃环 66 实例 0.77 MB）；标准误差 **2.89% →
5.78%**。**不推荐**：为省 9 MB 把去重人数误差翻倍（0.81% → 1.6% 量级），收益/代价
不划算，且 9 MB 在 256 MB 里不是瓶颈。

### 4.3 去重 Bloom 位数减半

m 33.5M→16.8M、k 12→6，省 16 MB。**代价：满容量误判率 0.0316% → 1.779%（×56）**，
150% 容量 0.6585% → 8.11%。**不推荐**：误判率是"新事件被误当重复丢掉"，8% 在过载
时不可接受；且 Bloom 32 MB 是固定的，减半省 16 MB 不足以改变"最坏瞬时逼近 78%"的
结论。若确需省内存，应降 `per_gen`（200 万→100 万）而非直接减半。

### 4.4 秒桶名单容量 512→256

双引擎同序对照（最后 60 s、url 维，`tools/exact.py` 的 topk/compare）：

| 分布 | k | cap=512 | cap=256 |
|---|---:|---|---|
| 长尾 | 100（API 上限） | 召回 1.0、重叠 1.0 | 召回 1.0、重叠 1.0（**无差异**） |
| 长尾 | 512 | 召回 0.975、unseen 295 | 召回 0.945、unseen 601 |
| 随机 | 100 | 原始重叠 5% | 2%（都在 count=1 的并列噪声里） |

**现实查询 k ≤ 100（API 上限），长尾热点足够重、256 的名单装得下，降容量对现实
Top-K 无影响**；差异只在 k=512（超出 API 上限）。**可作为可选优化**（省活跃环名单
~6 MB + 候选堆），但收益小、且降低极端长尾下 k>100 的回放精度，**非必需**。

### 4.5 T9b 建议（按优先级）

1. **user 侧写入端驻留表**（净省 ~7 MB，+1.3 ms/s，不碰冻结模块）——**做**。这是
   "T9 驻留表"的实质内容，且范围缩小到只 user、只写入端。
2. **不降 HLL p、不减 Bloom 位**——收益不足以抵消误差/误判率代价。
3. **url 侧驻留：依赖 T10b 的缓存键改动**——若 T10b 合并，url 侧无需再动；若 T10b
   未合并，则 url 侧驻留收益 9 MB，但更该做的是先把 T10b 的缓存键改动静下来（它
   同时解决 url 驻留 + 归一化缓存命中率）。
4. **秒桶名单 512→256**：可选、非必需，留 T11 视压测 CPU 决定。
5. **真正的大头（Bloom 32 + 环 CMS 16.5 + 线段树 HLL 12 = ~60 MB 固定结构）没有低
   代价的省法**，T9b 的加固重点应是**确认容器基线 + 分配器保留 + 大请求瞬时峰值
   的叠加**（§2 的"最坏瞬时逼近 78%"），而非抠这几 MB。

## 5. 字符串驻留表是否值得做（决定 T9 与 segtree.py 冲突是否需解决）

**明确结论：值得做，但范围可大幅缩小，且与冻结的 segtree.py 无冲突。**

1. **T9 原计划"驻留表与冻结的 segtree.py 冲突"的问题可以消解**：写入端驻留
   （`ingest` 里、`engine` 写入秒桶之前把 `batch.users` 替换为驻留对象）发生在数据
   进入引擎**之前**；进引擎后各结构（秒桶堆、候选堆、叶子/节点 keys、快照）引用的
   都是同一个字符串对象，**冻结的 segtree 只是引用、无需修改**。所以驻留不需要动
   segtree.py，冲突不存在。
2. **只需要 user 侧**：url 侧被 T10b 的缓存键改动顺带覆盖（见 §4.1）。
3. **收益/代价**：长尾净省 ~7.2 MB、+1.3 ms/s、表 0.13 MB——正收益、代价可忽略。
4. **上限**：8192 的 LRU（满则整体清空，与归一化缓存同策略），覆盖长尾、限制随机
   开销。

**前置确认**：url 侧结论依赖 T10b 的 model.py 缓存键改动（先剥 query 再查缓存）。
C1 基于的 lane-c 还没有该改动（lane-c 的 model.py 是按完整 raw URL 查缓存、url 不
共享）。**需用户确认 T10b 是否已定稿/将合并**——若合并，T9 的驻留表退化为"仅
