## 1. 本地复测 ingest_parsed 每条耗时（块 2000 vs 10000，P1b 三.3 前置）

方法：长尾 40 万条，逐块调 `engine.ingest_parsed`（写入核心，与容器主进程同路径），
计时取"总耗时/总条数"。本地 Python 3.11（比容器 Python 3.12 略慢）。

| 每块条数 | 每条耗时 | 单块同步耗时 |
|---|---|---|
| 2000（改前） | 1.99 μs | 6.6 ms |
| 5000 | 1.84 μs | 11.8 ms |
| 10000（改后 POOLED_CHUNK_EVENTS） | 1.75 μs | 26.3 ms |

结论：块越大主进程每条越省（2000→10000 降约 12%），单块同步耗时相应增长
（6.6→26.3 ms），方向与 P1b 二点五审查方表（2.98→1.88 μs/条、6.0→18.8 ms/块）一致，
确认 `POOLED_CHUNK_EVENTS=10000` 改动生效。

## 2. 块大小改动与等价性测试口径（提交 c850366）

- `ingest.py`：新增 `POOLED_CHUNK_EVENTS=10000`，仅进程池路径用它切块；单进程路径
  仍用 `CHUNK_EVENTS=2000`。
- 等价性测试（test_ingest_parsed_equals_ingest / test_pool_path_full_equivalence）：
  两条路径改用**同一块大小**切块（把块大小这个性能旋钮固定、只留"路径"变量）。
  原因：Top-K 名单是近似结构、堆成员对"逐秒 observe 的分批顺序"敏感，块大小不同会在
  高基数流量的名单深尾部产生少量差异（sketch 固有性质、非 bug）；改前池路径用 2000、
  in-proc 也用 2000 故相等，池路径改 10000 后两条路径切块不同、深尾不等。全量
  363 passed。

## 3. 修正后的测量方法（P1b 三.1 + 审查方两点修正）

新写 `tools/s1_measure.py`（严格串行版），运行在 **WSL 宿主机**（driver 需要 WSL 的
docker 守护、WSL /proc、taskset；服务在容器里）：
- 整个爬坡只启动一个容器，档位之间不重启（/healthz 计数器是累计的）。
- 每档严格串行：档前同步读 /healthz（H0）+ 宿主 /proc 主进程与各解析进程 CPU 时间（C0）+
  t0 → 跑 loadgen（taskset 固定到 load 核）阻塞等退出读汇总 → sleep 1 让尾部请求写完 →
  档后读 /healthz（H1）+ CPU 时间（C1）+ t1。
- 接受条数/在途拒绝/原始体拒绝 = H1−H0 差值；主进程 CPU 秒 = C1.main−C0.main；解析 CPU
  秒 = 各解析进程差值之和；**主进程每条 μs = 主进程 CPU 秒 ÷ 接受条数 × 1e6**（分子分母
  同窗口，不受窗口含 loadgen 启动/收尾影响，是主要判断依据）；主进程 CPU% = 主进程 CPU
  秒 ÷ (t1−t0) × 100（含爬坡/收尾一两秒，略偏低）。
- 读 CPU **不进容器**（修正 #1）：`docker inspect -f {{.State.Pid}}` 得主进程宿主 PID，
  扫宿主 /proc/*/stat 取 ppid==主进程的解析进程，**排除 resource_tracker**（修正 #2），
  断言解析进程数 == 期望（池开 3 / 池关 0）。
- 交叉核对：healthz 接受条数 vs loadgen 汇总 accepted，超 2% 标记。
- 后台每秒读 /healthz 的 memory_bytes 只记工作集峰值。

冒烟（池关、4 万×12s）：acc_h=acc_lg=480000，交叉核对 0.0%，us/ev=10.9 μs（落在池关
预期 10–14 μs），parse_cpu=0.0%（池关正确）。串行版正确。

## 4. 池开 16 MB 爬坡（2026-10-19）——第一次运行异常，已定位到"降级棘轮"

### 4.1 第一次完整爬坡（单容器 4/8/12/16/20/24 万）：异常

| 档位 | 接受率 | 在途拒绝 | 原始体拒绝 | 主进程 CPU% | 每条 μs | 解析 CPU% | 工作集峰值 |
|---|---|---|---|---|---|---|---|
| 4 万 | 63.1% | 105 | 84 | 19.8 | 10.5 | 12.8 | 236.4 MiB |
| 8 万 | 11.9% | 51 | 26 | 34.8 | 57.6 | 4.7 | 234.4 MiB |
| 12/16/20/24 万 | 0% | 0 | 0 | 27~42 | — | 0 | 221~232 MiB |

现象：8 万档开始崩，12 万+全 0；但**拒绝计数不增、errors_lg=0、交叉核对 0.0%**（healthz 与
loadgen 一致都是 0）——不是测量误差，是服务真的不收了，且不走 inflight/raw 计数路径。

### 4.2 聚焦复现（新容器，只跑 8 万+12 万）：健康

| 档位 | 接受率 | 在途拒绝 | 原始体拒绝 | 主进程 CPU% | 每条 μs | 解析 CPU% | degraded(档末) | 工作集峰值 |
|---|---|---|---|---|---|---|---|---|
| 8 万 | 95.6% | 333 | 50 | 40.2 | 6.65 | 40.2 | False | 223.6 MiB |
| 12 万 | 80.3% | 550 | 320 | 67.8 | 10.58 | 60.2 | **True** | 232.8 MiB |

### 4.3 定位：内存触发第 4 级降级后无法退出（"棘轮"）

- 阈值（degrade.py）：L3 = 内存 > 256×0.78=199.7 MiB；L4 = 内存 > 256×0.90=230.4 MiB。
  L4 行为（app.py）：`reject_ingest` —— **读取请求体之前直接 503**。这条路径不走
  inflight（尚未 try_reserve）也不走 raw budget（尚未 try_reserve），**两个拒绝计数器
  都不增**——与 4.1 中"12 万+全 0 且拒绝计数不动"完全吻合（loadgen 503 重试耗尽 → 全记
  rejected，accepted=0，errors=0）。
- 触发链：16 MB 原始额度下，一个在途请求最多 16 MB 解压+解析；池开时多请求并行，
  工作集峰值 223~236 MiB，常态就压在 L4 线（230.4）附近。爬坡单容器里，4 万档工作集
  就冲到 236.4 MiB → 进 L3/L4；之后负载不撤、内存缓降（glibc 碎片/环/树常驻），到
  L4 的退出线（<230.4×0.82/0.90 滞回区间）之前负载还在，**降不回去** → 后续各档全程
  L4 全拒。这就是 4.1 的形态。
- 聚焦运行（新容器、低档起步）工作集峰值 223~233 MiB，勉强压在 L4 线附近，故 8/12 万
  还能工作，但 12 万档末 degraded=True，已踩线。
- 结论：**256 MiB 容器 + 16 MB×2 额度 的组合，内存水位常态顶到第 4 级降级线**。这不是
  测量方法问题（交叉核对 0.0%、拒绝来源可区分都正常），是额度与内存限制的交互问题。

### 4.4 待审查方决定

- 若目标是"测出进程池真实上限"：需把内存水位压到降级线以下——选项：(a) 额度改回较小值
  （如 8 MB）；(b) 放宽容器内存（评测固定 256 MiB，本地实验可临时放宽以分离"额度"与
  "降级"两个因素）；(c) 按现状如实汇报"256 MiB 下 16 MB 额度触发 L4 降级，服务进入全拒
  状态且负载期间不恢复"。

审查方确认"降级棘轮"定位（L4 拒写不降内存，负载不撤退不出），设计问题留内存优化阶段；
本次改用 512 MiB 容器内存分离"额度"与"降级"（结论不能作为满足 256 MiB 约束的证据）。

### 5.1 判读

1. **CPU 上限档（接受率 ≥99% 且零拒绝的最高档）= 12 万**。16 万起出现原始体额度拒绝
   （139 次）且在途拒绝抬头，loadgen 发送率开始塌陷（16 万档只发出目标的 84%，24 万档
   54%）——拒绝 → Retry-After 等 1 秒 → 发送塌陷的老机制重现，这次由"主进程变慢 →
   请求占 raw 额度时间变长 → raw 额度满"触发。
2. **卡住档（16 万，实际吞吐 13.4 万/秒）三方 CPU**：主进程 89.5%（其 1 核上限的 89.5%）
   ≫ 解析池 100.8%（3 核上限的 33.6%）≫ 压测 554.5%（8 核上限的 69.3%）。**瓶颈在
   服务侧主进程（单写者事件循环）**：解析池还有约 2.4 倍余量、压测还有约 1.4 倍余量。
3. **主进程每条耗时随档位**：5.74 → 5.99 → 7.52 → 8.57 → 8.28 → 8.17 μs。低档平稳
   （~5.8），12 万起升至 7.5（事件循环内排队/tick 重叠），16 万后平台在 ~8.2–8.6。
   注：比审查方本地预测（块 10000 约 3.5–4 μs）高 ~1.7–2 倍——WSL2 + Docker 容器的
   环境开销比"用户机器 1.35 倍"的换算更大。
4. **内存**：最高可持续档（12 万）工作集峰值 276.5 MiB，比 256 MiB 容器的降级线
   （L3 = 256×0.78 ≈ 200 MiB）**高约 76.5 MiB**——这就是之后内存优化需要省出的量
   （16 MB 额度、12 万/秒 场景下）。memcur 峰值（含 glibc 碎片）同档 333.9 MiB，
   工作集与原始读数差 ~57 MiB，也提示碎片可回收空间。

### 5.2 结论（512 MiB 容器、16 MB 额度、块 10000）

- 最大可持续吞吐 ≈ **12 万事件/秒**（零拒绝、接受率 100%；16 万目标实际达成 13.4 万/秒
  但已有原始体额度拒绝）。
- 主进程每条耗时：**低档 ~5.8 μs，卡住档 ~8.6 μs**（单核主进程的理论上限
  1/8.6μs ≈ 11.6 万/秒，与实测一致）。
- 瓶颈：主进程（单写者事件循环），不在解析池、不在压测端。
- 该结论**仅说明额度放开后进程池的 CPU 上限**，不代表 256 MiB 约束下的表现（256 MiB
  下会先撞上 §4 的降级棘轮）。
