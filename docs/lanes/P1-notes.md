## 1. 本地复测 ingest_parsed 每条耗时（块 2000 vs 10000，P1b 三.3 前置）

方法：长尾 40 万条，逐块调 `engine.ingest_parsed`（写入核心，与容器主进程同路径），
计时取"总耗时/总条数"。本地 Python 3.11（比容器 Python 3.12 略慢）。

| 每块条数 | 每条耗时 | 单块同步耗时 |
|---|---|---|
| 2000（改前） | 1.99 μs | 6.6 ms |
| 5000 | 1.84 μs | 11.8 ms |
| 10000（改后 POOLED_CHUNK_EVENTS） | 1.75 μs | 26.3 ms |

结论：块越大主进程每条越省（2000→10000 降约 12%），单块同步耗时相应增长
（6.6→26.3 ms），方向与 P1b 二点五审查方表（2.98→1.88 μs/条、6.0→18.8 ms/块）一致，
确认 `POOLED_CHUNK_EVENTS=10000` 改动生效。

## 2. 块大小改动与等价性测试口径（提交 c850366）

- `ingest.py`：新增 `POOLED_CHUNK_EVENTS=10000`，仅进程池路径用它切块；单进程路径
  仍用 `CHUNK_EVENTS=2000`。
- 等价性测试（test_ingest_parsed_equals_ingest / test_pool_path_full_equivalence）：
  两条路径改用**同一块大小**切块（把块大小这个性能旋钮固定、只留"路径"变量）。
  原因：Top-K 名单是近似结构、堆成员对"逐秒 observe 的分批顺序"敏感，块大小不同会在
  高基数流量的名单深尾部产生少量差异（sketch 固有性质、非 bug）；改前池路径用 2000、
  in-proc 也用 2000 故相等，池路径改 10000 后两条路径切块不同、深尾不等。全量
  363 passed。

## 3. 修正后的测量方法（P1b 三.1 + 审查方两点修正）

新写 `tools/s1_measure.py`（严格串行版），运行在 **WSL 宿主机**（driver 需要 WSL 的
docker 守护、WSL /proc、taskset；服务在容器里）：
- 整个爬坡只启动一个容器，档位之间不重启（/healthz 计数器是累计的）。
- 每档严格串行：档前同步读 /healthz（H0）+ 宿主 /proc 主进程与各解析进程 CPU 时间（C0）+
  t0 → 跑 loadgen（taskset 固定到 load 核）阻塞等退出读汇总 → sleep 1 让尾部请求写完 →
  档后读 /healthz（H1）+ CPU 时间（C1）+ t1。
- 接受条数/在途拒绝/原始体拒绝 = H1−H0 差值；主进程 CPU 秒 = C1.main−C0.main；解析 CPU
  秒 = 各解析进程差值之和；**主进程每条 μs = 主进程 CPU 秒 ÷ 接受条数 × 1e6**（分子分母
  同窗口，不受窗口含 loadgen 启动/收尾影响，是主要判断依据）；主进程 CPU% = 主进程 CPU
  秒 ÷ (t1−t0) × 100（含爬坡/收尾一两秒，略偏低）。
- 读 CPU **不进容器**（修正 #1）：`docker inspect -f {{.State.Pid}}` 得主进程宿主 PID，
  扫宿主 /proc/*/stat 取 ppid==主进程的解析进程，**排除 resource_tracker**（修正 #2），
  断言解析进程数 == 期望（池开 3 / 池关 0）。
- 交叉核对：healthz 接受条数 vs loadgen 汇总 accepted，超 2% 标记。
- 后台每秒读 /healthz 的 memory_bytes 只记工作集峰值。

冒烟（池关、4 万×12s）：acc_h=acc_lg=480000，交叉核对 0.0%，us/ev=10.9 μs（落在池关
预期 10–14 μs），parse_cpu=0.0%（池关正确）。串行版正确。
