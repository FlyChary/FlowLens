## 1. 本地复测 ingest_parsed 每条耗时（块 2000 vs 10000，P1b 三.3 前置）

方法：长尾 40 万条，逐块调 `engine.ingest_parsed`（写入核心，与容器主进程同路径），
计时取"总耗时/总条数"。本地 Python 3.11（比容器 Python 3.12 略慢）。

| 每块条数 | 每条耗时 | 单块同步耗时 |
|---|---|---|
| 2000（改前） | 1.99 μs | 6.6 ms |
| 5000 | 1.84 μs | 11.8 ms |
| 10000（改后 POOLED_CHUNK_EVENTS） | 1.75 μs | 26.3 ms |

结论：块越大主进程每条越省（2000→10000 降约 12%），单块同步耗时相应增长
（6.6→26.3 ms），方向与 P1b 二点五审查方表（2.98→1.88 μs/条、6.0→18.8 ms/块）一致，
确认 `POOLED_CHUNK_EVENTS=10000` 改动生效。

## 2. 块大小改动与等价性测试口径（提交 c850366）

- `ingest.py`：新增 `POOLED_CHUNK_EVENTS=10000`，仅进程池路径用它切块；单进程路径
  仍用 `CHUNK_EVENTS=2000`。
- 等价性测试（test_ingest_parsed_equals_ingest / test_pool_path_full_equivalence）：
  两条路径改用**同一块大小**切块（把块大小这个性能旋钮固定、只留"路径"变量）。
  原因：Top-K 名单是近似结构、堆成员对"逐秒 observe 的分批顺序"敏感，块大小不同会在
  高基数流量的名单深尾部产生少量差异（sketch 固有性质、非 bug）；改前池路径用 2000、
  in-proc 也用 2000 故相等，池路径改 10000 后两条路径切块不同、深尾不等。全量
  363 passed。

## 3. 修正后的测量方法（P1b 三.1 + 审查方两点修正）

新写 `tools/s1_measure.py`（严格串行版），运行在 **WSL 宿主机**（driver 需要 WSL 的
docker 守护、WSL /proc、taskset；服务在容器里）：
- 整个爬坡只启动一个容器，档位之间不重启（/healthz 计数器是累计的）。
- 每档严格串行：档前同步读 /healthz（H0）+ 宿主 /proc 主进程与各解析进程 CPU 时间（C0）+
  t0 → 跑 loadgen（taskset 固定到 load 核）阻塞等退出读汇总 → sleep 1 让尾部请求写完 →
  档后读 /healthz（H1）+ CPU 时间（C1）+ t1。
- 接受条数/在途拒绝/原始体拒绝 = H1−H0 差值；主进程 CPU 秒 = C1.main−C0.main；解析 CPU
  秒 = 各解析进程差值之和；**主进程每条 μs = 主进程 CPU 秒 ÷ 接受条数 × 1e6**（分子分母
  同窗口，不受窗口含 loadgen 启动/收尾影响，是主要判断依据）；主进程 CPU% = 主进程 CPU
  秒 ÷ (t1−t0) × 100（含爬坡/收尾一两秒，略偏低）。
- 读 CPU **不进容器**（修正 #1）：`docker inspect -f {{.State.Pid}}` 得主进程宿主 PID，
  扫宿主 /proc/*/stat 取 ppid==主进程的解析进程，**排除 resource_tracker**（修正 #2），
  断言解析进程数 == 期望（池开 3 / 池关 0）。
- 交叉核对：healthz 接受条数 vs loadgen 汇总 accepted，超 2% 标记。
- 后台每秒读 /healthz 的 memory_bytes 只记工作集峰值。

冒烟（池关、4 万×12s）：acc_h=acc_lg=480000，交叉核对 0.0%，us/ev=10.9 μs（落在池关
预期 10–14 μs），parse_cpu=0.0%（池关正确）。串行版正确。

## 4. 池开 16 MB 爬坡（2026-10-19）——第一次运行异常，已定位到"降级棘轮"

### 4.1 第一次完整爬坡（单容器 4/8/12/16/20/24 万）：异常

| 档位 | 接受率 | 在途拒绝 | 原始体拒绝 | 主进程 CPU% | 每条 μs | 解析 CPU% | 工作集峰值 |
|---|---|---|---|---|---|---|---|
| 4 万 | 63.1% | 105 | 84 | 19.8 | 10.5 | 12.8 | 236.4 MiB |
| 8 万 | 11.9% | 51 | 26 | 34.8 | 57.6 | 4.7 | 234.4 MiB |
| 12/16/20/24 万 | 0% | 0 | 0 | 27~42 | — | 0 | 221~232 MiB |

现象：8 万档开始崩，12 万+全 0；但**拒绝计数不增、errors_lg=0、交叉核对 0.0%**（healthz 与
loadgen 一致都是 0）——不是测量误差，是服务真的不收了，且不走 inflight/raw 计数路径。

### 4.2 聚焦复现（新容器，只跑 8 万+12 万）：健康

| 档位 | 接受率 | 在途拒绝 | 原始体拒绝 | 主进程 CPU% | 每条 μs | 解析 CPU% | degraded(档末) | 工作集峰值 |
|---|---|---|---|---|---|---|---|---|
| 8 万 | 95.6% | 333 | 50 | 40.2 | 6.65 | 40.2 | False | 223.6 MiB |
| 12 万 | 80.3% | 550 | 320 | 67.8 | 10.58 | 60.2 | **True** | 232.8 MiB |

### 4.3 定位：内存触发第 4 级降级后无法退出（"棘轮"）

- 阈值（degrade.py）：L3 = 内存 > 256×0.78=199.7 MiB；L4 = 内存 > 256×0.90=230.4 MiB。
  L4 行为（app.py）：`reject_ingest` —— **读取请求体之前直接 503**。这条路径不走
  inflight（尚未 try_reserve）也不走 raw budget（尚未 try_reserve），**两个拒绝计数器
  都不增**——与 4.1 中"12 万+全 0 且拒绝计数不动"完全吻合（loadgen 503 重试耗尽 → 全记
  rejected，accepted=0，errors=0）。
- 触发链：16 MB 原始额度下，一个在途请求最多 16 MB 解压+解析；池开时多请求并行，
  工作集峰值 223~236 MiB，常态就压在 L4 线（230.4）附近。爬坡单容器里，4 万档工作集
  就冲到 236.4 MiB → 进 L3/L4；之后负载不撤、内存缓降（glibc 碎片/环/树常驻），到
  L4 的退出线（<230.4×0.82/0.90 滞回区间）之前负载还在，**降不回去** → 后续各档全程
  L4 全拒。这就是 4.1 的形态。
- 聚焦运行（新容器、低档起步）工作集峰值 223~233 MiB，勉强压在 L4 线附近，故 8/12 万
  还能工作，但 12 万档末 degraded=True，已踩线。
- 结论：**256 MiB 容器 + 16 MB×2 额度 的组合，内存水位常态顶到第 4 级降级线**。这不是
  测量方法问题（交叉核对 0.0%、拒绝来源可区分都正常），是额度与内存限制的交互问题。

### 4.4 待审查方决定

- 若目标是"测出进程池真实上限"：需把内存水位压到降级线以下——选项：(a) 额度改回较小值
  （如 8 MB）；(b) 放宽容器内存（评测固定 256 MiB，本地实验可临时放宽以分离"额度"与
  "降级"两个因素）；(c) 按现状如实汇报"256 MiB 下 16 MB 额度触发 L4 降级，服务进入全拒
  状态且负载期间不恢复"。

审查方确认"降级棘轮"定位（L4 拒写不降内存，负载不撤退不出），设计问题留内存优化阶段；
本次改用 512 MiB 容器内存分离"额度"与"降级"（结论不能作为满足 256 MiB 约束的证据）。

### 5.1 判读

1. **CPU 上限档（接受率 ≥99% 且零拒绝的最高档）= 12 万**。16 万起出现原始体额度拒绝
   （139 次）且在途拒绝抬头，loadgen 发送率开始塌陷（16 万档只发出目标的 84%，24 万档
   54%）——拒绝 → Retry-After 等 1 秒 → 发送塌陷的老机制重现，这次由"主进程变慢 →
   请求占 raw 额度时间变长 → raw 额度满"触发。
2. **卡住档（16 万，实际吞吐 13.4 万/秒）三方 CPU**：主进程 89.5%（其 1 核上限的 89.5%）
   ≫ 解析池 100.8%（3 核上限的 33.6%）≫ 压测 554.5%（8 核上限的 69.3%）。**瓶颈在
   服务侧主进程（单写者事件循环）**：解析池还有约 2.4 倍余量、压测还有约 1.4 倍余量。
3. **主进程每条耗时随档位**：5.74 → 5.99 → 7.52 → 8.57 → 8.28 → 8.17 μs。低档平稳
   （~5.8），12 万起升至 7.5（事件循环内排队/tick 重叠），16 万后平台在 ~8.2–8.6。
   注：比审查方本地预测（块 10000 约 3.5–4 μs）高 ~1.7–2 倍——WSL2 + Docker 容器的
   环境开销比"用户机器 1.35 倍"的换算更大。
4. **内存**：最高可持续档（12 万）工作集峰值 276.5 MiB，比 256 MiB 容器的降级线
   （L3 = 256×0.78 ≈ 200 MiB）**高约 76.5 MiB**——这就是之后内存优化需要省出的量
   （16 MB 额度、12 万/秒 场景下）。memcur 峰值（含 glibc 碎片）同档 333.9 MiB，
   工作集与原始读数差 ~57 MiB，也提示碎片可回收空间。

### 5.2 结论（512 MiB 容器、16 MB 额度、块 10000）

- 最大可持续吞吐 ≈ **12 万事件/秒**（零拒绝、接受率 100%；16 万目标实际达成 13.4 万/秒
  但已有原始体额度拒绝）。
- 主进程每条耗时：**低档 ~5.8 μs，卡住档 ~8.6 μs**（单核主进程的理论上限
  1/8.6μs ≈ 11.6 万/秒，与实测一致）。
- 瓶颈：主进程（单写者事件循环），不在解析池、不在压测端。
- 该结论**仅说明额度放开后进程池的 CPU 上限**，不代表 256 MiB 约束下的表现（256 MiB
  下会先撞上 §4 的降级棘轮）。

**判读**：
1. **在途 6 MB 无效**——与 2w+8MB 基本一样（甚至略差：4 万档工作集 230 vs 222 MiB），

3. **但 1w 仍达不到验收标准 1 的 9 万**：8 万档已进 3 级（98.8%），10 万档 84%。

`--pool off`（单进程路径，与"已提交版本"单核行为同路径），同四档：

| 配置 | 4万 acc/级/ws | 6万 acc/级/ws | 8万 acc/级/ws | 10万 acc/级/ws |
|---|---|---|---|---|
| **池关（单进程）** | 100% / 0 / 168.8 | 99.6% / 0 / 193.8 | 75.3% / 3 / 200.6 | 71.7% / 3 / 204.6 |
| 池 1w + 8MB | 100% / 0 / 181.8 | 100% / 0 / 190.0 | 98.8% / 3 / 201.7 | 84.0% / 3 / 214.5 |
| 池 2w + 8MB | 95.0% / 3 / 222.0 | 78.3% / 4 / 239.8 | 52.8% / 4 / 236.6 | 55.9% / 4 / 239.3 |
| 池 2w + 6MB | 95.6% / 4 / 230.5 | 77.9% / 4 / 232.3 | 54.1% / 4 / 244.5 | 61.7% / 4 / 244.6 |

（列 = 接受率 / 最高降级级 / 工作集峰值 MiB；主进程 CPU% 见 JSON。单进程 8 万主进程
CPU 87.3%、10 万 90.6%——同时被 CPU 与内存压住。）

**核心结论（P1c 目标的诚实判读）**：
1. **单进程（已提交版本）在 256 MB 下同样内存受限**：8 万档工作集 200.6 MiB 已碰
   L3 线（199.7）、主进程 CPU 87%。单进程 256 MB 最大可持续 ≈ **6 万**（99.6%、L0）。
   与 P1b/T11a"单核 CPU 上限 ~7.5 万、但端到端因内存只测到 5 万"一致。
2. **进程池在 256 MB 下不能把吞吐提到 2×单进程，反而更差**：
   - 单进程瓶颈是"主进程 = 单写者 CPU + 全部统计状态内存（~170-205 MiB 常驻）"。
   - 池把"解析"CPU 搬进 worker（主进程 CPU% 从 65% 降到 30% @6万），**但统计状态
     内存全在主进程、池省不掉**；worker 还额外加 19~35 MiB/个。
   - 结果：2w 的工作集（222~240 MiB）比单进程（168~205 MiB）更高，更早压过 L3/L4
     线 → 接受率反而最低。**内存（统计状态）才是 256 MB 下的约束，不是解析 CPU。**
3. **1w 是池配置里最好的**（6 万 100% L0、8 万 98.8% L3），但仍 < 9 万、8 万起进 3 级。
   2w+6MB 与 2w+8MB 基本一样（6MB 无效，与 C3 一致）。
4. **验收标准 1（≥9 万、2×单进程、全程 0 级）在 256 MB 下不满足**：任何配置都达不到。
   根因是统计状态常驻内存（~200 MiB）本身就在 256 MB 的 L3 线附近——四项调整省的是
   **空闲/worker 内存**，省不了**满载的统计状态**，所以救不回满载水位。池的 2× 收益
   只有在内存有余量（P1b §5 的 512 MB）时才兑现；256 MB 下被内存顶掉。

**按 P1c §二**：标准 1、2 均不满足，已按要求试了 6 MB 与 1 worker 并报告各配置吞吐
与内存，**不放宽验收标准**。继续跑 S3（精度，30k/s 应 L0、可比对已提交版本）、
S2（混合负载，仅报告）、单核对照（§6.10）。

### 6.13 补记：P1c 的"池关"配置比已提交版本差（内存与精度）

P1c 的"池关"（单进程路径）**不等价于已提交版本**：长尾 3 万/秒 × 5 分钟（S3）下，
池关进入第 3 级（工作集峰值 227.4 MiB、L3 持续 148/303 秒、期间采样权重 2）、
计数误差 0.35%/0.48%；而已提交版本（T9b g3 参照、相同条件）全程第 0 级、
计数误差 0.05%/0.09%（<0.1%）。召回/落界/去重/p95 两者都在参照水平，差别主要在
"是否进第 3 级"这一个环节。

现单进程路径与已提交版本的差异（P1 第一~三节引入，git 历史已核对）：
- 块大小 `CHUNK_EVENTS` 5000 → 2000（每 2000 条让出一次事件循环）；
- "写入引擎"段被写入信号量串行化（决定五，池/非池两路径共用）。

**怀疑**：块更小 + 信号量让出点变多 → 持续写入下在途请求（解析在途 + 占着在途额度）
增多 → 工作集上抬贴到 L3 线。**未进一步验证**（要验证需把单进程路径块调回 5000、
或去掉信号量各重跑一次 S3 对照，本次未做）。

## §6 总结：验收结论（256 MB、--memory=256m --memory-swap=256m）

| # | 验收标准 | 结论 | 关键数据 |
|---|---|---|---|
| 1 | S1 ≥9 万/秒、2×单进程、全程 0 级 | **不满足** | 池 2w 最高档接受率 95%（4 万）且进 3 级；任何配置都到不了 9 万全程 0 级 |
| 2 | S4 全程 0 级、ws≤200 MB、100% | **不满足** | 30k/s 全随机 9/10 分钟卡 4 级、接受 10.7%、平台 ~213 MiB |
| 3 | S3 精度不差于已提交版本 | **部分**（见下） | 池关（=已提交路径）召回/落界/去重/p95 达参照，计数误差因本机进 L3 偏高；池开精度作废 |
| 4 | 单核自动退回单进程、与已提交一致 | **满足** | 1 核解析进程数 0、4/6 万 100% L0 |
| 5 | pytest + docker build --target test | **满足** | pytest -q 369 passed、slow 9 passed、docker build --target test 通过 |

**根本原因（P1c 目标的核心发现）**：256 MB 下，**主进程的统计状态常驻内存 ~200 MiB
本身就贴在 L3 线（199.7 MiB）附近**。进程池把"解析"CPU 搬进 worker（主进程 CPU% 从
65% 降到 30% @6万），所以**在 8 万档池 1w 确实比单进程好（98.8% vs 75.3%）**；但池
**省不掉主进程的统计状态内存**，每个 worker 还额外顶 19~35 MiB。于是：
- 1 worker：6 万 100% L0、8 万 98.8% L3——比单进程略好，但仍到不了 9 万全程 0 级；
- 2 worker：额外 ~50 MiB 把工作集推过 L4 线（239~245 MiB），接受率反而最低；
- 单进程（已提交）：8 万也进 L3 + CPU 87%——**256 MB 下单进程本身也内存受限**。

**结论**：P1c"256 MB 内稳定、吞吐约 2×单进程"这个组合目标**在 256 MB 上限下不可达**——
不是四项调整没做好（它们确实生效：空闲省 ~20 MiB、进级 trim 生效、单核正确退回），而是
**"2× 吞吐"需要的解析 CPU 余量与"256 MB 稳定"需要的内存余量互相冲突**：池的 2× 收益
只有在内存有余量（P1b §5 的 512 MB）时才兑现，256 MB 下被统计状态常驻内存顶掉。
四项调整 + 1 worker 是 256 MB 下池配置里**最好**的（6 万 100% L0、8 万 98.8%），可作为
"256 MB 下尽量用池"的折中，但达不到验收标准的 9 万/2×/全程 0 级。

## P1 总结（2026-10-19，支线 lane-c 结束）

### 目标

用户决定：不再追求每秒 20 万条，把 P1 收尾成"在 256 MB 内稳定运行、吞吐约为单进程
两倍"的版本，验证后合并进 main。

### 做了什么

- **P1（实现）**：解析进程池（`parse_pool.py`，spawn 上下文，validate+归一化+哈希进

- **P1b（512 MB 分离实验）**：严格串行 driver（`s1_measure.py`）、池关三档校验、

### 最终结论与原因

用户口径（如实报告）：**512 MB 下吞吐约 2 倍（12 万/秒 vs 单进程 256 MB 的 6 万/秒，
注意容器内存口径不同）；256 MB 下受内存限制无法兑现；根因是 Python 的逐条处理开销
与进程、对象的内存开销。**

- **CPU 侧（逐条处理开销）**：单写者事件循环每条 5.7~8.6 μs（512 MB 容器口径），
  单核理论上限 1/8.6μs≈11.6 万 ~ 1/5.74μs≈17.4 万/秒，实测卡住档主进程 CPU ~90% 即停。
- **内存侧（进程与对象开销）**：统计状态（环+树+去重，全是 Python 对象）满载常驻
  ~200 MiB，本身就贴在 256 MB 的 L3 线（199.7 MiB）上；每个解析 worker 再顶
  19~54 MiB。256 MB 下**单进程本身也内存受限**（8 万档碰 L3 + CPU 87%），池的
  2× CPU 收益被内存余量顶掉。
- 验收标准 1（256 MB S1 ≥9 万、2×、全程 0 级）与 2（S4）不满足，**接受该结论、
  不调整验收标准**；标准 4（单核自动退回单进程）满足；标准 5（pytest + docker
  build）满足。**lane-c 不合并进 main，main 保持已提交版本不动**（用户决定）。
- 另见 §6.13 补记：P1c 的"池关"配置比已提交版本差（30k/s 进 L3、计数误差
  0.35~0.48% vs 全程 0 级、<0.1%），怀疑来自单进程路径块 5000→2000 与写入信号量，
  未进一步验证。

### 如果继续，应走的方向

**热路径用原生代码实现**（C/Rust/Cython 等）：把单写者事件循环里的写入核心
（classify、Bloom 去重、DimBucket.observe、tick 的逐条/向量化段，约 3.5~10 μs/条）
与统计状态的数据结构搬到原生代码。这一刀同时解决两侧根因——每条 CPU 降到亚微秒级
（单核上限翻倍以上），且紧凑数组代替 Python 对象能把 ~200 MiB 统计状态内存降一个
量级，256 MB 的 CPU 与内存两个上限同时上移。进程池方案（本支线）是 Python 内部能
拿到的最好折中，天花板就在这里。

### 7.3 判读（关键）

1. **"核数多→内存高"不成立，是单次运行方差主导。** 4 核三次跑出 188(L0)、227(L3)、
   229(L3)；16 核两次跑出 196(L0)、229(L3)。同一核数既可能全程 0 级、也可能进 3 级，
   首跑"4 核最差、16 核最好"是**运气**，复测即反转（16 核复跑反而 229/L3）。S3 的满载
   平台在 ~180~229 MiB 之间，正好骑在 L3 线（256×0.78≈199.7 MiB）上，单次是否越过是
   边际抖动，不是核数的单调函数。
2. **线程数不是内存主因（Config D 直接排除）。** 强制 `Threads=1`（与 1 核参照完全
   相同）的 D 组**照样进 L3（217 MiB）**——OpenBLAS 按核建的那 15 个线程不是把内存
   顶上去的原因（本服务只用向量运算，那些线程基本空转、缓冲本就小）。可见核数通过
   OpenBLAS 影响的是 `Threads`，不是工作集。
3. **进第 3 级不拒写、不掉接受率。** 所有多核配置（含"最差"的 4 核 227/229、D 217）
   30k/s 全程 **100% 接受、0 个 503**；只有第 4 级才拒写，而 30k/s 下**没有任何多核
   配置摸到第 4 级**。反而 1 核参照的 S4 因"单核争抢把平台顶到 243 MiB"才进 4 级、
   掉了 13.7%。**多核在可用性上不比 1 核差，只可能比 1 核更好**（1 核是 CPU 争抢的
   下界）。
4. **降级只伤精度、不伤可用性，且精度代价正比于 L3 时长。** L3 期间按 1/2 采样 →
   计数误差从 L0 的 ~0.05% 升到 ~0.3~0.4%（与 §6.10 池关的 0.35%/0.48% 同源同量级）；
   召回恒 1.000、落界恒 100%、去重/p95 不受影响。所以"进 3 级"的代价是**采样精度**，
   不是丢数据、不是拒写。
5. **对 §6.13 的回溯影响（重要）**：§6.13 记"lane-c 池关（4 核）3 万/秒进 L3、误差
   0.35~0.48%，劣于已提交版本（1 核）0 级、<0.1%，怀疑是块 5000→2000 + 信号量"。
   本对照证明**已提交版本本身在 4 核下也会进 L3（227/229 MiB、误差 0.30/0.43%）**——
   那 ~49 MiB 的差距**很可能主要是"是否恰好越过 L3 线"的单次方差，而非块大小改动的
   系统性效应**。§6.13 的"怀疑块 2000 + 信号量"因此**存疑**，需按 §6.13 原计划把块调回
   5000 各重跑 S3 才能定论（本次未做）。

### 7.4 结论（回答本节的动机问题）

- **评测方不限 CPU（不加 cpuset）不会让已提交版本不可用**：30k/s 下 100% 接受、不碰
  第 4 级拒写线，工作集 ~180~229 MiB（多数时间压在 L3 线附近、偶发进 L3）。
- **风险被排除在"核数→内存"这条路径上**：多核不单调抬内存，线程数不是内存主因（D 组
  排除）；进 L3 是平台贴线的单次方差，代价是采样精度（~0.3~0.4% 计数误差）而非可用性。
- **已提交版本真正的降级风险在"CPU 争抢"而非"核数"**：1 核争抢把 S4 平台顶到 243 MiB、
  进 4 级拒写（86.3%）——比任何多核配置都差。即**限核比不限核更容易降级**。
- 因此 §7 不改变"lane-c 不合并、main 保持已提交版本"的决定；但也**不必**为"评测方
  不限核"担心——不限核（B/D）与限 4 核（A）在 30k/s 下都 100% 接受、不拒写。
