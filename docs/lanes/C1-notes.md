## 已定的决策

1. **满载模拟走完整真实写入路径**（C1）：`flowgen.EventGen` 生成 → orjson 序列化 →
   `IngestService.ingest`（解码/预留/解析/校验/URL 归一化/`engine.ingest`），
   每模拟秒一次 `engine.tick()`。请求按 5000 条切分（单个请求解压后必须 < 4 MB，
   与 `IngestService` 分块、loadgen 一致）。这样"写入路径"的字符串、归一化缓存、
   解析临时对象都是真实的，账本不用为模拟另造一套事件流。
2. **记账方法：按对象 id 去重的深度遍历 + 组件有向遍历**（C1）：
   - 对每个组件（Bloom、环的 CMS/名单/HLL/DDSketch、树的累加器/候选堆/冻结概要/
     HLL/DDSketch、快照、查询缓存、归一化缓存）分别做有向遍历，**共享同一个 seen
     集合，先到达者记账**——跨组件共享的对象（快照引用秒桶的 Part 等）只计一次。
   - numpy 数组按 `nbytes` 计、不展开；标量/类型/函数/方法/模块不展开。
   - **绑定方法必须跳过不展开**（`types.MethodType`）：`ring.finalize` 是
     `engine._on_finalize` 的绑定方法，展开它的 `__self__` 会"向上"走到 engine，
     把还没轮到遍历的组件提前错误归账（初版 bug：`活跃环·其他结构` 虚高 8 MB）。
   - key 字符串单列一行：名单里的字符串位置（秒桶堆、候选堆、叶子/节点 keys、
     快照）预先收集 id 集合，遍历时无论可达自哪个组件都计入该行，避免"字符串
     藏在 dict/list 里被算进组件结构"。
   - 交叉核对用 **RSS 增量**（满载后 RSS − 空载 import 基线），不是绝对 RSS——
     基线就是"Python 运行时与依赖库"（本机 conda 3.11 实测约 38 MB）。
3. **tracemalloc 只在模拟最后 30 秒开启**（C1）：全程开启开销约 3 倍，且我们只
   关心稳态数值；30 秒窗口足够稳态（保留期 600 秒里数据构成已稳定）。
4. **模拟工具自身开销单独统计、不计入服务端**（C1）：`EventGen._sent` 等生成器
   状态（满载下约 30 MB）用同一个 walker 单独走一遍报告，避免污染"服务端内存"
   的口径。
5. **驻留节省是静态测算**（C1，不重跑）：C1.md 允许"假设性改动后重新统计"，
   但更直接的做法是由 key 字符串盘点（值 → 对象集合）直接算出：当前字节
   （逐对象 sizeof 求和）、驻留后字节（每值一个规范对象）、驻留表开销
   （条目数 × 56 B 估算）、净节省。写入耗时影响用微基准（每请求 5000 条做
   dict 查表替换）外推到每模拟秒。
6. **驻留表条目开销按 56 B 估算**（C1）：CPython 3.11 dict 条目 24 B、负载率
   2/3 → 均摊 36 B，加值指针 8 B 与表增长的均摊余量，取 56 B。报告里注明这是
   估算；长尾满载下驻留表条目数（url 1,847 + user 2,448 个不同值）对应的表
   开销约 0.23 MB。
7. **HLL p=12 与 Bloom 减半按实例数/公式折算**（C1）：满载后 HLL 实例数
   （线段树 = 叶子 600 + 各层节点 + 构建中，长尾/随机各统计）× 每实例节省
   （2^14−2^12 字节）；Bloom 减半用标准误判率公式 (1−e^{−kn/m})^k，k 同步减半。
8. **召回对照（cap 512 vs 256）用双引擎同序事件 + 固定区间**（C1）：同一事件
   序列分别喂两个引擎（只改 `Config.heap_cap`），对"最后 60 秒"（恰 60 个整秒，
   事件 ts 均匀落在当前秒内）用 `tools/exact.py` 的 `ExactSolution.topk` 与
   `compare` 对比 k=100 与 k=512 两档；另报"原始重叠率"（返回 key 集合 ∩ 精确
   top-k 集合 / k），因为随机流量下精确答案在海量并列里任意选取、召回口径
   （并列不算错）会失真。
9. **4 MB 峰值用 4 万条长尾事件（JSON ≈ 3.8 MB）构造**（C1）：`IngestService`
   上限是"解压后 4 MB"，2.4 万条只有 2.3 MB 不够；tracemalloc 记录
   "reset_peak 后到 ingest 返回"的峰值增量（identity 与 gzip 各一次）。
10. **满载 = 11 分钟 × 每秒 3 万条**（C1）：保留期 600 秒填满、环 66 秒满、
    Bloom 8 代各约 30 万条插入（离 per_gen 200 万容量远，不触发 saturated）；
    默认速率 30k/秒足以让每个秒桶两维名单写满（长尾下秒桶热点约 1 万个 key，
    512 容量堆满）。
11. **PYTHONHASHSEED 固定为 0**（C1）：工具启动时检查并警告；本工具只测内存
    不测数值正确性，但哈希一致性让 key 字符串分布与真实服务一致。

## 未解决的问题

1. **RSS 增量显著大于对象图**（满载实测：纯服务端 RSS 增量 96.5/96.6 MB，
   而长尾对象图 117 MB / 随机 99 MB；EventGen 驱动时 RSS 增量高达 245/226 MB，
   其中 ~150 MB 是模拟工具自身的 churn 碎片）。Python（MSVC 堆）把释放的
   大对象页留在 RSS 里（高水位/碎片），`gc.collect()` 与等待数秒都不回落；
   反过来对象图也可能高于 RSS（长尾 117 > 96.5：大量小对象共享/未完全驻留，
   且 EventGen 驱动与纯探针的 URL 分布不同）。**口径三分**（C1-report.md
   §1）：对象图 = 存活数据（逻辑账）、纯服务端稳态 RSS 增量 = 容器看到的
   服务端常驻、EventGen 驱动 RSS = 被模拟工具污染（仅用于出账本数字，不用于
   "服务端内存"结论）。这对评测的含义：容器内存读数反映 RSS 而非存活对象，
   "最坏情况推算"要按 RSS 口径。Windows 开发机与 Linux 容器的堆行为可能
   不同，最终以 T10b 容器实测为准。
2. **查询临时内存未单独统计**：tracemalloc 峰值（含一次 4 MB 请求的解析/合并
   临时对象）与稳态存活之间的差值可作参考，但"查询 p99 期间的临时峰值"需要
   T10b 的 S2 混合负载场景实测。
3. **内存读数的口径之争**：T10b 前置修正（工作集 = memory.current −
   inactive_file）与本账本的 RSS 增量口径一致，都高于"存活对象"口径。两者
   谁更接近评测的判罚口径，待 T10b 容器实测后定。

## 事故记录：首轮全部数据作废（必须引以为戒）

**现象**：首轮满载/召回/峰值数据里，长尾下 url 维名单字符串"每值仅 1 个对象、
重复 0 份"，与"每个事件都新建字符串"的写入路径模型矛盾。

**根因**：conda 环境 `flowlens_env` 的 editable install 指向**主仓库**
`D:\dhy\code\flowlens`（`pip show flowlens` → `Editable project location:
D:\dhy\code\flowlens`）。`python tools/mem_report.py` 脚本模式下 **CWD 不在
sys.path**，flowlens 解析到主仓库——而主线当时正在执行 T10b 前置修正
（`model.py` 已改成"先剥 query/fragment 再查归一化缓存"），raw URL 的
query 随机、但剥掉后键相同 → 缓存高命中 → url 字符串天然共享。首轮数据
（对象图、驻留测算、归一化缓存条目数 20,000/100,000 等）全部是**主线代码
的行为**，作废。

**修复**：`tools/mem_report.py` 启动时把**项目根显式插到 sys.path 最前**
（`sys.path.insert(0, str(_ROOT))`），保证 `import flowlens` 落在本支线
（lane-c）的代码上。验证方式：`flowlens.__file__` 与
`normalize_url` 源码应来自 `D:\dhy\code\flowlens-c`。

**教训**：
1. 子工作目录（worktree）开发时，任何"可导入的独立工具"（tools/*.py）都必须
   显式把项目根放进 sys.path 最前；不能依赖 CWD（脚本模式 CWD 不在 path）。
2. conda 环境的 editable install 永远指向当初安装的那个仓库根，**不随
   worktree 变化**——跨 worktree 共用同一环境时，import 解析到谁取决于
   sys.path 顺序。
3. 记账类工具在出数之前必须做一次"身份自检"（打印 `flowlens.__file__`），
   与"每值 1 个对象"这类与写入路径模型矛盾的数字出现时立即停手排查。
4. 注：`pytest` 不受此问题影响（rootdir/CWD 在 path 最前，277 passed 有效）。
