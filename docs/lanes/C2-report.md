# C2（T9b 支线）内存增长调查报告

**问题**：主线 T10b 在容器（`--memory=256m`）以 3 万/秒跑 S3，工作集 ~90s 进第 3 级、
~200s 进第 4 级、峰值 ~229 MiB；而支线 C1 在**进程内**模拟同样 3 万/秒、11 分钟，
纯服务端稳态 RSS 增量仅 ~97 MB。两者差 ~90 MB。本任务在容器里加探针查清这 90 MB
是碎片、并发瞬时峰值叠加、还是泄漏，并给出解决方法。

**环境**：容器 = 本工作目录 `flowlens:latest`（`--target app`，Python 3.12-slim、
`PYTHONHASHSEED=0`），`--memory=256m --memory-swap=256m --cpuset-cpus=0`（服务固定 1 核）；
压测 = WSL 宿主 `tools/loadgen.py`（`taskset -c 1-6`），长尾、3 万/秒、每批 5000、
4 进程×8 并发、5 分钟（同 T10b S3）。探针 `tools/mem_probe.py` 在容器内用
`create_app` 启动**与 `python -m flowlens` 相同配置、真实 memstat** 的服务，逐 10s
采 cgroup 工作集/anon/file、进程 RssAnon/VmRSS、`getallocatedblocks`、gc 对象数与
C1 `MemWalker` 各结构总量，并记录降级级别。

> **口径说明**：`walked`（MemWalker）= 引擎全部统计结构+缓存的**存活**字节（C1 的
> "对象图"口径）；`RssAnon` = 进程堆（anon）常驻集；`工作集` = cgroup
> `memory.current − inactive_file`（降级判定同口径）。**非存活 anon = RssAnon − walked**
> ≈ 解释器/依赖 + HTTP 连接层 + **分配器保留的已释放页**。

## 二、原因判定

**结论：不是泄漏。是"分配器保留已释放页（碎片）"与"并发瞬时峰值叠加"的组合**：
前者解释"容器里内存只涨不跌、停发不回落"，后者是"C1 进程内"与"容器真实 HTTP"
差距的最大单一成分（两者分解见第三节）。

判据逐条：

1. **排除泄漏**。`gc.get_objects()` 总对象数全程平稳（~44k–58k 震荡、无趋势）；
   `getallocatedblocks()` 在 54 万–69 万间**震荡**而非单调上升；MemWalker 统计的
   **全部**结构（Bloom、活跃环 CMS/名单/HLL/DD、线段树各层、快照、查询缓存、归一化
   缓存）`walked` **平台化**在 ~85–92 MiB，甚至随 600s 保留期滚动而略降（基线
   85.6→84.8→82.8 MiB）。没有任何 Python 对象结构持续增长。
2. **并发瞬时峰值叠加真实存在且量级大**。满载时非存活 anon（RssAnon − walked，
   含空载基线 25）：单连接（顺序流、无并发）~78 MiB，32 连接 ~111–127 MiB——
   **并发多出的 ~40–49 MiB** 就是"in-flight 请求的解析临时对象（orjson 5000 dict +
   numpy 列，每请求瞬时 ~2.5 MiB）叠加 + TCP/aiohttp 每连接栈（协议对象/收发缓冲/
   socket 缓冲）"。单连接照样 100% 收满 3 万/秒、RssAnon 仍 ~169 MiB——**顺序流
   本身就有 ~53 MiB 非存活 churn 保留**（碎片 + 单连接 HTTP 层），并发再叠 ~45。
3. **碎片（分配器保留）是"只涨不跌"的直接证据**。负载中 RssAnon 持续爬升、**停发后
   基线 0 回落 / 单连接仅 ~11 回落**，但 `malloc_trim` 一停发就回收 ~60 MiB（trim
   实验 213.9→154.2 MiB）——正是"对象释放了、glibc 把已释放页留住没还给 OS"的
   碎片特征。且 `MALLOC_ARENA_MAX=2`、`PYTHONMALLOC=malloc` 均**无改善**，说明保留
   来自 glibc 主分配器对 per-request 解析 churn 的普通页/堆顶保留，不是 arena 计数
   或 CPython 私有块分配器。

## 三、与 C1 账本的 90 MB 差距分别来自哪里

先把口径对齐——**这 90 MB 里有相当一部分是"口径混用"，不是真实内存差**。

C1 的两个数（C1-report）：**满载稳态 RSS 增量 ~97 MB**（= 满载 RSS − 空载 import
RSS，**增量**口径，Windows、无 HTTP、进程内顺序批；这 97 里**已含空引擎的 ~52 MB
固定结构**）与"稳态满载估算 ~137 MB"（= 基线运行时 40 + 增量 97）。本任务容器工作集
是**绝对值** ~229 MiB（32 连接满载峰值，含空载基线 ~83）。

**拿"绝对值 229"去减"增量 97"才得到 90 MB**。两者对齐口径后差距小得多：

```
增量口径（把空载基线都扣掉，只看"持续写入让内存涨了多少"）：
  C1（进程内顺序流）     = 97 MB
  容器 32 连接          = 229 − 83(空载) ≈ 146 MiB
  → 真实"负载增量"差距 ≈ 49 MiB
绝对口径（两边都含空载基线，才是 C2 指令里那个"229 vs 137 ≈ 90"）：
  容器 229 − C1 137 ≈ 92 MiB = 上述 49（增量差）+ 43（空载基线差，见 ⑤）
```

把 49 MiB 的**负载增量差**分解到本任务实测（非存活 anon = RssAnon − walked，
空载非存活基线 24.6 MiB）：

| 成分 | MiB | 依据（本任务实测） |
|---|---:|---|
| **① 并发瞬时峰值叠加**（32 连接 in-flight 请求的解析临时对象 + 每连接 aiohttp/TCP 栈；C1 进程内直驱 ingest、顺序流、无 HTTP，**根本测不到**） | **~45** | 32 连接非存活 churn 保留 **~103** MiB（RssAnon 210 − walked 83 − 空载基线 24.6）− 单连接 churn 保留 **~53** MiB（RssAnon 169 − walked 91 − 24.6）≈ 50，扣两档事件数略差（5.45M vs 9M）取 ~45 |
| **② glibc 保留比 MSVC 高**（同为顺序流的 churn 页，"释放后不还 OS"的碎片量差） | **~21** | 容器**单连接** churn 保留 53 − C1 的分配器保留 ~23（C1 probe6 自洽对照：RSS 增量 110.8 − 对象图 88 ≈ 23）≈ 30，再扣单连接比 C1 多 1 条 TCP+aiohttp 连接的固定部分 ~9，净 ~21 |
| ③ 存活结构差（**方向相反**：C1 19.8M 事件、11 分钟填满 600s 保留期；本支线 32 连接 80s 就 L4 拒写、只 5.45M、保留期没填满） | **−30** | C1 对象图 117 MB − 容器 walked 峰值 85.6 MiB ≈ −31（C1 这次反而更高，抵消上面两项） |
| ④ 工作集口径含少量 file 缓存（RssAnon 增量口径不含） | ~13 | 工作集 229 − RssAnon 210 ≈ 19，扣掉空载部分 ~6 ≈ 13 |
| **合计（增量口径 49 MiB）** | **~49** | 45 + 21 − 30 + 13 ≈ 49 |

**绝对口径的 92 MiB = 上述 49 + ⑤ 空载基线差 ~43**（容器空载 83 − C1 空载 import
基线 40 ≈ 43：容器解释器+aiohttp+numpy 比 C1 的 conda 3.11 import 基线高、且工作集
口径含 file 缓存）。⑤ 不是"负载导致的"，是两个进程空载时的固有差，**与 90 MB 之谜
无关**，只是被"绝对值 vs 增量"的口径混用带进来了。

**判定**：真实的负载增量差 ~49 MiB 里，**~45 是并发瞬时峰值叠加**（①，容器真实
HTTP 的固有代价，C1 进程内模拟天然测不到——这是 90 MB 之谜的**实质答案**）；~21 是
glibc 对解析 churn 的保留比 MSVC 高（②，"碎片"部分，解释"只涨不跌"）；被 ~30 的
存活结构差（③，本支线因 L4 拒写没填满保留期）抵消。**"泄漏"贡献为 0**（第二节已
排除）。剩下 ~43 的绝对值差距（⑤）是口径混用，非负载内存差。

## 四、推荐的解决方法、效果与代价

| 方案 | 效果（32 连接、3 万/秒满载） | 代价 | 结论 |
|---|---|---|---|
| **定期 `malloc_trim(0)`**（Ticker 每 10–30s，或负载回落时） | 停发后回收 ~60 MiB（213.9→154.2）、防内存棘轮式累积；满载中每次回收 20–42 MiB 但**压不住满载峰值**（追不上 churn） | 0.4–6.8 ms/次（满载下），一次 Ticker 拍内完成，可忽略 | **做**。改动最小（T9b 主线在 Ticker 加一行 ctypes 调用，无新依赖），把"负载后的常驻高水位"降下来 |
| **降低单请求解析峰值**（单批 5000→1000，或流式解析不一次性展开全部 dict） | 每请求解析峰值 ~2.5→~0.5 MiB，**解析高水位 ~58→~12 MiB**（线性外推）；但**每连接 aiohttp/TCP 栈 ~1.4 MiB × 32 ≈ 45 MiB 治不了**（取决于客户端连接数，服务端只能建议客户端降并发） | 请求数增 5×（5000→1000 条/批，仍 < 4 MB 上限），HTTP 往返略增；流式解析改动 ingest.py（冻结模块外的上层） | **治本，推荐**（T9b/T11）。C2 只测不改，此处为建议 |
| `MALLOC_ARENA_MAX=2` | 无改善（RssAnon 平台 ~184 MiB，与基线同量级） | — | **不做**（实测否决） |
| `PYTHONMALLOC=malloc` | 无改善（平台 ~184 MiB；峰值在 glibc 侧 dict/numpy，非 CPython 块） | 启动参数 | **不做**（实测否决） |
| `M_MMAP_THRESHOLD`/`MALLOC_TRIM_THRESHOLD_` 调低 | 让大临时对象走 mmap、free 即还 OS（与 trim 互补） | 需 Dockerfile 加 env；mmap 碎片另有开销 | **可选**，作为解析峰值方案的补充 |

**组合建议（T9b 实施）**：① Ticker 定期 `malloc_trim`（防棘轮、降负载后常驻）
**+** ② 单批降为 1000 条或流式解析（压解析高水位）。两者叠加预期：RssAnon ≈
walked ~92（9M 事件、保留期填满，实测）+ 基线 25 + 连接栈 45 + 解析高水位 12 ≈
**174 MiB**，工作集 ≈ **179 MiB（~70%）**——比现状 ~229 MiB（~89%）低 ~50 MiB。

## 五、推荐方法下，3 万/秒持续 5 分钟是否保持第 0 级

**仅定期 `malloc_trim`：否**（实测 trim 实验 101s 仍进 3 级、292s 进 4 级——满载中
trim 追不上 churn，压不住峰值）。

**定期 `malloc_trim` + 单批 5000→1000（或流式解析）：稳态保持第 0 级（~70%），
瞬时尖峰可能偶发触及第 3 级，不触及第 4 级。** 依据：单批降到 1000 后每请求解析
峰值 ~5× 下降，解析高水位从 ~58 MiB 降到 ~12 MiB，但**每连接 aiohttp/TCP 栈 ~45 MiB
治不了**（取决于客户端并发连接数）。预期满载**稳态** RssAnon ≈ walked 92 + 基线 25 +
连接栈 45 + 解析高水位 12 ≈ **174 MiB**、工作集 ≈ **179 MiB ≈ 70%**——低于 78% 第
3 级阈值（199.7 MiB）、更低于 90% 第 4 级（230.4 MiB）。但 32 连接同时有请求在
解析时的**瞬时尖峰**（现状峰值 232 vs 平台 210，~20 MiB；降到 1000 条后 ~4–8 MiB）
叠加上去，工作集瞬时 ~185–190 MiB ≈ 72–74%，**接近但不稳定越过 78%**——即稳态 0
级、偶发瞬间可能触到 3 级（随后回落），不会持续降级、更不触及 4 级。**要稳定保持
第 0 级（连偶发尖峰也不触 3 级），还需客户端降低并发连接数**（比如 4 进程×2 连接 =
8 连接，连接栈从 45 降到 ~11 MiB，工作集 ~145 MiB ≈ 57%、尖峰 ~60%，全程 0 级）
或**调低 M_MMAP_THRESHOLD 让解析临时列走 mmap**。此为**由单连接/32 连接实测数据的
线性外推**，C2 未直接跑"1000 条/批 + trim + 低并发"组合，**T9b 实施后需复测确认**。

**注意（诚实 caveat）**：本支线压测机（WSL2、服务固定 1 核、压测抢其他核）比 T10b
当时更紧张，32 连接下 80s 就进 4 级拒写（接受率 60.6%），接收事件数（5.45M）少于
单连接（9M）。这**不影响"碎片/并发判定"**（非存活 anon 平台高度、单连接对照、gc/walk
平稳都一致），但 4w×8c 与 T10b S3 的**进级时间线不完全同**（本支线 80s vs T10b 200s
进 4 级）——差异来自压测机争抢，非服务行为变化。碎片/并发的**定性结论与占比**不受
此影响。
