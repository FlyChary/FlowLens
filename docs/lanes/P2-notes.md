## 一、主进程剖析（py-spy，A/B 两组）

方法：容器加 `--cap-add SYS_PTRACE`；`docker inspect -f {{.State.Pid}}` 取主进程宿主
PID；`sudo py-spy record -t --pid <PID> --duration 30 --rate 200 --format raw`
（不加 --subprocesses；不用 --nonblocking——冒烟实测该模式采样丢失 ~85%）。
负载在预热 30 秒稳定后开始采样 30 秒；接受条数与主进程 CPU 秒都取同一 30 秒窗口
（/healthz 差值 + 宿主 /proc 差值）。类别占比 = 该类别采样数 ÷ 全部采样；
每条 μs = 类别占比 × 主进程每条 μs。

### 1.3 "主进程那约 6 μs 是什么"的结论

P1 的悬念：主进程每条 8.5 μs（16 万饱和档），其中写入引擎 ~2.5 μs，**其余
~6 μs 来源不明**。py-spy（12 万档，主进程 7.5 μs 口径）把它拆开了：

1. **进程池通信 ~1.8 μs（23.5%）**——这是池架构自身的成本，P1 的口径里没算它
   （"等解析结果"当时归在不明项）。主进程 23.5% 的 CPU 花在 multiprocessing
   队列的 feeder 线程（回传 ParsedBatch）、池管理线程（等 worker 结果）、以及
   主线程 `await wrap_future` 上。三线程共抢 GIL：MainThread 只占 77%，**池的
   两个线程吃掉了主进程 23% 的 GIL 时间**。
2. **tick ~1.2 μs（15.7%）**——每秒定稿（segtree.add_leaf → CMS/HLL 摘要）+
   60 秒窗口快照（collect_parts → bounds.top_k）。A 组（15.7%）比 B 组（7.7%）
   高一倍：12 万/秒下定稿的秒桶更大、快照覆盖的数据更多。tick 随吞吐涨。
3. **写入引擎 ~3.5 μs（46.4%）**——Bloom 去重 1.67（check_and_set 的
   double_hash/derive/mix64 占大头）+ 维度 observe 1.09 + intern/秒分组/入口
   0.72。比 P1 的 2.5 μs 高：bench 口径只量 `_ingest_core` 主体，没算
   intern、ring.slot、入口组装与 Bloom 的哈希派生。
4. **HTTP ~0.65 μs + 事件循环 ~0.44 μs（14.4%）**——aiohttp 协议/读体/响应与
   asyncio 调度，不大。

合计：1.76（池）+ 1.18（tick）+ 3.48（写入）+ 1.09（HTTP+循环）≈ 7.5 μs，与
12 万档的 7.52 μs 闭合。换算到 16 万饱和档的 8.5 μs：多出的 ~1 μs 是排队/
让出（P1b §5.1：12 万起升 7.5→8.6，事件循环内排队 + tick 重叠）。

**结论：那 ~6 μs（8.5−2.5）= 池通信 ~1.8 + tick ~1.2 + 写入细项（intern/秒分组/
入口/Bloom 哈希派生，P1 的 2.5 没细拆的部分）~1.5 + HTTP/事件循环 ~1.1，
另加饱和档排队 ~1.0。其中池通信是池架构的固定税（与吞吐几乎无关，~1.8 μs/条
+ 23% 的 GIL 争抢），tick 随吞吐线性涨；写入引擎主体（~2.5-3.5 μs）是两条
路线都要动的那块（见 §四 的路线估计）。**

## 二、压测工具快速模式（tools/loadgen.py --fast）

### 2.1 实现

- 每 worker 启动时预生成 `--fast-templates`（默认 32）个完整请求体模板（--mode 分布，
  默认长尾），模板与现有模式同构（同一套 key 规则/query/fragment）。
- 两个等宽占位：ts → 13 位 `9999999999999`；event_id 序号 → 12 位 `888888888888`
  + w 位批内下标（w = len(str(batch-1))）。占位串互不为子串，替换不会互相破坏；
  模板生成时按 count 校验占位只出现在预期位置（撞上自然内容则断言失败重生成）。
- 每次发送前 `bytes.replace` 两个占位：当前毫秒（批内同 ts）与该 worker 递增的
  批基准序号（worker 起点 = wid × SEQ_STRIDE + 1，批间 +10^w）→ event_id 全局不重复、
  ts 在迟到窗口内（= 发送时刻，0 回退）。
- 不支持 --archive 与精确解对比（main 里互斥拒绝）；--mode 随机不支持（模板复用
  固定 key 集，无吞吐测试意义）。帮助文本已写明。

### 2.2 验证与开销

**正确性（P2a 二.5）**：快速模式 10 万/秒 × 25 秒打到 lane-c 服务（池 3、
16 MB 额度、512 MB），服务端 **acc=256 万、deduped=0、late=0、invalid=0**
（占位替换没有产生重复 id、越窗 ts 或坏字段），全部 202、0 错误 0 重试。
本地断言另验证：批内/跨批/跨 worker 的 event_id 互不碰撞、ts 全为发送时刻、
替换前后字节长度不变、url/user 字段完好。

**压测端每条事件的 CPU 时间（发送窗口口径，排除模板预生成启动开销；
summary 新增 client_cpu_us_per_ev 字段）**：

| 压测端 | 目标速率 | 实际发出 | 每条 CPU | 8 核 CPU 占用 |
|---|---|---|---|---|
| 原模式（生成+序列化） | 12 万 | 11.0 万/s（100% 接受） | **55.0 μs** | 606%（7.6 核） |
| 快速模式 | 12 万 | 10.9 万/s（100% 接受） | **0.77 μs** | 4% |
| 快速模式 | 24 万 | 12.0 万/s（100% 接受） | **0.75 μs** | 7% |

（"实际发出"按发送窗口 15 s 算；wall 含 ~11 s 模板生成与收尾，summary 的
accepted_events_rate 按 wall 算会偏低，判读用 sent ÷ 窗口。）

**本机 8 核（核 8-15）上快速模式的最大发送能力**（打 echo server，隔离出纯发送
能力，8 个压测 worker）：

| 目标速率 | 实际发出 | 接受率 | 每条 CPU | 8 核 CPU 占用 |
|---|---|---|---|---|
| 30 万 | 30.0 万/s | 100% | 0.70 μs | 7% |
| 40 万 | 40.0 万/s | 100% | 0.52 μs | 10% |
| 50 万 | 50.0 万/s | 100% | 0.73 μs | 14% |

原模式在 12 万/秒就吃满 7.6 个核（55 μs/条 × 12 万 ≈ 6.6 核 + 事件循环/网络），
这是 P1 记录的"13.4 万需 5.5 核、20 万需 8 核以上"的根因；快速模式把每条压测
CPU 从 55 μs 砍到 ~0.7 μs（**~73 倍**），同样 8 核在 **50 万/秒时只占 ~1.1 核**，
离天花板还差一个量级——**20 万/秒目标在压测端已无瓶颈**（瓶颈完全回到服务端
主进程）。

**实现中踩到的坑**（都已修，记在此供实现 20 万冲刺时参考）：
1. 模板生成初版用逐条 `bytes.replace(...,1)` 在 800 KB 串上找 `"e<seq>"`——
   O(n²)，32×10000 条要 ~13 分钟，8 个 worker 启动全卡死、压测 0 发送。
   改为**直接在 dict 里写占位符再一次 orjson.dumps**（O(n)），32×10000 条
   11.4 s（worker 启动一次，可接受）。
2. `deadline` 原来在 worker 开头算，模板生成（~11 s）吃掉发送窗口，短
   --duration 下一条都发不出。改为模板生成后起算。
3. 占位串必须**互不为子串**（`9999999999999` 与 `888888888888`），否则先后
   replace 互相破坏；模板生成时 count 校验占位只出现在预期位置。

## 三、msgspec 与正则归一化基准（tools/bench_parse.py）

每批 5000 条、每方案 300 轮（150 万条），flowgen 生成请求体；归一化缓存在两方案
间共享（长尾下缓存热，与真实服务一致）。计时取 5 组中位数。WSL 宿主 Python 3.14、
taskset 固定 4 个空闲核（与服务/压测核不重叠）。

| 方案 | 长尾 μs/条 | 随机 μs/条 | 长尾内存峰值 | 随机内存峰值 |
|---|---|---|---|---|
| 现有 orjson+validate | 3.57 | 3.56 | 11.14 MiB | 11.38 MiB |
| msgspec Struct(gc=False)+剩余检查 | 2.89 | 3.15 | **1.96 MiB** | **1.98 MiB** |
| 收益 | **1.23×** | 1.13× | **省 9.18 MiB** | 省 9.40 MiB |

- **CPU**：长尾 1.23×（3.57→2.89 μs/条，−0.68 μs），全随机 1.13×。收益主要在
  orjson 的 dict 构造被 Struct 取代（每事件 5 字段 × dict 开销）；msgspec 的
  类型强校验还顺带把"列式类型检查"省了。
- **内存**：解析一批 5000 条的 tracemalloc 峰值 11.1→1.96 MiB（**−8.2 MiB/批**）。
  这是常驻收益：单进程路径下"解析完持有到写完"期间，dict 列表 + 五列的 Python
  对象比 Struct 数组（紧凑、gc=False 不进 GC）少占一个量级。12 万/秒、在途
  ~4 个请求 × 8 批时，稳态可省 ~250 MiB？——不，是**每批**省 8.2 MiB、在途批数
  ~2-4 → 省 ~20 MiB 峰值，且这些批的生命周期变短（解析快 23%）。
- **容错差异（实现时需注意）**：msgspec 对"某条字段类型错"是整批解码失败
  （orjson+validate 是逐条计 invalid）。压测/正常流量下无差异；要保留逐条容错
  需 try 整批失败后退回 orjson 逐条（慢路径），实现时的取舍。

### ID 段替换：预编译正则一次 sub（隔离这一步测）

| 流量 | 现有逐段 fullmatch | 正则一次 sub | 加速 |
|---|---|---|---|
| 长尾 | 1.84 μs/条 | 0.79 μs/条 | **2.33×** |
| 全随机 | 1.68 μs/条 | 0.73 μs/条 | **2.29×** |

（对比的是 `_normalize_url_impl` 里"split + 逐段判 ID"这一段，输入是已剥
query/fragment 的路径——现有整管线里这段占缓存未命中路径的大头，长尾下缓存命中
的 URL 根本不进来，所以按"缓存未命中条数"折算更准：长尾约一半 URL 每次未命中，
等效整条 URL 归一化省 ~0.5 μs。）

### 等价性检查（正则 sub 完整管线 vs tests/test_model.py 改前参考实现）

- 检查 20054 条（tests 的 54 个边界 + 2 万条模糊：数字段/十六进制/UUID/全角/
  中文/截断边界/多斜杠/scheme/query/fragment），**不一致 0 条**。
- 过程中发现并修正了 C 方案自己的两个实现错误（只报告、未动服务）：
  ① 整段边界若写成 `(?<=.)/…` 会漏掉紧跟根斜杠后的第一段（`/123` 参考判 `{id}`、
  正则不判）——正确边界是"段前恰好一个 `/`"，根段（空串）前没有 `/` 天然跳过；
  ② 截断必须按**字节**（`len(b) > 128`），按字符会截短中文路径（100 个"中"
  300 字节，参考截到 42 字符、按字符截到 128 字符=384 字节不截）。

## 四、汇报

### 4.1 两组配置的主进程 CPU 分类表（含每条 μs）

见 §1.1（A：池 3、16 MB、512 MB、12 万/秒，主进程 7.5 μs 口径）与 §1.2
（B：已提交版本、单进程、256 MB、5 万/秒，主进程 10.5 μs 口径）。
**"主进程那约 6 μs 是什么"**：§1.3 的结论——池通信 ~1.8 + tick ~1.2 +
写入细项（P1 的 2.5 没拆的 intern/秒分组/入口/Bloom 哈希派生）~1.5 +
HTTP/事件循环 ~1.1 + 饱和档排队 ~1.0。**其中池通信 ~1.8 μs/条是池架构的
固定税**（23.5% CPU、23% GIL 争抢），tick ~1.2 随吞吐涨，写入引擎主体
~2.5-3.5 μs 是两条路线共用的那块。

### 4.2 线程与 GIL 争抢、访问日志

- **A（池 3）**：主进程 3 线程——MainThread 77.0%、QueueFeederThread
  13.5%（multiprocessing 结果回传）、Thread-1 9.4%（池管理等 worker）。
  **两个池线程吃掉主进程 23% 的 GIL 时间**，这就是"池通信 23.5%"的构成：
  主线程 `await wrap_future` 本身几乎不耗 CPU（阻塞不采样），耗的是池线程
  序列化/回传 ParsedBatch 时的 GIL。争抢程度：中——MainThread 仍有 77%，
  但池线程的 CPU 是**纯额外成本**（单进程路径 B 完全没有，B 主进程 100%
  是 MainThread）。
- **B（单进程）**：主进程 1 个活跃 Python 线程（100% MainThread；另有
  GC/信号线程空闲不占 CPU），无 GIL 争抢。
- **aiohttp 访问日志：未开启**（`__main__.py` 的 `web.AppRunner(app)`
  没传 access_log，aiohttp 默认关闭）——剖析里 http 类不含日志开销。

### 4.3 压测工具改造前后的开销与快速模式最大发送能力

- 每条压测 CPU：**原模式 55.0 μs/条 → 快速模式 0.75-0.77 μs/条（~73 倍）**
  （12 万/秒同速率、发送窗口口径、8 压测 worker）。
- 快速模式在本机 8 核（核 8-15）上 **30/40/50 万每秒全部 100% 达成、0 错误**，
  CPU 只占 7-14%（~0.6-1.1 核），离天花板还差一个量级。
- 正确性：打真实服务 10 万/秒 × 25 s，deduped=late=invalid=0（§2.2）。
- 原模式的 55 μs/条就是 P1"压测端 13.4 万/秒用 5.5 核"的根因（55 μs ×
  12 万 ≈ 6.6 核）；现在 20 万/秒的压测端开销 ≈ 0.15 核，**压测端不再是
  20 万/秒的约束**。

### 4.4 msgspec 与正则归一化的实测收益

- **msgspec**（§三）：长尾 3.57→2.89 μs/条（**1.23×**）、全随机 1.13×；
  解析一批 5000 条的内存峰值 **11.1→1.96 MiB（−8.2 MiB/批）**。注意 msgspec
  是整批类型强校验（某条类型错整批失败），要保留"逐条计 invalid"的容错需
  退回 orjson 慢路径。
- **正则 ID 段替换**：1.84→0.79 μs/条（**2.33×**，长尾；全随机 2.29×）。
  与改前参考实现等价性检查 20054 条 **0 不一致**（过程中修了 C 方案自己的
  两处实现错误：整段边界漏根后第一段、截断按字符而非字节——只报告未动服务）。

### 4.5 两条路线各自能达到的估计

**路线一：512 MB + 进程池**（现状：可持续 12 万、饱和 13.4 万，瓶颈主进程
单核 7.5-8.5 μs/条）
- 主进程构成：池通信 1.76 + tick 1.18 + 写入 3.48 + HTTP/循环 1.09（§1.1）。
- 纯 Python 内可拿的：① 池通信——worker 3→2（P1c 实测解析池余量 2.4 倍，
  第 3 个无吞吐收益）+ 减小回传体积（ParsedBatch 的字符串列改传编号/只传
  url 不传 user 等）可省 ~0.8-1.5 μs 与大部分 GIL 争抢；② tick 1.18——定稿
  摘要与快照的向量化/缓存，乐观省 ~0.5；③ msgspec/正则**不帮主进程**
  （解析本就在 worker，只让 worker 更快、worker 已 2.4 倍余量）。
- 估计：①+② 做到极限主进程 ~5.5-6 μs/条 → **单核上限 ~16-18 万/秒**；
  20 万需要主进程 ≤5 μs，即写入引擎 3.48 也要砍掉 ~1（Bloom/observe 的
  向量化极限），**纯 Python 够不到 20 万，现实上限 ~16-18 万**。

**路线二：256 MB + 单进程，每条 ~4 μs**（现状：最大可持续 ~6 万，P1c；
主进程 10.5 μs = 解析 4.86 + 写入 3.77 + tick 0.81 + HTTP/循环 1.06）
- msgspec 省 ~0.8（4.86→4.06）+ 正则归一化省 ~0.5（归一化是解析段里
  缓存未命中路径的大头）→ **~9.2 μs/条，CPU 上限 ~11 万/秒**。
- 但 256 MB 下还有**内存墙**：统计状态常驻 ~200 MiB 贴在 L3 线（P1c §6），
  3 万/秒持续 5 分钟就进 L3；6 万/秒起工作集 ~194-205 MiB。20 万/秒的
  在途/解压缓冲会再顶几十 MiB → **256 MB 下内存先于 CPU 到顶，现实上限
  ~7-9 万**。要 4 μs/条（=20 万）需要：msgspec + 正则（−1.3）+ 写入核心
  原生/更激进向量化（3.77→~1.5）+ tick 摊薄（0.81→~0.3）+ HTTP 精简
  （1.06→~0.5），且**内存必须省一个量级**（原生紧凑结构替代 Python 对象）——
  与 P1 总结"热路径用原生代码实现"的方向一致。
- **结论：20 万/秒在两条路线下都不是"再优化几处 Python"能到的：路线一
  纯 Python 上限 ~16-18 万（512 MB），路线二现实上限 ~7-9 万（256 MB 内存
  墙）。20 万的下一步杠杆是写入核心（~2.5-3.5 μs/条，两条路线共用）与
  统计状态内存的原生化。**
