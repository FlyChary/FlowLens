# FlowLens 设计文档

## 1. 概述

FlowLens 挂在 API 网关旁边，在 256 MB 内存里实时回答：最近一段时间哪些 URL、哪些用户最热，有多少个不同的用户，响应大小的 p95 是多少。

事件太多存不下，我们只存摘要：Count-Min Sketch 估次数，小顶堆记热点名单，HyperLogLog 估去重人数，DDSketch 估分位数。这几种摘要两份可以直接合成一份，所以把时间切成 1 秒一格，每格一份摘要，查某段时间就把对应的格子合起来。滑动窗口、`at` 回放都建立在这一点上。服务用 Python 实现，单进程运行，性能靠按批处理和 numpy 向量化获得。

<p align="center"><img src="./flowlens-architecture-v3.png" alt="FlowLens 全组件架构图" width="100%"><br><em>图 1　全组件架构</em></p>

左边是写入：解码、校验、预留容量、迟到检查、去重，再按秒聚合写入。中间是统计引擎：最近 66 秒放在环里，更早的冻结后放进稀疏线段树，保留 10 分钟。右边是读取：默认查询读每秒生成的快照，带 `at` 的查询由回放引擎现场合并。

## 2. 题目留白处的约定

| 问题 | 约定 | 原因 |
|---|---|---|
| 按什么时间统计 | 事件自带的 `ts` | 同一段时间无论何时查结果都一样，回放才有意义 |
| 查询区间 | `[at − window, at)`，精确到毫秒；默认 `at` 为当前时间取整到秒 | 相邻窗口不重不漏；当前这一秒还没结束 |
| 迟到与未来 | `ts` 早于 now − 60 s 丢弃（`late`），晚于 now + 5 s 视为非法（`invalid`）；`at` 在最近 60 秒内时结果标 `final: false` | 题目允许迟到不超过一个窗口；分界线用服务器时钟算，免得一条错乱的 `ts` 把它推歪；5 秒留给时钟偏差。见图 2 |
| 重试 | 只看 `event_id`，假设重试时 `ts` 不变 | 去重只需覆盖一小段 `ts` |
| URL 归一化 | 去掉 query 和 `#` 之后；纯数字、UUID、长十六进制路径段换成 `{id}`；最长 128 字节 | `/order/123` 和 `/order/456` 是同一个接口 |
| 并列 | 次数多的在前，相同按 key 字典序 | 结果稳定 |
| 保留期 | 10 分钟，`window` 最长 600 s | 由内存预算决定 |

## 3. 各模块怎么做

### 3.1 写入与去重

写入处理依次做：gzip 解码（压缩后超 8 MB 或解压后超 64 MB 返回 413）；解析校验、URL 归一化、批量算 64 位哈希；预留容量；迟到检查；`event_id` 去重；同一秒同一 key 先合并，再写入秒桶。做完返回 202 和 `{accepted, deduped, late, invalid}`。

预留容量必须在去重之前：在途事件超过上限（10 万条）时整个请求直接返回 503。如果先去重再拒绝，这些 `event_id` 已经写进 Bloom，调用方重试时会被当成重复事件丢掉。

精确记住所有 `event_id` 要几百 MB，所以用 Bloom filter。它不能删元素，所以按 `ts` 每 10 秒分一代，保留 8 代（图 2 最下面一行），整代过了 watermark 就清空复用。每代按峰值 200 万条、误判 0.1% 设计，位数向上取到 2 的幂，实际误判约 0.03%，8 代共约 34 MB。同一批里重复出现的 id 先在批内去重，第一次出现的才去查 Bloom。

### 3.2 单进程、单写者、按批处理

Python 有全局解释器锁，多线程用不上多核；每个 Python 进程又有几十 MB 的基础内存，256 MB 里开不了几个进程。所以服务只跑一个进程、一个事件循环（asyncio + aiohttp），全部统计状态归一个引擎对象，只在事件循环里修改。只有一个写者，就完全不需要锁。

性能靠按批处理获得：一个请求里的事件先拆成 numpy 数组，分类、去重、按秒和 key 聚合都是向量化运算；Count-Min、HLL、DDSketch 也按批更新。名单已满时，先向量化筛掉不可能入选的 key，只对剩下的少数逐个更新堆。实测统计核心单核约每秒 25 万条。耗时操作（大请求、大区间合并）分块执行，块之间让出事件循环，避免查询延迟超过 50 ms。

### 3.3 最近 66 秒：活跃环

引擎里有一个 66 格的环：60 格是窗口，1 格是当前秒，5 格留给时钟偏差带来的"未来"事件。写指针每秒前进一格，最旧的一格定稿后离开。每格存 url 和 user 各一套 Count-Min（4 × 8192，保守更新）和小顶堆（512 个位置，带索引表），另有 HLL 和 DDSketch。

每条事件先写 Count-Min 拿到估计次数。key 在堆里就加一；不在堆里但超过堆顶，就替换堆顶。已在堆里的 key 也写 Count-Min，这样被挤出后再回来，次数不会丢。

后面常用到一个性质：一秒结束时不在堆里的 key，这一秒的真实次数不超过堆顶。因为它每次出现时都没超过当时的堆顶，被挤出时次数等于当时的堆顶，而堆顶只增不减。我们把它叫缺席上界 u。

为了不漏掉"每秒都不热、一分钟加起来很热"的 key，引擎为默认窗口另外维护一个候选堆，用"上一秒的窗口汇总 + 当前秒"的估计值筛选。

### 3.4 更早的数据：稀疏线段树

`at` 精确到毫秒，`window` 可以任意填，评测会和离线精确结果对比。历史如果只按 10 秒对齐，60 秒窗口最多有六分之一落在错误区间，所以历史也要 1 秒精度。但 600 个完整秒桶要两三百 MB，我们只让环里的 66 格保持完整，更早的只留必要信息。

秒桶离开环后变成叶子，只留前 128 个 key 的次数、u、稀疏的 HLL 和 DDSketch。叶子之上是第 1 到第 9 层，第 k 层每个节点覆盖 2^k 秒。每层同一时刻只有一个节点在构建，带一个累加用的 Count-Min 和候选堆；每个秒桶定稿时，把它的 Count-Min 加进所有正在构建的祖先节点。节点完成时按估计值留下前 m 个，记下 u，扔掉 Count-Min，变成只读数组。

这样每个节点只截断一次，误差不会像普通线段树那样逐层叠加（图 3）。能做到这一点，是因为每秒的数据离开环之前 Count-Min 都还在。8 秒以上的节点才带 HLL 和 DDSketch。

<p align="center"><img src="./fig3-truncate-once.png" alt="为什么每个节点只截断一次" width="78%"><br><em>图 3　为什么每个节点只截断一次</em></p>

字符串表有硬上限（约 12 万个）。冻结时次数不超过 u 的条目直接丢掉，表满后新 key 不再入库、次数算进 u。这样无论流量长什么样内存都有上限，随机 URL 的攻击流量会让节点自然变空。

### 3.5 快照与查询

每秒做一次 tick：封存当前秒；最旧秒桶冻结成叶子，并入各层累加器，冻结完成的节点；推进去重 Bloom 的代；对最近 60 秒做一次合并，生成快照（前 100 名、去重人数、p95），整体替换旧快照。每秒重建而不做增量加减，迟到事件下一秒自然算进去。快照、回放、SSE 补帧都调用同一个组装时间片的方法，保证结果一致。

默认的 `/v1/topk` 直接读快照。带 `at` 或其他 `window` 的走回放引擎（图 4）：最近 66 秒用环里的秒桶，更早的拆成最多约 20 个线段树节点，两端不满一秒的按覆盖比例 f 折算。然后给每个候选算出次数的上下界，用第 K 大的下界当门槛，上界够不着的直接淘汰，只精算剩下的。定型区间的结果进 LRU 缓存，大区间分块合并。

<p align="center"><img src="./fig4-replay-query.png" alt="回放查询的区间拆分与剪枝" width="78%"><br><em>图 4　回放查询：区间怎么拆、候选怎么剪</em></p>

`/v1/stats` 的长窗口同样合并环、叶子和 8 秒以上节点，HLL 的边缘秒覆盖过半才计入。结果都带 `count`、`err` 和实际的 `from`、`to`。SSE 订阅者共用计算结果，重连时按 `Last-Event-ID` 补发最多 30 帧，慢客户端只留最新一帧。

### 3.6 过载与降级

调用方只等本批数据的处理（约每千条 5 毫秒）。负载上来时依次降级，每级有进入和退出两个阈值，状态见 `/healthz` 的 `degraded`：

| 级别 | 触发 | 动作 |
|---|---|---|
| 1 | 在途事件 > 60% 或 tick 延迟 > 1 s | SSE 降频，快照缓存变长，暂停回放（503） |
| 2 | 在途事件 > 80% | Top-K 和 DDSketch 按概率 p 采样、每条按 1/p 计；HLL 和去重照常 |
| 3 | 内存 > 200 MB | 缩短历史保留，收紧并发 |
| 4 | 内存 > 230 MB | 写入返回 503 + Retry-After |

第 4 级不等于丢数据：去重保证重试不会重复计数。

## 4. 复杂度与误差

写入每条 O(L + d)，L 为 key 长度、d = 4，名单更新只发生在筛选后的少数 key 上，每个 O(log m)；默认查询 O(K)；回放最多合并约 20 个节点加环内秒桶。

| 统计项 | 误差 |
|---|---|
| 环内单秒的 Top-K 次数 | Count-Min 只高估，每秒不超过 e·N/w ≈ 66，概率 ≥ 98% |
| 60 秒窗口 | 约 4000，结果里带 `err` |
| 冻结节点、边缘秒 | 不在名单的 key ≤ u；边缘秒为 `[0, 整秒次数]`，都一定成立 |
| 去重用户数 | HLL p = 14，标准误差 0.81% |
| p95 | DDSketch α = 1%，相对误差 ≤ 1%，一定成立 |
| `event_id` 去重 | 设计上限 0.1%，实际约 0.03% 的新事件被误丢 |

## 5. 内存预算

按最坏情况（所有 URL 和用户互不相同）估算：Python 运行时与依赖库约 45 MB，活跃环约 34 MB，线段树约 30 MB，字符串表上限约 13 MB，去重 Bloom 34 MB，在途写入（上限 10 万条）约 20 MB，查询临时内存与快照约 20 MB，合计约 195 MB。大块数据都放在 numpy 数组里，避免 Python 对象开销。以上为估算，以 256 MB 容器实测为准。`memory_bytes` 读 cgroup 的 `memory.current`，读不到用 RSS。

## 6. HTTP 语义

写入成功 202（含空数组、部分事件非法）；参数不合法 400（`k` 1~100，`window` 1~600 s）；`at` 早于保留期 422；方法不对 405；超大 413；编码不支持 415；过载 503 + `Retry-After`。

## 7. 测试

离线精确程序读同一份数据，和服务对比各项误差。自测脚本覆盖 14 个边界用例，如重复 `event_id`、`ts` 正好在 watermark 上、区间起止边界、损坏的 gzip、`at` 带毫秒、SSE 重连、过载进入和恢复。核心模块已有 46 个单元测试；线段树的性质测试检查随机区间拆分不重不漏、真实次数落在上下界内，并做过变异检验。另用 `docker run --memory=256m` 跑全随机流量验证内存有界，并压测吞吐和 p99。

待补实验：两种流量下的 Top-10 召回率与次数误差、随机流量下的峰值内存、吞吐瓶颈。

## 8. 主要取舍

用近似换内存，误差有上限并随结果报出。迟到上限等于窗口，去重和活跃环才能限定在 70 秒左右，这是内存可控的前提。稀疏线段树换来任意区间 1 秒精度的回放，代价是实现和测试更复杂。选 Python 换来代码好读、答辩讲得清，代价是吞吐余量变小：端到端预计接近每秒 20 万条，要以压测为准。过载时先降精度后拒绝，因为去重让重试是安全的。

## 9. 规划中：节点退出与历史落盘

主功能完成后实现。节点超出保留期后先标记为已废弃，新查询不再选它，进行中的查询读完后才释放。可选把释放的 64 秒节点写进日志（默认关闭），用于离线分析和重启恢复；开启时 `memory_bytes` 只统计匿名内存，避免页缓存被算进去。
