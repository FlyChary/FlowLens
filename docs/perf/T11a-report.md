# T11a 端到端 CPU 剖析报告（T11a-2 修正后）

> 数据：`results/T11a/run_100k.json`、`results/T11a/run_60k.json`。
> 环境：WSL 容器（python:3.12、256 MB、服务固定 0 号核，`--memory-swap=256m`），
> loadgen 压 1-6 号核（4 进程 ×8 并发），假内存读数（50 MB/256 MB，永不因内存降级）。
> 两组均为长尾、每批 5000 条、不 gzip、预热 30 s + 测量 30 s；测量窗口用**墙钟 deadline**
> 跑满 30 s（T11a-2 修正，`measure_sec` 实测 30.1 s / 30.1 s，不再是上一版的 47 s）。

本次相对上一版（T11a 的 20 万/秒）有三处测量方法修正：
1. **测量窗口改墙钟 deadline**——上一版 `sleep(0.5)×N` 在满载下被循环延迟拖成 47 s，
   窗口尾部无流量，把 `accepted_rate` 与核占比稀释了。
2. **垃圾回收单独计账**——每次回收的墙钟起止时刻记下，各阶段按"调用时段与回收区间的
   交叠"把回收耗时从阶段里扣出（`gc_us` 字段），GC 单独汇总。上一版 GC 的 CPU 混在各
   阶段里，阶段之和虚高。
3. **归一化缓存命中率**——运行时包装 `model.normalize_url`/`_normalize_url`，统计命中/未命中
   与未命中的平均耗时。

## 一、两次运行的结果

### 10 万/秒（测处理能力，核接近打满）

服务核 **97.2%**（接近饱和）。loadgen 按 10 万/秒发，服务只能接受 **72,911/秒**
（服务端每批 5000 条同步处理 61 ms，单核物理上限就在那，见第六节）。
（loadgen 汇总里的 131 万条 error 是测量结束后 10 s 余量里、客户端往正在关闭的容器
发送产生的连接重置，与服务端处理能力无关——见附节。）

- 进程 CPU 时间 29.32 s / 30.17 s
- **每条被接受事件 CPU ≈ 13.33 μs**
- 单核 CPU 上限 ≈ 1/13.33 μs ≈ **7.5 万/秒**（实测接受 72,911/秒，距上限 2.9%，说明 10 万/秒已把核喂满）

|---|---:|---:|---|

| ingest（引擎写入） | 2.93 | 22.0% | 见细分 |
| 　└ dim_write（写秒桶） | 1.31 | 9.8% | 两维 DimBucket.observe |

aiohttp 协议处理、JSON 响应序列化、定时器回调等未包装部分）。**注意 load_array 单阶段扣了

这两处正是"GC 被计入其他阶段"的修正效果，扣后才是它们自身的开销。

### 两组对比

| 指标 | 10 万/秒 | 6 万/秒 |
|---|---:|---:|
| 服务核 CPU | 97.2%（饱和） | 71.6%（有余量） |
| 实际接受速率 | 72,911/秒 | 59,973/秒（全部接受） |
| 每条事件 CPU | 13.33 μs | 11.94 μs |
| 单核 CPU 上限 | ~7.5 万/秒 | ~8.4 万/秒 |
| validate 每条 | 8.23 μs | 7.18 μs |
| 每批 5000 条同步块（wall） | **61.1 ms** | **53.7 ms** |
| 批到达间隔（cadence） | 69 ms（块占 89%） | 83 ms（块占 64%） |

**单核可持续速率（无内存降级干扰）≈ 7.5 万～8 万/秒**：6 万/秒核才 71.6%（还能再喂 ~40%），
10 万/秒核已 97.2%（接近物理上限、实际只接受 7.3 万/秒）。取两者夹逼，**单核可持续处理
约 7.5 万/秒**，与 T10b 端到端测到的"最大可持续 5 万/秒"（当时服务处于内存第 3 级降级、
额度减半导致 503）的差异主要由**内存降级**解释——去掉降级后处理能力更高。

**每条 CPU 在 10 万/秒比 6 万/秒高 1.4 μs（13.33 vs 11.94）**，主要来自 validate
（8.23 vs 7.18，归一化缓存未命中在满载下更贵，见第三节）与 GC 叠加——不是算法变慢，
是负载相关效应（分配速率高 → gen2 更频繁、缓存更冷）。

## 二、垃圾回收

回收总耗时很低（**占核 <0.6%**），但**第 2 代回收有 13～19 ms 的单次长停顿**，
对事件循环延迟有实际影响（见第四节）。分代统计：

| 组 | 代 | 次数/30s | 总耗时 | 最长一次 | 占核 |
|---|---|---:|---:|---:|---:|
| **10 万/秒** | gen0 | 438（14.6/s） | 77.4 ms | 1.3 ms | |
| | gen1 | 40（1.3/s） | 17.4 ms | 0.75 ms | |
| | **gen2** | **4**（0.13/s） | **67.3 ms** | **18.9 ms** | |
| | 合计 | 482（16.0/s） | 162.1 ms | — | 0.55% |
| **6 万/秒** | gen0 | 363（12.1/s） | 45.2 ms | 0.84 ms | |
| | gen1 | 33（1.1/s） | 10.3 ms | 0.83 ms | |
| | **gen2** | **1**（0.03/s） | **13.6 ms** | **13.6 ms** | |
| | 合计 | 397（13.2/s） | 69.2 ms | — | 0.32% |

- **gen0 高频短**（12～15 次/秒、单次 <1.5 ms）——是分配速率的直接产物，几乎无感。
- **gen2 低频长**：满载 4 次/30s、6 万/秒 1 次/30s，**单次 13～19 ms**。gen2 遍历全部
  长期存活对象（名单条目、key 字符串、缓存条目），所以慢。这 13～19 ms 的停顿直接抬高
  事件循环延迟的 p99/max（见第四节），也解释了 T10b 观察到的偶发查询超时。
- 总耗时占比小（<0.6%）说明 GC **不是吞吐瓶颈**，优化方向应聚焦"缩短 gen2 单次停顿"
  （`gc.freeze()` 冻结启动期对象、调高 gen2 阈值减少触发），而非"减少 GC 总时间"。

## 三、URL 归一化缓存

| 指标 | 10 万/秒 | 6 万/秒 |
|---|---:|---:|
| 总调用（= 接受事件数） | 2,200,000 | 1,805,000 |
| **命中率** | **38.5%** | **38.5%** |
| 未命中次数 | 1,352,829 | 1,110,613 |
| 未命中平均耗时 | **5.04 μs** | **4.43 μs** |
| 未命中中路径带 ID 段占比 | **90.6%** | **90.6%** |

**命中率只有 38.5%，根因是 flowgen 的流量构成，不是缓存太小。** 压测流量里：
- ~50% 的 URL 模板路径含 `{id}` 段（`/api/order/{id}/x{i}` 等），`raw_url` 把 `{id}`
  替换成随机纯数字/UUID/长十六进制——**这些路径每条都不同，归一化缓存以"剥掉 query 的
  路径"为键，每条都是新键，必然未命中**。
- 未命中里 **90.6% 是带随机 ID 的路径**，即命中率上不去几乎全由这批随机 ID 路径造成。

**未命中成本 4.4～5.0 μs/次**（含 `_SCHEME_HOST`/`_MULTI_SLASH` 两个正则、逐段 `_is_id_segment`
判断、缓存回填），占 validate 的 ~38%（61.5% 未命中率 × 5 μs ≈ 3.1 μs/事件，validate 共 8.2 μs）。
这正是 validate 是第一大头（60%+）的原因，也是**首要优化点**（见第六节方向 1）。

命中率在满载（10 万/秒）没有进一步下降（仍是 38.5%），说明 10 万条的缓存上限没成为瓶颈
——瓶颈是流量里 50% 的随机 ID 路径天然不命中。

## 四、事件循环延迟

每 100 ms 探针（call_soon 一个小任务，记"计划时刻→实际执行"延迟）：

| 组 | p50 | p99 | max |
|---|---:|---:|---:|
| 10 万/秒 | 204 ms | 397 ms | 405 ms |
| 6 万/秒 | **66 μs** | 41.0 ms | 61.1 ms |

- **6 万/秒 p50 只有 66 μs**——但这是探针的**自同步**特性：探针协程睡到计划时刻才
  `call_soon`，而它自己的 `sleep` 唤醒本身也会被阻塞推迟，所以它几乎总在"空闲时刻"
  采到样本，p50 偏低。**p99/max 才暴露真实的最坏阻塞**：41 ms / 61 ms ≈ 一个 5000 条
  写入同步块（53.7 ms）的长度。
- **10 万/秒 p50 就 204 ms**：核 97.2% 饱和、服务端跟不上（只接受 7.3 万/秒），就绪队列
  持续有积压，探针任务排在一堆批次处理后面，所以中位数都被拖到 200 ms 量级。

**最长停顿的来源**：
1. **5000 条写入的同步块**（parse+validate+ingest，wall 54～61 ms）——**主要来源**。
   每批在 `ingest.py` 里是 `for i in range(0, n, CHUNK_EVENTS=5000)` 循环内**不 yield**
   地连续处理 5000 条，只有块与块之间才 `await asyncio.sleep(0)`。这是单核上最连续的
   独占时段。
2. **gen2 GC 停顿**（13～19 ms）——次级，叠加在写入块之上时把 p99 再抬高。
3. **每秒 tick**（快照 ~14 ms + 定稿 ~5 ms）——发生在秒边界，也会短暂占住循环。

写入块占事件循环 wall 的比例：6 万/秒 53.7 ms/83 ms ≈ **64%**、10 万/秒 61.1 ms/69 ms ≈ **89%**。
**只要写入块不拆小，事件循环延迟的 p99 就无法显著低于 ~50 ms**——这是查询 p99 能否达标的
关键（见第五节）。

## 五、6 万/秒时查询 p99 能否低于 50 ms

**要分两种查询：**

**（1）默认查询（60 s 窗口、不带 `at`）——能，且富余极大。**
本次加了一个查询探针（每 250 ms 发一次真实 `QueryService.topk(URL, 60s, k=10)`，wall 计时），
结果（6 万/秒）：**p50 0.016 ms、p99 0.040 ms、max 0.040 ms**。原因：60 s 窗口 + k≤100
命中快照路径，直接读 `engine.snapshot` 预计算好的 Top 列表（O(1) 拷贝），计算本身**亚毫秒**。
探针本身只占极少量 CPU（快照 topk 亚毫秒），未影响该组吞吐（核 71.6% 与无探针时 73.5% 一致）。

**（2）回放查询（带 `at`、或非 60 s 窗口）——计算上可能、但受写入块阻塞，需缩短写入块才稳。**
回放走 `collect_parts + bounds.top_k`，T10b 在 3.5 万/秒 + 内存降级下实测 p99 156～195 ms。
去掉降级、6 万/秒（核 71.6%、余量 40%）下，计算本身会好于 T10b，但 60 s 数据量的
`collect_parts + top_k` 本身约 10～50 ms，且**查询协程若恰好落在一个 53.7 ms 的写入同步块
之后，要等块结束才执行**（第四节 p99=41 ms 已证）。所以回放查询 p99 <50 ms 需要同时满足：
计算 <~15 ms **且** 不撞写入块——后者靠**缩短写入块**（第六节方向 2）解决。

**结论**：默认（快照）查询 p99 远低于 50 ms（实测 0.04 ms）。回放查询 p99 <50 ms 在
6 万/秒**有条件可达**——瓶颈不是 CPU（有余量），而是**写入块的 54 ms 独占段**造成的
事件循环延迟；把写入块从 5000 拆到 ~1000 条（~10 ms），查询 p99 <50 ms 才有把握。

## 六、优化方向清单（按预计收益排序，只列方向不实施）

| # | 方向 | 针对阶段 | 预计节省 | 需改文件 | 涉及冻结模块 | 风险 |
|---|---|---|---|---|---|---|
| **1** | **归一化未命中提速**：(a) 路径既无 `://` 也无 `//` 时跳过 `_SCHEME_HOST`/`_MULTI_SLASH` 正则（压测路径多为 `/api/...` 相对路径）；(b) 用预编译正则 `fullmatch` 判 ID 段替代逐字符 `_is_hex` 循环；(c) 对"路径含随机 ID"的键**不写缓存**（反正必未命中，写缓存只占内存 + 触发 10 万上限清空） | validate（60%） | 未命中 4.4～5.0 μs→~1.5 μs，省 ~2.5 μs/事件 ≈ **每条省 20%、核省 ~13%**，可把单核上限从 ~7.5 万提到 ~9 万 | `flowlens/model.py` | **否**（model.py 是上层，非 ✅ 冻结） | 低。需保证 `normalize_url` 输出逐字节不变（`tests/test_model.py` 有改前参考实现对照，加回归即可）；(c) 会改变缓存语义（不缓存带 ID 键），需确认不影响"命中"路径 |
| **2** | **写入块从 5000 降到 ~1000 条**，使单个同步块 ~10～12 ms | 事件循环延迟 / 查询 p99 | 写入块 54→11 ms，**事件循环 p99 从 ~41 ms 降到 ~11 ms 量级**，直接解锁回放查询 p99<50 ms；对吞吐几乎无损（块间 `sleep(0)` 让出反而缓解饱和积压） | `flowlens/ingest.py` 的 `CHUNK_EVENTS` | **否** | 低。纯参数；需确认块间 `sleep(0)` 在 10 万/秒下不因让出过多而降低吞吐（本次 10 万/秒已饱和，让出反而有利） |
| **3** | **GC 调优**：预热结束后 `gc.freeze()`（把启动期常驻对象移出分代追踪）+ 调高 `gc.set_threshold`（减少 gen2 触发频率） | gen2 停顿（13～19 ms） | 削掉 gen2 的 13～19 ms 单次停顿（事件循环 p99/max 的主要次级来源）；总耗时占比 <0.6%，**不影响吞吐**，纯粹降尾延迟 | `flowlens/__main__.py`（启动后调 gc）或 `engine.py` 初始化 | **否** | 中。`gc.freeze()` 后这些对象永不被分代 GC（靠引用计数回收）——需确认冻结的确实是"长期存活"对象（名单、缓存），不会把本应回收的对象钉住导致内存涨 |
| **4** | **快照改维护窗口汇总**：每秒 tick 的 `tick_snapshot`（~14 ms、占核 4～5%）目前重算 60 s 窗口的两维 Top；改为增量维护（每秒只并入新定稿的秒、滚动淘汰过期秒），把快照从 O(60s 全量) 降到 O(1s 增量) | tick_snapshot（5%） | 省 ~13 ms/秒 ≈ 核 4～5%，同时缩短秒边界的 tick 独占段（对事件循环 p99 有帮助） | `flowlens/engine.py`（快照计算）+ 可能 `flowlens/bounds.py`（**冻结**） | **可能涉及** `bounds.top_k`（冻结）——若增量维护需要新的合并语义，得先确认能否只用现有 `bounds` 公开接口，不能则停下说明 | 中高。快照是 T3 已冻结审过的逻辑，改动需保证与全量重算结果一致（有 slow 等价性测试可锁） |
| **5** | **gen2 停顿与 tick 拆段让出**：把 gen2 回收（若可控）与长 tick（定稿 ~5 ms + 快照 ~14 ms）拆成多段、段间 `await sleep(0)`，避免单段独占 | gen2 / tick | 与方向 3 叠加，进一步削尾延迟；但 gen2 由解释器内部触发、**外部无法直接拆段**，实际只能靠方向 3 减少其频率 + 让 tick 拆段 | `flowlens/engine.py`（tick 拆段） | tick 逻辑在 engine（上层），**否** | 中。gen2 本身拆不了（方向 3 是正解）；tick 拆段需保证秒边界的一致性（同一秒的定稿+快照不能拆到两个 tick 里各做一半） |

**排序理由**：方向 1 是唯一能同时降"每条 CPU"（提吞吐上限）和 validate 大头的，收益最大；
方向 2 收益第二且风险最低（一个常量），直接解锁查询 p99 目标；方向 3/5 只降尾延迟、不动吞吐，
且 gen2 的真正解法（3）比 5 更直接，故 3 排在 5 前；方向 4 收益小且可能碰冻结模块，放最后。

## 附：测量口径说明

- **每条事件 CPU** = 测量窗口进程 CPU 时间 / 窗口内接受事件数（预热期也在写，用窗口内
  增量而非容器累计）。
- **扣 GC**：各阶段 `cpu_us`/`wall_us` 是"扣除该调用时段内发生的回收耗时"后的值；`gc_us`
  字段是被扣掉的量。校验口径 =（扣后阶段之和 + GC 总耗时）/ 进程 CPU ≈ 1.0（10 万 0.948、
  6 万 0.932，余 ~5～7% 是未包装的 aiohttp 协议/响应序列化/定时器）。
- **查询探针**：仅 6 万/秒组开启（`--query-probe`），每 250 ms 一次 `topk(URL, 60s, k=10)`
  快照查询；10 万/秒组不开，避免探针干扰处理能力测量。
- **loadgen error 计数**：两组 loadgen 汇总里的 `errors`（10 万 131 万条、6 万 64 万条）
  是**测量结束后 10 s 余量**里、客户端往正在关闭的容器发送产生的连接重置——
  `sent = accepted + rejected + errors` 严格相等，且 error 数 ≈ 10 s × 目标速率
  （640k = 10×60k；1310k = 10×100k + 少量积压），与服务端处理能力无关。测量窗口内
  服务端 **0 拒绝、0 503 重试**（`rejected`/`retries`），窗口内接受率见第一节。
