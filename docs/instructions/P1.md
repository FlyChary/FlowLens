## 一、解析进程（新建 flowlens/parse_pool.py）

1. 进程池用 multiprocessing 的 spawn 上下文创建，在 __main__ 中、创建引擎之前启动，避免子进程继承主进程的大块内存。子进程只导入完成解析所需的模块（orjson、flowlens.model、flowlens.hashing），不导入 aiohttp 与引擎
2. 子进程的任务函数：输入原始请求体与 Content-Encoding，依次 decode_body、load_array、validate、计算 event_id、url、user 三列的 64 位哈希。返回一个可 pickle 的小对象：ts 与 nbytes 两个 int64 数组、三个 uint64 哈希数组、urls 与 users 两个字符串列表、invalid 计数。异常（BadRequest、PayloadTooLarge、UnsupportedEncoding）原样抛回主进程
3. 子进程启动时做一次哈希自检：对一个固定字符串计算哈希，与主进程传入的期望值比较，不一致就报错退出（防止 PYTHONHASHSEED 不一致导致两边哈希不同）
4. 进程数：读取容器的 CPU 配额（cgroup v2 的 cpu.max，v1 的 cpu.cfs_quota_us 与 cpu.cfs_period_us），没有配额时用 os.cpu_count()；解析进程数 = min(3, 可用核数 − 1)；结果小于 1 时不启用进程池。可用环境变量 FLOWLENS_PARSE_WORKERS 覆盖（0 表示禁用）
5. 子进程崩溃（BrokenProcessPool 等）：记录日志，重建进程池，当前请求返回 503 + Retry-After（此时尚未去重，重试安全）

## 二、主进程的写入路径（flowlens/ingest.py、flowlens/engine.py）

1. IngestService：预留在途额度后，进程池可用时用 loop.run_in_executor 把请求体交给解析进程，await 结果；不可用时走现有路径
2. engine 增加一个接受"已解析结果"的写入入口：跳过 key_hashes，直接使用传入的哈希数组；其余逻辑（classify、Bloom、采样、按秒分组、写入秒桶）与现有 ingest 共用同一份代码，不要复制。user 与 url 的字符串驻留在主进程中进行（驻留表只在主进程有意义）
3. 限制同时写入引擎的请求数：用一个 asyncio.Semaphore（默认 1）保护"写入引擎"这一步，写入引擎仍按块进行、块间让出事件循环。块大小从 5000 条改为 2000 条（写入引擎每条约 2.5 μs，单块约 5 ms）。依据：混合负载下查询 p99 高的原因是查询排在多个写入块之后

## 三、等价性与正确性测试

1. 同一个请求体（长尾、全随机、含各种非法事件、gzip、NDJSON），分别走进程池与单进程路径，写入两个全新的引擎后，对同一区间的 topk（url 与 user）、stats、计数器逐项比较，结果必须完全相同
2. 503 重试：进程池路径下在途额度已满时返回 503，释放后重试不被判为重复
3. 子进程崩溃后重建，后续请求正常
4. 核数为 1 时不启用进程池；FLOWLENS_PARSE_WORKERS=0 时禁用
5. 应用关闭（包括 SIGTERM）时进程池被关闭，没有残留进程

## 四、容器实测（256 MB，服务不再固定单核）

CPU 分配：用户的 CPU 是 8 核 16 线程，WSL 中的 16 个逻辑核两两共享一个物理核。先用 lscpu -e 查出逻辑核与物理核（CORE 列）的对应关系，给服务分配 4 个位于不同物理核上的逻辑核（例如 --cpuset-cpus=0,2,4,6，以实际查到的为准），压测进程用剩余物理核上的逻辑核，并在汇报中写明分配方式。压测进程本身也会消耗不少 CPU（每秒 20 万条时约需 2.5～4 个核），如果压测端成为瓶颈，在汇报中说明。

1. S1 吞吐爬坡：最大可持续吞吐（与之前相同的判定标准），以及饱和时的接受速率
2. S2 混合负载：各类查询的 p99
3. S4 全随机攻击流量 10 分钟：工作集峰值与降级级别（所有进程合计的内存）
4. S3 精度：结果不能比之前变差
5. 同一组实验再用 --cpuset-cpus=0（单核）跑一次 S1，确认退回单进程路径后与之前的结果一致

如果内存超出（S4 进入第 3 级以上），依次尝试：减少解析进程数、确认子进程没有导入不必要的模块；在报告中写明每种配置的内存与吞吐。
