# T10c：控制台接真实服务（实时 + 回放）

## 开始前提

收尾提交已完成（TASKS.md 的"执行顺序"里 T10c 排在提交之后）。因此本任务的约束比前面几个任务更紧：

- **`flowlens/` 下的服务代码只允许做缺陷修复，不改变行为**。本任务原则上不改 `flowlens/`；确实发现缺陷时先停下来说明，确认后再改，并在汇报里单列
- 冻结的基础模块（config、dims、hashing、timewin、sketch、dedup、bounds、segtree、ring）照样不许动
- 不引入新依赖：只用 numpy / orjson / aiohttp / pytest 与标准库（压缩用 `gzip`、`zlib`）
- 控制台是独立工具，全部新代码放 `tools/` 下；`docs/prototype/console.html` 作为界面原型**保持原样不动**（它是设计稿，答辩时要对照），适配后的页面放到 `tools/console/index.html`

开始前确认：`tools/loadgen.py` 有 `--fast`；`tools/experiments.py` 能读 `前端数 N（原因）`（`parse_front_count`）；`flowlens/api/debug.py` 的 `/debug/structure`、`/debug/info` 可用（`FLOWLENS_DEBUG=1`）。不满足时停下汇报。

## 零、先定下来的几件事

原型页面里的数据全由内置模拟器 `S`/`step()`/`finalize()` 生成，帧结构是 `{m, cur, ringNext, newest, slots, nodes, builders, tk, sse, ingested}`，渲染函数（`renderRing/renderTree/renderEvents/renderQuery/renderPanels/renderCompare/lineChart`）全部只读这个帧结构。适配的正确做法是**保留全部渲染代码不改，只换掉"帧从哪来"**。

由此确定三条设计决策，后面的实现都按它来：

### 1. 帧由后端生成，实时与回放共用同一套帧

后端（`tools/console_server.py`）负责把各数据源拼成**同一种帧 JSON**，实时模式和回放模式都从这里取。页面里只有一个适配层（把帧交给渲染函数），不写两套逻辑。这样"字段拼错"这类问题能在 Python 单测里挡住，而不是靠肉眼看页面。

帧的字段（与原型帧名对齐，渲染代码不动）：

```json
{"mode": "live|replay",
 "t": 1792316804, "now_ms": 1792316804230,
 "cur": 1792316804, "ringNext": 1792316739, "newest": 1792316738,
 "slots": [{"sec": 1792316700, "events": 4821, "heapUrl": 512, "heapUser": 512,
            "u": 0, "top": [{"k": "/api/item/x12", "c": 1903}]}],
 "nodes": [{"level": 0, "start": 1792316100, "end": 1792316101,
            "events": 5000, "items": 512, "u": 0}],
 "builders": [{"level": 2, "start": 1792316100, "span": 4, "filled": 3, "cand": 120}],
 "tree": {"by": "url", "newest": 1792316738, "retention_range": [1792316138, 1792316739]},
 "retention_sec": 600,
 "topk": {"by": "url", "k": 10, "unseen_upper": 0, "degraded": false,
          "items": [{"key": "/api/item/x12", "count": 1903, "err": 21}]},
 "stats": {"approx_distinct_users": 128310, "approx_p95_bytes": 8421, "window_ms": 60000},
 "healthz": {"...": "/healthz 的原始对象，取不到时为 null"},
 "run": {"sent": 50000, "accepted": 49880, "rejected": 120, "errors": 0,
         "lat_p50_ms": 12.1, "lat_p95_ms": 31.0, "lat_p99_ms": 44.2},
 "env": {"front_count": 0, "front_reason": "...", "run_mode": "single|fronts",
         "debug": true, "flowlens_url": "http://127.0.0.1:8080"},
 "accuracy": {"topk_url": {...}, "topk_user": {...}, "stats": {...}}}
```

`slots` 必须补齐到 66 个（环的 66 个槽，`cur-60 … cur+5`），没有数据的秒用
`{"sec": s, "events": 0, "heapUrl": 0, "heapUser": 0, "u": 0, "top": []}` 填充——
`/debug/structure` 只返回有数据的秒桶，不补齐会导致环图错位。

`accuracy` 只在回放的 S3 里出现，其他情况为 `null`。`run` 在没有压测时也为 `null`。

### 2. "估计与真实"的对比只做回放，且不造逐秒真实值

原型 `renderCompare` 里逐秒的 `usersTrue`、`p95True`、`top[].lo` 是模拟器算的真值。真实世界里逐秒真值只有拿 `archive/` 里的存档调 `tools/exact.py` 才能算，成本高（每秒一次精确解）且与"离线抽样对比"的口径重复。

所以：回放模式下"估计与真实对比"面板呈现两件事——逐秒的**服务值曲线**（来自 S3 `accuracy.jsonl` 的 `per_second`，带 `err` 的上下界带），以及一张**抽样对比表**（来自 `sample_comparison`：召回、计数相对误差、`in_bounds` 比例、去重用户数与 p95 的 service/exact）。**不要在页面上画"真实值曲线"**，也不要在后端为此逐秒调精确解。面板标题下加一行小字说明口径。

### 3. 前端数与前/单进程模式怎么知道

`/healthz` 里**没有**前端数，也没有模式字段；服务代码已冻结，不给它加。可用的三个信号，按可靠性排序：

1. `/debug/info` 的 `query_sock`：非空 ⇔ 前端模式（只有前端模式才起引擎侧 Unix 套接字）。这是唯一的结构化信号，但要求 `FLOWLENS_DEBUG=1`
2. 服务启动日志里的 `前端数 N（原因）` 一行（格式与 `tools/experiments.py::parse_front_count` 相同）
3. 控制台自己的命令行参数 `--fronts` / `--front-reason`，手工填（前两条都拿不到时用）

后端启动时按 1 → 2 → 3 依次尝试，把结果和来源（`"source": "debug|log|arg|unknown"`）一起写进 `env`，页面在结构视图的标题旁显示"单进程模式"或"前端模式（N 个接受端）"，取不到就显示"模式未知"。回放模式下从 `meta.json` 的 `front_count` / `front_reason` 读（`tools/experiments.py::write_meta` 已经在写这两个字段）。

日志来源的实现：控制台提供一个可选参数 `--service-log <路径>`（`docker logs -f` 或重定向文件均可，只读末尾若干行）；没有该参数就只试 1 和 3。

## 一、T10c-1：控制台后端与实时模式

### 1. `tools/console_server.py`

一个 aiohttp 应用，默认监听 `127.0.0.1:8090`，命令行：

```
python tools/console_server.py --flowlens http://127.0.0.1:8080 --port 8090
       [--results results] [--service-log <日志文件>] [--fronts N --front-reason ...]
       [--loadgen-python <python>] [--max-clients 8]
```

要求：

- **代理**：页面所有请求都发给控制台，由后端转给 FlowLens，页面不直接跨域访问 8080。转发 `GET /healthz`、`GET /v1/topk`、`GET /v1/stats`、`GET /debug/structure`、`GET /debug/info`；透传查询串与状态码（422/503 原样返回，不用异常包一层）。用一条共享的 `aiohttp.ClientSession`，超时 5 秒
- **静态页**：`GET /` 返回 `tools/console/index.html`；页面里的 CSS/JS 全部内联（与原型一致），不加外链资源
- **实时帧流**：`GET /api/live`（SSE，`event: frame`，1 Hz）推送上面定义的帧。订阅者数上限 `--max-clients`（默认 8），超限返回 503 + `Retry-After`；发送缓冲区高水位时丢弃该订阅者的旧帧而不是保留（与 `flowlens/api/stream.py` 同样的思路：慢客户端只丢自己的帧）
- **回放**：见第二节的接口
- **有界**：帧流只保留最近 300 帧（页面只需要当前帧，但保留少量便于断线重连后补画）；后端不缓存整个实验结果到内存，回放帧一次性返回且限制条数（见第二节）

各接口一览（写进 `tools/console/README.md`，见第三节）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/` | 页面 |
| GET | `/api/env` | `env` 对象（前端数、模式、debug 是否开启、FlowLens 地址） |
| GET | `/api/live?by=url` | SSE，1 Hz 推帧 |
| GET | `/api/structure?by=&at=&window=` | 代理 `/debug/structure`（页面高亮查询用） |
| POST | `/api/run/start` | 启动压测，请求体见下 |
| POST | `/api/run/stop` | 停止压测 |
| GET | `/api/run/status` | `{running, scenario, stage, stage_index, stages, started_ms, elapsed_s, error}` |
| GET | `/api/replay/runs` | 结果目录列表 |
| GET | `/api/replay/frames?run=&scenario=` | 回放帧数组 |
| GET | `/api/replay/summary?run=&scenario=` | 该场景 `summary.json` 与 `meta.json` |

### 2. 压测控制

后端 `subprocess` 启动 `tools/loadgen.py`（异步读它的 stdout，按行解析每秒 JSON），同一时刻**只允许一个压测进程**，第二个 `start` 返回 409。

请求体（页面下发，后端原样映射成 loadgen 参数）：

```json
{"scenario": "const|ramp|overload|random",
 "rate": 50000, "duration_s": 90, "batch": 5000, "conc": 32,
 "dist": "长尾|均匀|随机", "gzip": true, "fast": false}
```

场景 = **多级速率表**（后端定义，不在页面里写逻辑）：`const` 一级；`ramp` 从 `rate/4` 起四档递增到 `rate`，每档 `duration_s/4`；`overload` 先 `rate` 跑 60 秒、再停 60 秒观察恢复；`random` 一级、强制 `dist=随机` 且 `--p-*` 全为默认。分级是**顺序起多个 loadgen 进程**（每级一个），不是在一个进程里改速率——loadgen 不支持运行中调速。级与级之间留 2 秒空档，`run.status` 暴露 `stage_index/stages`。

`--fast`：页面上一个复选框。勾选时后端必须拒绝与它冲突的选项（`gzip` 无冲突、`dist=随机` 冲突、`accuracy` 场景冲突）并在 400 里说明原因；`fast=true` 时把「请求体 gzip」置灰。理由写在页面的说明文字里：快速模式省掉发送端开销，高速率才打得上去，但事件全部是正常事件、不能用于精度实验。

压测进程的 argv 一律用列表形式传给 `create_subprocess_exec`，不走 shell；stdout 必须按 UTF-8 解码（`encoding="utf-8", errors="replace"`）。进程退出后保留最后一次 `{"type":"summary"}` 的内容，放进 `/api/run/status` 的 `summary` 字段，页面在结束时显示接受率、p99、客户端 CPU。

### 3. `tools/console/index.html`（页面适配）

从 `docs/prototype/console.html` 复制过来改，**渲染函数与样式不动**。改动清单：

1. 删掉模拟器（`S`、`step`、`finalize`、`windowTopK`、`recordFrame`、预热循环、`restart/tick` 的定时推进）
2. 新增适配层：`toFrame(raw)` 把后端帧补齐成渲染函数要的形状（字段名已在第零节对齐，这里主要是把 `top` 的 `{k,c,e}` 与 `slots` 的形状整理好，以及把 `healthz`/`run` 里的数字取出来放进 `m`）
3. 实时模式：`new EventSource('/api/live?by=' + topBy)`，收到 `frame` 事件就 `frames.push`、按原型同样的 300 帧上限裁剪、`draw()`
4. 内部结构：帧里就带 `slots/nodes/builders`，直接用（不再本地模拟定稿）
5. 查询高亮（`qBtn`）：删掉 `computeQuery`，改为 `GET /api/structure?by=<dim>&at=<agoMs>&window=<n>s`，用返回的 `plan`（`ring_secs` / `tree_nodes` / `edges`）喂给 `renderRing/renderTree/renderEvents` 的高亮参数。请求失败或 debug 未开启时，在 `qResult` 里显示原因（"服务的调试接口未开启，请用 FLOWLENS_DEBUG=1 启动"）
6. 节点悬停提示：`/debug/structure` 的节点**不返回名单内容**（只有 `items/u/events`），实时模式下节点提示里不要再列 top 键值；秒桶提示照旧（`dims.url.top` 有 3 个）
7. 「模拟速度」面板改成「回放速度」，只在回放模式可用；实时模式下置灰并说明"实时模式按真实时间刷新"
8. 拒绝计数：服务状态面板增加 `ingest_rejected`（在途额度拒绝）与 `raw_rejected`（请求体额度拒绝）两个读数，以及 `invalid` / `late` / `deduped`；这些字段来自 `/healthz`，回放时来自 `timeline.jsonl` 里那份 `healthz`
9. 模式与前端数：结构视图标题旁显示"单进程模式"或"前端模式（N 个接受端）"，取自帧里的 `env`；回放时取自 `meta.json`
10. 场景下拉改成真实可跑的四项（`const/ramp/overload/random`），说明文字写清"精度实验请用 `tools/experiments.py --scenarios S3` 跑完再来回放"
11. 「与离线精确解对比」区域：实时模式下显示"精度对比只在回放模式可用"

## 二、T10c-2：回放模式与内部结构录制

### 1. 录制内部结构（新增 `tools/structrec.py` + `tools/experiments.py` 加开关）

回放要展示活跃环与线段树的演变，但现在没有任何实验把 `/debug/structure` 存下来。做法：

- 新模块 `tools/structrec.py`：`StructureRecorder(url, outdir, interval_ms=1000, by="url")`，每秒 GET 一次 `/debug/structure?by=url`，把返回对象按行写进 `<场景目录>/structure.jsonl.gz`（`gzip.open(..., "wt", encoding="utf-8")`，一行一个 `{"t": sec, "s": <structure 对象>}`）。只存 `by=url` 一份：两个维度的环/树结构相同，差别只在名单长度（`/debug/structure` 的 `dims` 里两维都有）
- 体积：实测一次约 94 KB 原始、压缩后 15～20 KB，10 分钟实验约 10 MB。写入前不必再压，但要在文件头（第一行）写一个 `{"t": 0, "meta": {"by": "url", "interval_ms": 1000}}` 便于将来兼容；条数上限 7200 行（2 小时），超过就停录并记一条警告
- `tools/experiments.py` 增加 `--record-structure`（默认关）。开启时每个场景启动服务后顺带起录制器、场景结束前停掉；`meta.json` 的 `params` 里记 `record_structure: true`
- 录制器读不到结构（`FLOWLENS_DEBUG` 未开 → 404）时，记一条日志然后整场禁用，不中断实验；服务的 `--extra-env FLOWLENS_DEBUG=1` 由用户在命令行自己加（不要替用户默认打开，调试接口读的是真实状态，会给服务加少量开销）
- `docs/EXPERIMENTS_FORMAT.md` 补一节 `structure.jsonl.gz`：字段、行格式、体积、以及"没开 `--record-structure` 时该文件不存在，控制台的内部结构视图在回放时显示提示"
- 顺带把文档里缺的 `S4` 目录补上（现在只写了 S1/S2/S3/S5，`tools/experiments.py` 已经实现 S4）

### 2. 回放接口（`tools/console_server.py`）

- `GET /api/replay/runs`：列出 `--results` 根目录下所有 `<日期时间>/` 及其子场景目录，只返回含 `timeline.jsonl` 的；每项 `{run, scenario, created_ms, params, front_count, front_reason, has_structure, has_accuracy}`（前几项来自 `meta.json`）。上限 200 项
- `GET /api/replay/frames?run=&scenario=`：读 `timeline.jsonl`，按 `t` 逐秒组帧；同一秒在 `structure.jsonl.gz` 里找 `sec <= t` 的最近一帧（1 Hz 录制时基本一一对应），桥接 `slots/nodes/builders/newest/ringNext`；`accuracy.jsonl` 的 `per_second` 行按 `t_ms` 归到秒。返回 `{"frames": [...], "missing": {"structure": bool, "accuracy": bool}}`
  - 帧数上限 7200；超过返回 413 并在页面提示"该实验超过 2 小时，本版不支持整段回放"
  - 路径安全：`run` 与 `scenario` 只允许 `[A-Za-z0-9_.-]`，拼出的路径必须在 `--results` 根目录之内，否则 400
  - 文件大小上限：单个 `timeline.jsonl` 64 MB、`structure.jsonl.gz`（解压后）512 MB，超限 413
- `GET /api/replay/summary?run=&scenario=`：直接回 `summary.json` 与 `meta.json` 的内容（读不到就回 `null`）
- 页面回放：`modeReplay` 时拉一次 `frames`，滑块与"播放"按原型逻辑走（速度用「回放速度」面板）；内部结构在 `missing.structure` 为真时显示"该实验未录制内部结构（运行时加 `--record-structure`）"并只显示空洞；查询高亮在回放模式**不提供**，输入框置灰并在 `qResult` 里说明"回放的查询拆分需要实时调用 `/debug/structure`，本版不做"
- 「估计与真实对比」按第零节第 2 条：逐秒服务值曲线（`accuracy.per_second` 的 `topk_url`/`stats` 响应体）+ 抽样对比表（`sample_comparison`，只统计 `bucket == "valid"` 的样本，`degraded`/`rejected` 只计数）。面板顶部显示该场景 `summary.json` 里的 `valid/degraded/rejected` 三个数
