## 已知结论（不需要再验证）

- 每条被接受事件的 CPU 约 10.7 μs，单核上限约 9 万～10 万条/秒
- validate 在满载下 5.28 μs/条，远高于基准。审查时已在本地确认主要原因：flowgen 约一半的 URL 路径带随机 ID（如 UUID），归一化缓存以去掉 query 后的路径为键，带 ID 的路径每条都不同，每条都无法命中。本地实测：缓存命中 0.37 μs/条，未命中 5.89 μs/条
- 写入每块 5000 条、每条约 10.7 μs，一块同步处理约 53 ms，这本身就让事件循环延迟无法低于 50 ms

## 一、修正与补充测量（tools/profile_server.py）

1. 测量窗口改用墙钟截止时间（time.monotonic），不再按"睡 0.5 秒 × 次数"计时。loadgen 的持续时间必须覆盖整个预热与测量窗口，并多留 10 秒余量
2. 垃圾回收单独计账：用 gc.callbacks 记录每次回收的开始与结束时刻。分阶段计时中，扣除在该阶段内发生的回收耗时，把它们单独汇总为"垃圾回收"一项（按代分列：次数、总耗时、最长一次）。这样各阶段的数字才是它们自身的开销
3. 归一化缓存的命中率：在运行时包装 flowlens.model.normalize_url（总调用次数）与 flowlens.model._normalize_url（未命中时才会被调用），报告命中率与未命中时的平均耗时；同时统计未命中的原始 URL 中，路径带 ID 段的比例
