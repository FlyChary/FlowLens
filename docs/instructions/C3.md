## 一、三项改动

1. 定期归还空闲内存（flowlens/ticker.py）：每隔一段时间（默认 10 秒，可配置）通过 ctypes 调用 libc 的 malloc_trim(0)。非 Linux 平台或找不到该函数时什么都不做，不能报错。记录每次调用的耗时，以及累计调用次数，通过 /healthz 暴露。依据：C2 测得满载时每次可回收 20～42 MiB，停止发送后一次回收约 60 MiB
2. 字符串驻留（新建 flowlens/intern.py）：提供一个有上限的驻留表（字典，满了整体清空，与归一化缓存的策略一致），相同内容的字符串返回同一个对象。
   - 用户 ID：在 engine.ingest 写入秒桶之前对 users 做驻留，上限 8192（C1 的建议）
   - URL：在 model.normalize_url 返回结果之前对归一化结果做驻留（不改归一化逻辑本身）。原因：路径带不同 ID 的原始 URL（如 /order/1 与 /order/2）归一化后内容相同，但现在每次都会生成新的字符串对象，各秒桶、叶子、节点里会存很多份。上限 32768
   - 上限作为模块常量，不放进 config.py
3. 在途额度作为实验变量：把 ingest.py 中在途解压后字节数的上限（MAX_PENDING_BYTES）改为可通过环境变量覆盖（默认值保持 4 MB 不变），用于下面的实验对比

## 二、实验（全部在容器中，--memory=256m --memory-swap=256m，使用真实的内存读数）

参数与 C2 的基线相同：长尾，每秒 3 万条，每批 5000 条，4 个进程 × 每进程 8 个并发连接，持续 5 分钟。记录工作集、RssAnon 随时间的变化，以及降级级别的变化。依次比较：
1. 当前主线代码（C2 已测过，可直接引用 C2 的数字，不必重跑）
2. 加上定期 malloc_trim
3. 再加上字符串驻留
4. 再把在途额度降到 2 MB

取效果最好的组合，再做两项：
5. S4 攻击流量：全随机分布（每个 URL 和用户都不重复），每秒 3 万条，持续 10 分钟。这是题目要求的"对抗性流量下内存有界"的直接证据。在 tools/experiments.py 中加入 S4 场景
6. 如果第 3 或第 4 组能让服务在 5 分钟内保持第 0 级：重做 S3 精度实验（长尾，每秒 3 万条，5 分钟，存档后用 tools/exact.py 对比），得到第一份有效的精度数据。注意 T10b 已修复"空结果被算作召回 100%"的问题，抽样时记录每个响应的状态码与 degraded 字段
