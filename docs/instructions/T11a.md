# T11a：端到端 CPU 剖析

## 背景

T10b 测得最大可持续吞吐约 5 万事件/秒，换算每条约 20 微秒；而统计核心单独测时每条约 4～5 微秒（bench_engine），解析约 0.5～1.8 微秒（bench_model）。中间约 15 微秒去向不明。同时，T10b 的测量发生在服务因内存进入第 3 级降级时，降级本身（额度减半导致 503）也影响了结果。

本任务只回答一个问题：在不受内存降级干扰的情况下，服务处理每条事件的 CPU 时间花在了哪里。内存问题由支线 C2 同时调查，本任务不处理。

## 规则

- 只新建 tools/profile_server.py、docs/perf/T11a-report.md，以及必要的测试；不修改 flowlens/ 下的任何文件，不改 Dockerfile
- 可以在工具脚本里对服务的函数做"包装计时"（运行时替换为带计时的包装函数），但不得改变它们的行为
- 不引入新依赖（cProfile、gc、time 等标准库即可）
- 结束时更新 docs/PROGRESS.md、AI_LOG.md，提交（不要推送）

## 一、剖析脚本：tools/profile_server.py

1. 在进程内用 create_app 启动真实的服务，传入固定的假内存读数（例如始终返回 50 MB 与 256 MB 上限），保证服务不会因内存进入降级
2. 在容器中运行，与评测环境一致：用正式镜像，把仓库的 tools 目录挂载进去，docker run --memory=256m --memory-swap=256m --cpuset-cpus=<服务核>；loadgen 在 WSL 宿主上用其他核运行（核的分配与 T10b 相同）
3. 每次运行先预热 15 秒，再测量 60 秒。总时长控制在 90 秒以内，避免真实内存在长时间运行后逼近容器上限（假读数会让降级失效，必须注意不要真的超限；运行期间记录真实工作集，超过 220 MB 时提前结束并在报告中说明）
4. 测量内容：
   a. 分阶段计时（包装计时，所有阶段的耗时之和应接近服务核的 CPU 时间）：读取请求体、gzip 解压、load_array、validate、engine.ingest（再细分：classify、去重 Bloom、哈希、按秒分组、各维度写入秒桶）、每秒 tick（定稿与快照分开）、其他
   b. 垃圾回收：用 gc.callbacks 记录每次回收的代数、耗时、回收对象数。服务内存中有大量长期存活的 Python 对象（名单条目、key 字符串等），Python 的分代垃圾回收在做第 2 代回收时会遍历全部对象，可能产生很长的停顿。这一项要单独统计：每秒回收次数、第 2 代回收的次数与最长耗时
   c. 事件循环的延迟：每 100 毫秒调度一个小任务，记录它实际被执行的延迟，得到延迟分布（这直接决定查询的 p99）
   d. cProfile：单独运行一次，取累计耗时最多的前 30 个函数。cProfile 本身会让程序变慢，它的结果只用来看比例，不用来算绝对值
5. 运行组合（每组都要做 a～c；d 只在第 1 组做一次）：
   - 第 1 组：长尾，每秒 5 万条，每批 5000 条，不压缩
   - 第 2 组：同上，gzip 压缩
   - 第 3 组：同上，每批 1000 条（看每个请求的固定开销）
   - 第 4 组：快速爬坡（每秒 5 万、10 万、15 万，每级 15 秒，不开 cProfile），在没有内存降级干扰时，CPU 能支撑的最高速率

## 二、报告：docs/perf/T11a-report.md

1. 每组运行的结果：实际被接受的速率、服务核的 CPU 占用、每条事件的平均 CPU 时间，以及按阶段拆分的表格（每条事件多少微秒、占比）
2. 与 bench_engine、bench_model 的数字对比：端到端多出来的时间分别花在了哪里
3. 垃圾回收的统计：频率、第 2 代回收的停顿时长，以及它对吞吐和事件循环延迟的影响有多大
4. 事件循环延迟的分布（p50、p99、最大值），以及最长的停顿分别由什么造成（tick、垃圾回收、大请求的同步处理等）
5. 第 4 组：没有内存降级干扰时的最高可持续速率
6. 按预计收益排序的优化方向清单：每一项写明针对哪个阶段、预计能省多少、需要改哪些文件、是否涉及冻结的基础模块、风险。只列方向，不实施
