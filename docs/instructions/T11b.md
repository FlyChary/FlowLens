## 零、子进程输出的编码（先做）

Windows 中文系统的默认编码是 GBK。以文本模式读取子进程输出却不指定编码时，Python 会用 GBK 解码，遇到 UTF-8 的中文日志就报 UnicodeDecodeError，读到的输出变成 None，后续再调用 .strip() 又报 AttributeError。用户已在 conda 环境中设置 PYTHONUTF8=1 作为临时措施，但代码本身也必须改正：
1. 以下 4 处以文本模式调用子进程的地方，都加上 encoding="utf-8", errors="replace"：tests/test_packaging.py 第 54 行附近、tools/experiments.py 第 572 行附近、tools/profile_server.py 第 713 行与第 858 行附近（行号以当前文件为准，用 grep 搜索 text=True 与 universal_newlines 确认没有遗漏）
2. 检查 tools/ 与 tests/ 中所有 open() 读写文本文件的地方，没有指定 encoding 的一律加上 encoding="utf-8"

## 一、归一化未命中的快路径（flowlens/model.py）

1. 字符串中没有 "//" 时，跳过去除 scheme 与主机的正则，也跳过合并连续斜杠的正则
2. 判断路径段是否为 ID：用一个预编译的正则 fullmatch 一次判断（纯数字、UUID、长度不少于 16 的十六进制），替代逐字符的 Python 循环。注意只能匹配 ASCII 字符：用 [0-9] 与 [0-9a-fA-F]，不要用 \d（\d 会匹配其他语言的数字字符，与现有规则不一致）
3. 缓存策略：归一化过程中发生了 ID 段替换时，不把这个原始路径写入缓存（这类路径几乎不会再次出现，写进去只会把能命中的路径挤出去）。在 bench_model 中报告修改前后的命中率
4. 等价性：把修改前的 normalize_url 与 _normalize_url 原样复制进测试作为参考实现，用现有的全部表驱动用例、flowgen 生成的大量随机 URL、以及专门构造的边界（Unicode 数字、全角字符、恰好 15/16 位十六进制、大小写混合的 UUID、截断边界）逐一比较，结果必须完全相同

目标：未命中耗时从约 4.7 μs 降到 1.5 μs 以内。

## 二、校验的列式快路径（flowlens/model.py 的 validate）

1. 先用列表推导一次性取出 event_id、user_id、url、ts、bytes 五列（dict.get），整列做类型与范围检查：字符串列用 type(x) is str 且非空；整数列用 type(x) is int（它天然排除 bool）并检查最小值与最大值；event_id 的长度与 ASCII 检查；元素本身是否为 dict
2. 整块全部合法时走快路径：user_id 只在确实超长时才截断，url 用列表推导调用 normalize_url，直接构造 EventBatch
3. 只要有一条不合法，就退回现有的逐条校验路径（保留现有实现，不要删除）
4. 等价性：把修改前的 validate 复制进测试作为参考实现，用全部合法、各种非法类型混入、空列表、超长 user_id、超大整数、bool 冒充整数、非 dict 元素等情况逐一比较 EventBatch 的每一列与 invalid 计数

目标：全部合法、缓存命中时 validate 从约 1.8 μs/条降到 1 μs 以内。

## 三、写入分块的大小（flowlens/ingest.py）

CHUNK_EVENTS 决定一次同步处理多少条事件：越大，numpy 的固定开销被摊得越薄，吞吐越高；越小，事件循环被占住的时间越短，查询延迟越低。完成第一、二节后，用新的每条耗时重新权衡：
1. 用 bench_engine 与 profile_server 分别测量 1000、2000、5000 三种块大小下的每条 CPU 时间与单块的同步耗时
2. 选择能让单块同步耗时不超过约 15 ms 的最大块，并把选择依据写进 ingest.py 的注释

## 四、垃圾回收调优（flowlens/__main__.py 与 flowlens/ticker.py）

1. 服务启动完成后调用一次 gc.freeze()；Ticker 每隔一段时间（默认 60 秒）再调用一次，把这段时间里新产生的长期存活对象移入永久代，不再参与扫描
2. 适当调高 gc.set_threshold 的第 0 代阈值（例如 10000），减少回收次数；具体数值用实验确定
3. 风险评估：被冻结的对象即使后来变成垃圾也不会被循环回收器回收。在报告中说明这对本服务的影响（服务的数据结构中几乎没有循环引用，被淘汰的秒桶内容靠引用计数释放），并在 60 秒冻结一次的情况下，用 C3 的内存实验参数跑 5 分钟，确认工作集没有因此持续增长
4. 测量第 2 代回收的停顿修改前后的变化

## 五、内存收尾（T9b-B）

背景（C3）：长尾、每秒 3 万条时基本保持第 0 级；但 S4 全随机攻击流量（每秒 3 万条、10 分钟）下工作集在 208～234 MiB 平台化，峰值 243 MiB，进入第 4 级，拒绝了约 14% 的写入。内存"有界"已经成立，本节的目标是把平台压到第 3 级阈值（约 200 MiB）以下，让攻击流量下也不拒绝写入。按顺序做，每一项都在容器中用 S4 的参数验证效果，达到目标就不再做后面的项：

1. 固定 glibc 的大块分配阈值：Dockerfile 的正式镜像加入环境变量 MALLOC_MMAP_THRESHOLD_=131072 与 MALLOC_TRIM_THRESHOLD_=131072。原因：glibc 默认每归还一次大块内存就自动调高"大块"的门槛，几轮之后约 650 KB 的请求体与 numpy 临时数组改从普通堆分配，用完后变成碎片；固定门槛后这类大块用完立即归还操作系统。先用 docker run -e 做对照实验（加与不加），确认有效再写进 Dockerfile，并在注释中写明依据
2. 归一化缓存的上限从 10 万条降到 2 万条（flowlens/model.py 的 NORM_CACHE_CAP）。全随机流量下它约占 10 MiB；第一节完成后带 ID 的路径不再写入缓存，2 万条足以覆盖长尾流量中不带 ID 的全部路径（C1 测得长尾下不同的归一化结果约 1847 个）。用 bench_model 确认长尾流量下命中率没有下降
3. 仅当前两项完成后 S4 仍会进入第 4 级时：把 config.py 中 bloom 字段的默认值改为 BloomConfig(per_gen=1_100_000)（其余参数不变）。依据：dedup.py 把位数向上取到 2 的幂，per_gen 从 200 万降到 110 万后位数从 2^25 降到 2^24，内存从 32 MiB 降到 16 MiB；哈希个数由 12 变为 11。各写入速率下的误判率（每代 10 秒）：每秒 8 万条约 0.03%、11 万条约 0.07%、13 万条约 0.2%、20 万条约 3%。在 config.py 中用注释写明这张表，以及"容量按实测单核处理能力设定"的理由；在 docs/PROGRESS.md 的"已定的决策"中记录用户批准了这一处修改
4. 在 /healthz 中增加 Bloom 当前代的已插入条数与设计容量（只读），便于观察是否接近饱和

## 六、验证

全部在容器中，使用真实的内存读数（不再用假读数），核的分配与之前相同：
1. tools/profile_server.py：每秒 6 万条与每秒 10 万条各一次，报告每条 CPU 时间、分阶段表、事件循环延迟
