# P1c：让解析进程池在 256 MB 内稳定运行

## 目标与背景

用户决定：不再追求每秒 20 万条，而是把 P1 收尾成一个在 256 MB 内稳定运行、吞吐约为单进程两倍的版本，验证后合并进 main 并补发邮件。

P1b 的结论（见 docs/lanes/P1-notes.md §5）：512 MB 下，3 个解析进程、块 10000、两个额度 16 MB，可持续约 12 万条/秒，瓶颈在主进程；但工作集在 12 万档约 277 MB，256 MB 下无法运行。空闲时开 3 个解析进程，工作集就约 152 MB（每个解析进程约 25 MB）。

**验收标准（256 MB，--memory=256m --memory-swap=256m）：**
1. S1：最大可持续吞吐（接受率 ≥ 99%、无拒绝）不低于每秒 9 万条，且在这一档及以下全程第 0 级
2. S4（全随机，每秒 3 万条，10 分钟）：全程第 0 级，接受率 100%，工作集峰值不高于 200 MB
3. S3（长尾，每秒 3 万条，5 分钟）：精度不比已提交版本差（召回 100%、计数误差 < 0.1%、落界率 100%、去重误差约 0.9%、p95 误差约 0.14%）
4. 单核（只给 1 个核）时自动退回单进程路径，S1 与已提交版本一致（约 5 万条/秒）
5. pytest 与 docker build --target test 全部通过

规则：不修改冻结的基础模块；每一步的结果追加到 docs/lanes/P1-notes.md 的新一节"§6 P1c"并提交；命令只打印汇总行。

## 一、内存的四项调整（逐项做，每项做完测一次空闲内存）

先测基线：池关、池开 3 个解析进程，两种配置下启动容器、等 5 秒，读主进程与每个解析进程的 RssAnon 和容器工作集。

1. 限制 numpy 底层库的线程数：Dockerfile 正式镜像加入 OPENBLAS_NUM_THREADS=1、OMP_NUM_THREADS=1、MKL_NUM_THREADS=1，注释写明依据（numpy 自带的 OpenBLAS 导入时按核数创建线程与缓冲区，本服务只用向量运算，用不到多线程矩阵运算）。测量加入后每个进程的 RssAnon 变化
2. 解析进程数默认上限从 3 改为 2：resolve_worker_count 改为 min(2, 可用核数 − 1)，FLOWLENS_PARSE_WORKERS 仍可覆盖。在 parse_pool.py 的注释中写明依据（每个解析进程约多占若干 MB，以第 1 步实测为准；2 个解析进程的解析能力约 20 万条/秒以上，超过主进程的上限，第 3 个没有收益）
3. 额度：进程池开启时，在途额度默认改为 8 MB（单进程路径仍为 4 MB）；原始请求体额度保持 8 MB。依据：同时在途的请求数 = 每秒请求数 × 每个请求占额度的时长，每秒 10 万条约 20 个请求，每个请求占额度约 0.2～0.3 秒，约 4～6 个请求、3～5 MB。两个环境变量仍可覆盖
4. 修复"降级棘轮"：降级控制器进入第 3 级或第 4 级的那一刻（on_change 回调中），立即调用一次 malloc_trim 归还碎片（复用 ticker.py 中已有的实现，非 Linux 平台什么都不做）。依据：第 4 级拒绝写入并不会让内存下降，负载不撤就退不出来；实测一次 malloc_trim 可回收数十 MB。补一个测试：用可控的内存读数让控制器进入第 3 级，断言 malloc_trim 被调用一次

四项都完成后，再测一次空闲内存（池关、池开 2 个），与基线一起列表。

## 二、256 MB 下的验证（tools/s1_measure.py 与 tools/experiments.py）

服务核与压测核的分配沿用 P1b（服务 0,2,4,6，压测用其余物理核上的逻辑核）。确认 WSL 空闲后按顺序运行：

1. S1：4 万、6 万、8 万、10 万、12 万、14 万，每档 20 秒。表格列与 P1b §5 相同，另加"该档内到过的最高降级级别"。找出满足验收标准 1 的最高档
2. S4：全随机，每秒 3 万条，10 分钟。每分钟的工作集峰值与降级级别、接受率、malloc_trim 的调用次数与回收量
3. S3：长尾，每秒 3 万条，5 分钟，与精确解比较
4. S2：混合负载，写入为 S1 最大可持续吞吐的 70%，各类查询的 p50、p99（不作为验收标准，但要报告；预期比已提交版本的 160～173 ms 明显降低）
5. 单核对照：--cpuset-cpus=0，S1 跑 4 万、6 万两档，确认退回单进程路径（解析进程数为 0）且结果与已提交版本一致

如果验收标准 1 或 2 不满足：先看工作集在哪一档越过 200 MB，再尝试把在途额度降到 6 MB、或解析进程数降到 1，并在汇报中写明每种配置的吞吐与内存，不要自行放宽验收标准。
