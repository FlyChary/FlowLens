# C2（支线）：在容器中查清内存增长的原因

## 开始前提

主线的 T10b 必须已经提交并推送。开始前在本工作目录执行 git fetch 与 git merge origin/main，确认包含 T10b 的改动（tools/experiments.py 存在、tools/flowgen.py 生成带路径 ID 的 URL、memstat 使用工作集、Dockerfile 有 test 阶段）。不满足时停下来告诉用户。

## 背景

- 支线 C1 在进程内模拟每秒 3 万条、持续 11 分钟的满载状态：服务常驻增量约 97 MB，加上运行时约 137 MB（54%）
- 主线 T10b 在容器中（docker run --memory=256m）以每秒 3 万条运行 S3：约 90 秒时工作集超过第 3 级阈值，约 200 秒时进入第 4 级，工作集达到约 229 MiB
- 两者相差约 90 MB。本任务的目标是查清这 90 MB 是什么，并找到解决方法

可能的原因（需要用数据区分）：
1. 内存碎片：每个写入请求解析出大量临时 Python 对象，释放后分配器没有把内存还给操作系统，常驻内存只涨不跌
2. 并发请求的瞬时峰值叠加：多个请求同时处于解析阶段
3. 泄漏：某个结构在持续增长，而 C1 的模拟没有覆盖到

## 一、探测脚本：tools/mem_probe.py

在容器内运行（用已构建的正式镜像，把仓库的 tools 目录挂载进去，例如 docker run --memory=256m --memory-swap=256m -v <仓库>/tools:/probe ... python /probe/mem_probe.py）：
1. 在进程内用 create_app 启动真实的服务（与 python -m flowlens 相同的配置，使用真实的 memstat）
2. 每 10 秒采样一次，写成每行一个 JSON：
   - cgroup：memory.current，memory.stat 中的 anon、file、active_file、inactive_file，以及工作集
   - 进程：/proc/self/status 中的 VmRSS 与 RssAnon
   - Python 层：sys.getallocatedblocks()；gc 中对象数量最多的前 10 种类型及数量
   - 每 30 秒一次：用 C1 的 MemWalker 统计引擎各结构与各缓存的总量（记录这次统计本身的耗时，确认它不影响结论）
   - 当时 /healthz 中的降级级别
3. 运行方式作为参数，便于对比：
   - 基线（与生产相同）
   - 环境变量 MALLOC_ARENA_MAX=2
   - 每 10 秒通过 ctypes 调用一次 libc 的 malloc_trim(0)，并记录调用前后的 RssAnon
   - 环境变量 PYTHONMALLOC=malloc（绕过 Python 自己的小对象分配器）

## 二、实验

从 WSL 宿主用 tools/loadgen.py 向容器施压，参数与 T10b 的 S3 相同（长尾、每秒 3 万条、每批 5000 条、4 个进程、每进程 8 个并发连接、持续 5 分钟）。按顺序做：
1. 基线：确认能复现 T10b 的现象（工作集持续上涨、进入第 3 级）
2. 单连接对照：同样的总速率，但只用 1 个进程、1 个并发连接（如果单连接达不到每秒 3 万条，就用它能达到的速率，并同时用这个速率重跑一次基线做对照）
3. 依次运行第一节的另外三种方式

每次实验结束后保存采样文件，下一次实验重新启动容器。

## 三、结论：docs/lanes/C2-report.md

1. 每种运行方式下，工作集、RssAnon、Python 层统计量随时间的变化（可以用文字表格，每分钟一行）
2. 判断属于哪种原因：如果 Python 层统计量平稳而 RssAnon 持续上涨，是碎片；两者一起涨，是泄漏（指出是哪个结构）；只在并发时上涨，是瞬时峰值叠加。也可能是几种原因的组合，请给出各自占多少
3. 与 C1 账本的差距这 90 MB 分别来自哪里
4. 推荐的解决方法，以及它的效果（例如某种运行方式下 5 分钟后的工作集），代价（例如 malloc_trim 每次耗时多少），以及需要修改哪些文件（Dockerfile 的环境变量、服务代码中的定期调用等，由主线实施）
5. 在推荐的方法下，以每秒 3 万条持续 5 分钟，服务是否保持在第 0 级
