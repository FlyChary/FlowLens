## 一、让压测流量更接近真实情况

### 1. 生成的 URL 带路径 ID 与主机名（tools/flowgen.py）

现在的 key 都是 /api/item/x{i}，原始 URL 只在后面加 query 和 fragment，"把路径中的 ID 替换为 {id}"这条归一化规则在压测中没有被覆盖。修改为：
- 一部分 key 的模板本身含有 {id} 段，例如 /api/order/{id}/x{i}、/api/user/{id}/profile/x{i}（比例可配置，默认约一半）
- raw_url 把模板中的 {id} 替换为随机的纯数字、UUID 或长十六进制，并按一定比例加上 scheme 与主机名（https://api.example.com）、query、fragment
- 保持 normalize_url(raw_url(key)) == key，测试覆盖所有变化形式

### 2. 归一化缓存先去掉 query 与 fragment 再查（flowlens/model.py）

缓存现在以原始 URL 为键。真实流量里 query 几乎每次都不同，缓存几乎命中不了，每条事件都要走正则。修改为：先用 str.find 找到第一个 ? 或 #，截掉之后的部分，再用剩下的部分查缓存和归一化。scheme 与主机名的去除仍在缓存未命中时进行。
- 归一化结果必须与修改前完全一致：在 tests/test_model.py 中把修改前的 normalize_url 原样复制为参考实现，用大量随机原始 URL（包括 tests 中现有的全部用例与 flowgen 生成的各种变化）逐一比较
- 修改 tools/bench_model.py：增加"真实流量"一组，原始 URL 由 flowgen 生成（带随机 query 与路径 ID），分别报告修改前后每条的耗时

## 二、实验运行脚本：tools/experiments.py

### 1. 服务的启动方式

- --target docker（默认）：用 docker run --rm --memory=256m --memory-swap=256m 启动镜像，镜像在脚本开始时构建一次（支持传入 PIP_INDEX_URL）。用 --cpuset-cpus 把服务固定在一个 CPU 核上（服务是单线程的，一个核足够），压测进程用 taskset 固定在其他核上，避免互相争抢；把核的分配写进结果
- --target local：在 WSL 中直接用 python -m flowlens 启动，同样做核的隔离
- 每个场景开始前启动一个全新的服务，结束后正常停止，保证场景之间互不影响
- 服务的端口避开 80xx（WSL2 中该段可能被保留），默认 9000

### 2. 场景

- S1 吞吐爬坡：发送速率按阶梯上升（默认 5 万、10 万、15 万、20 万、25 万、30 万，每级 20 秒），每批 5000 条；不压缩与 gzip 各跑一次。每一级记录：实际被接受的速率、503 比例、写入请求延迟的 p50/p95/p99、服务的 CPU 占用（docker stats 或 /proc）、压测进程的 CPU 占用。"最大可持续吞吐"定义为：被接受速率不低于发送速率的 99%、没有 503、写入 p99 低于 500 ms 的最高一级
- S2 混合负载：写入保持在 S1 最大可持续吞吐的 70%，同时运行查询进程：默认窗口 topk（url 与 user）、带随机 at 与 window 的回放 topk、stats，以及 4 个订阅组共 20 个 SSE 订阅，持续 120 秒。按查询类型分别记录延迟的 p50/p95/p99 与次数，对照"查询 p99 < 50 ms"的目标
- S3 精度：按指定分布（本次只跑长尾）以每秒 3 万条运行 5 分钟并存档。运行期间每秒记录一次默认窗口的 topk（url 与 user，k=10）和 stats 的响应，供控制台回放时做"估计与真实对比"；结束时（数据仍在保留期内）随机抽取 200 个已定稿的区间调用 /v1/topk?at=，与精确解比较：召回（并列不算错）、计数相对误差、真实值是否落在 [lower, upper] 内；以及 stats 的去重用户数与 p95 的相对误差
- S5 过载与恢复：以 S1 最大可持续吞吐的 1.5 倍发送 60 秒，然后停止发送再观察 60 秒。记录降级级别随时间的变化、503 比例、内存，以及从停止发送到回到 0 级的恢复时间；检查服务全程没有崩溃
- S4（攻击流量的内存实验）留给 T9，本次不做

### 3. 结果格式

结果写入 results/<日期时间>/<场景>/（results/ 加入 .gitignore）：
- meta.json：git 提交号、机器信息（CPU 型号、核数、内存、操作系统）、服务的启动方式与核的分配、全部参数
- timeline.jsonl：每秒一行，包括发送、接受、拒绝、写入延迟分位数，以及当时 /healthz 的完整内容
- queries.jsonl（S2、S3）：每个查询一行，类型、参数、状态码、延迟
- accuracy.jsonl（S3）：每秒一行的服务响应（默认窗口），以及结束时 200 个抽样区间的比较结果
- summary.json：该场景的汇总数字

把这些文件的字段写成文档 docs/EXPERIMENTS_FORMAT.md，T10c 的控制台回放会直接读取它们。

另外提供 tools/summarize.py：读取一个结果目录，打印各场景的汇总表格（Markdown 格式），便于填进设计文档。

### 4. 测试

- 汇总计算（分位数、最大可持续吞吐的判定、召回）用构造的数据做单元测试
- 一个在进程内启动服务、只跑几秒钟的冒烟测试，验证结果目录与各文件的格式，标记为 slow

## 三、第一次端到端粗测

在 WSL 中用 --target docker 依次运行 S1（不压缩与 gzip）、S2、S3（长尾 5 分钟）、S5，把 tools/summarize.py 的输出放进汇报。并回答：
1. 最大可持续吞吐是多少？离 20 万事件/秒差多少？瓶颈在服务还是压测进程（看两边的 CPU 占用）？
2. 混合负载下各类查询的 p99 是多少？哪一类最慢？是否与每秒的定稿和快照有关（可以对照 timeline 中 tick 的耗时）？
3. 精度实验的召回与误差
4. 过载时降级是否按预期进入和退出，有没有在两级之间反复切换，恢复用了多久

把最大可持续吞吐、各类查询的 p99 追加到 docs/PROGRESS.md 的"基准数据"表，单独成"端到端（Docker 256 MB）"一组。
