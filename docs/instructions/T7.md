## 零、前置小修

1. memstat 的读数选择：只有当前进程所在的 cgroup 设置了内存上限时，才使用 cgroup 的读数，否则使用进程常驻内存（statm）。
   - cgroup v2：读 memory.max，内容为 "max" 视为没有上限
   - cgroup v1：读 memory.limit_in_bytes，数值不小于 2^60 视为没有上限
   - 原因：WSL 里 /sys/fs/cgroup 是整个 Linux 发行版，读到的是所有进程的总和（实测 427 MB，而本进程只有约 109 MB），T8 的降级控制器会因此误判。评测容器用 --memory 启动，一定有上限，读数不受影响
   - 新增 memory_limit_bytes(root="/") -> int | None，没有上限时返回 None；/healthz 增加字段 memory_limit_bytes
   - 补测试：有上限时用 cgroup、没有上限时退回 statm，v1 和 v2 都要覆盖
2. __main__.py 用 argparse 支持 --host（默认 0.0.0.0）和 --port（默认 8080），Dockerfile 里的 --port 8080 才会生效。用 logging.basicConfig 配置日志输出到标准输出（级别 INFO，带时间），启动信息和 PYTHONHASHSEED 警告改用 logging。
3. app 上的键改用 web.AppKey，消除 NotAppKeyWarning。改完后 pytest -q 不应再出现这类警告。
4. app.py 模块文档中"预留在整个请求处理完毕后释放"与代码不符（实际是读完请求体就释放）。代码保持不变，把文档改为实际行为，并说明为什么是安全的：读完后紧接着在 IngestService 里按解压后字节数预留，中间没有让出事件循环，进入处理阶段的请求数量已由在途预留限制。
5. tools/exp/big5mb.bin 从 git 中删除（git rm --cached），加入 .gitignore；实验脚本改为在运行时临时生成这个文件。脚本和 results 目录保留。
6. WSL 的代理来自 WSL 的自动代理功能（autoProxy，会把 Windows 的代理设置同步进 WSL）。不要修改它；实验脚本和以后的压测脚本里设置 NO_PROXY=localhost,127.0.0.1，并在 docs/PROGRESS.md 的"已定的决策"里记一条说明。

## 一、SSE：GET /v1/topk/stream

参数：window、k、by、interval，解析复用 QueryParams（interval 已在 T6b 实现）。不接受 at。

### 1. 帧的时间与内容

- 帧时刻按 interval 对齐到时间网格：T = ⌊now / interval⌋ × interval（服务器时钟，毫秒）
- 每一帧的内容等于 QueryService.topk(d, window, k, at=T) 的结果，即区间 [T − window, T)
- 帧格式：
  ```
  id: <T>
  event: topk
  data: <JSON>

  ```
  data 的 JSON 与 /v1/topk 的响应完全相同。把 /v1/topk 里构造响应字典的代码抽成一个函数，两处共用，不要写两份
- 连接建立后先发 `retry: 3000`；每 15 秒发一行 `: ping` 作为心跳（周期可配置，测试时调小）

### 2. 订阅组与计算量控制（重要）

- 参数相同（by、window、k、interval）的订阅者属于同一个订阅组，共用一个后台任务和同一份计算结果，不能每个订阅者各算一份
- 同一组每秒最多重新计算一次：interval 小于 1 秒时，在同一秒内复用上一次的计算结果，只更新帧时刻 T 和 id。原因：回放每次可能需要几十毫秒，不加限制时，几个 200 ms 间隔、600 s 窗口的订阅就能占满 CPU
- 订阅组最多 8 个，超过时新订阅返回 503 + Retry-After（在开始发送流之前，用正常的 JSON 错误响应）
- 最后一个订阅者离开后，订阅组的任务结束并释放
- 应用关闭时，所有流都正常结束，所有订阅组任务都被取消并等待结束

### 3. 背压与连接上限

- 每个订阅者只有一个"最新帧"位置：用容量为 1 的 asyncio.Queue，满了就先取出旧帧再放入新帧。被丢弃的帧数计入订阅者的计数器
- 每个订阅者有自己的写任务；单次写入超过 5 秒未完成就断开这个订阅者
- 全部订阅者最多 256 个，超过时返回 503 + Retry-After（在开始发送流之前）
- 客户端断开时，及时从订阅组中移除

### 4. 断线重连：Last-Event-ID

- 请求头带 Last-Event-ID 时，解析为毫秒整数 L；格式不对、早于保留期或晚于当前时间时忽略，直接从实时帧开始
- 否则补发 L 之后、到当前为止网格上的每一帧（T = L + interval, L + 2·interval, …），最多补最近的 30 帧，然后接上实时帧
- 补发的帧逐帧调用 QueryService.topk 计算（最终态的区间会命中缓存），帧与帧之间让出一次事件循环
- 补发与实时帧之间 id 必须连续且严格递增，不能重复，也不能出现间隔

### 5. 代码组织

- 新建 flowlens/api/stream.py：订阅组、订阅者、管理器三个类，管理器挂在 app 上（web.AppKey）
- 管理器的上限（组数、连接数）、心跳周期、计算的最小间隔都作为构造参数，默认值即上面的数字，测试时可以调小
- 统计信息（当前组数、订阅者数、累计丢弃帧数）通过 /healthz 的 sse 字段暴露

## 二、测试（新建 tests/e2e/test_stream.py）

用 TestServer 和 aiohttp 客户端读取原始流，自己按行解析 SSE，不引入新依赖。时间相关的测试用较小的 interval（例如 200 ms）和真实的事件循环时间；数据用 FakeClock 驱动的引擎准备。

- 帧格式：id、event、data 三行加空行；data 能被严格的 JSON 解析器解析，字段与 /v1/topk 相同；连接开头有 retry: 3000
- 帧的 id 严格递增、没有重复，相邻 id 之差等于 interval
- 共享计算：两个参数相同的订阅者，后台计算次数与只有一个订阅者时相同（统计 QueryService.topk 的调用次数）
- 计算频率：interval 为 200 ms 时，1 秒内重新计算不超过一次
- 订阅组上限与连接上限：超过时返回 503 + Retry-After，且响应体是 JSON
- 慢客户端：连接后不读取数据，持续数秒，服务端为它保留的帧始终不超过 1 帧，丢弃计数增加，其他订阅者正常收到帧
- 断线重连：带 Last-Event-ID 重连后，补发的帧与之后的实时帧 id 连续；超过 30 帧时只补最近的 30 帧；Last-Event-ID 格式错误或过旧时直接从实时帧开始
- 心跳：调小心跳周期后能收到 : ping
- 客户端断开后订阅者被移除；最后一个离开后订阅组被释放
- 应用关闭时所有流都正常结束
