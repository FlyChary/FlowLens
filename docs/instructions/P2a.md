# P2a：冲刺 20 万条/秒的第 1 步——诊断与准备

## 背景

用户的新目标：达到每秒 20 万条。分两条路线评估，本任务是两条路线共用的第 1 步：
- 放宽内存路线：多进程（前端进程接收请求、引擎进程只写入），需要约 512 MB
- 256 MB 路线：单进程，把每条事件的开销砍到约 4 μs（msgspec 类型化解析、正则归一化、合并写入等）

已知数据（见 docs/lanes/P1-notes.md）：
- 512 MB、进程池 3 个解析进程、块 10000、额度 16 MB：可持续约 12 万条/秒，饱和约 13.4 万；主进程每条约 8.5 μs，是唯一接近跑满的一方；其中写入引擎本身约 2.5 μs，其余约 6 μs 来源不明
- 已提交版本（单进程）：主进程每条约 10.5 μs
- 压测端在 13.4 万条/秒时约用 5.5 个核，要发 20 万条/秒需要 8 个以上，本机不够

**本任务只做诊断与工具，不修改 flowlens/ 下的任何代码。** 结果逐项写进 docs/lanes/P2-notes.md（新建）并提交；命令只打印汇总行。

## 一、剖析主进程（py-spy）

1. 在 WSL 的虚拟环境中安装 py-spy（只作为诊断工具，不加入项目依赖）
2. 容器加 --cap-add SYS_PTRACE；在宿主机上用 docker inspect -f '{{.State.Pid}}' 取主进程的宿主机 PID，用 sudo py-spy record --pid <PID> --duration 30 --rate 200 --format raw（或 speedscope）记录。只剖析主进程，不加 --subprocesses
3. 两组配置，各在稳定运行 30 秒后开始记录：
   - A：lane-c 当前代码，进程池 3 个解析进程、块 10000、两个额度 16 MB、容器 512 MB，每秒 12 万条（长尾）
   - B：已提交版本镜像 flowlens:submitted、单进程、容器 256 MB，每秒 5 万条（长尾）
4. 把主进程的采样按以下类别归类，报告每类占主进程 CPU 的百分比，并换算成每条事件的 μs（类别占比 × 主进程每条耗时）：
   - HTTP：aiohttp 的协议解析、读取请求体、构造与发送响应
   - 事件循环：asyncio 的调度、selector、回调
   - 进程池通信（仅 A）：concurrent.futures、multiprocessing、相关线程
   - 解压、JSON 解析、校验、URL 归一化、哈希（B 在主进程中；A 应基本没有）
   - 写入引擎：ingest_parsed / ingest / _ingest_core，并细分 Bloom、按秒分组、各维度写入
   - tick：定稿（advance）与快照（refresh_snapshot）
   - 垃圾回收、其他
5. 同时报告：主进程的线程数及每个线程的采样占比（py-spy 的 --threads 或按线程统计），用于判断进程池内部线程与事件循环之间争抢全局解释器锁的程度；以及 aiohttp 的访问日志当前是否开启

## 二、改造压测工具，让它能发到 20 万条/秒（tools/loadgen.py）

现在每次发送都要生成事件并序列化，压测端开销太大。增加一个快速模式 --fast：
1. 每个压测进程启动时预先生成若干个（例如 32 个）完整的请求体模板，按指定的分布（长尾）生成，序列化为 JSON 字节
2. 模板中的 ts 写成固定宽度（13 位）的占位数字，event_id 写成"固定宽度的序号占位 + 批内下标"的形式
3. 每次发送前用 bytes.replace 把两个占位分别替换为当前毫秒时间与该进程递增的序号（保证 event_id 全局不重复、ts 在迟到窗口之内）。同一批内事件的 ts 相同，这对吞吐测试没有影响
4. 快速模式不支持存档与精确解对比（这两项仍用原来的模式），在帮助文本中写明
5. 验证：用快速模式发送一段时间后，服务的 deduped 为 0、late 为 0、invalid 为 0
6. 报告改造前后，压测端每发送一条事件的 CPU 时间（压测进程 CPU 秒 ÷ 发送条数），以及在本机分配给压测的核上，快速模式最多能发到每秒多少条

## 三、msgspec 的实际收益（只做基准测试，不修改服务）

在虚拟环境中安装 msgspec（不加入项目依赖），新建 tools/bench_parse.py：
1. 用 flowgen 生成长尾与全随机两种请求体（每批 5000 条）
2. 对比两种做法每条事件的耗时与解析时的内存峰值（tracemalloc）：
   - 现有：orjson 解析为字典列表 + validate（含归一化）
   - msgspec：定义 Event 结构体（msgspec.Struct，gc=False），用 msgspec.json.Decoder(list[Event]) 解析，再用列表推导取出各列、做 validate 中剩余的检查（长度、范围、截断）与归一化
3. 再单独测一项：URL 归一化中"ID 段替换"改用一个预编译正则一次 sub 完成，对比现有实现的耗时；并用 tests/test_model.py 中的参考实现做等价性检查，报告是否存在不一致的输入（只报告，不修改服务）
