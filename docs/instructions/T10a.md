T10 拆成三步：T10a 工具（本任务）、T10b 实验场景与第一次端到端粗测、T10c 调试接口与控制台页面（界面参考 docs/prototype/console.html）。请先在 docs/PROGRESS.md 的任务列表中把 T10 拆成这三行。

约束：不得修改冻结的基础模块；不引入新依赖（只用标准库、numpy、orjson、aiohttp）；工具代码放在 tools/，但可复用的逻辑写成可导入的模块（例如 tools/flowgen.py、tools/exact.py），命令行入口只做参数解析。

## 一、数据生成与发送：tools/loadgen.py（及可导入的生成模块）

### 1. 事件生成（确定性）

- 同一个随机种子、同一组参数，生成的事件序列完全相同
- 三种分布：
  - 长尾：URL 2 万个，按 Zipf（s = 1.1）抽取；用户 20 万个，按 Zipf（s = 0.9）抽取
  - 接近均匀：URL 2 万个、用户 20 万个，均匀抽取
  - 全随机：每个事件的 URL 和用户都不重复（编号单调递增）
- URL 与用户都用整数编号表示，字符串由编号确定性生成：
  - key_of(i)：归一化后的 URL，例如 /api/item/x{i}
  - raw_of(i, rng)：发送时使用的原始 URL，在 key_of(i) 的基础上随机加入 query、fragment、纯数字段或 UUID 段等变化，归一化后必须等于 key_of(i)
  - user_of(i)：用户 ID
- bytes 用对数正态分布生成（p95 约 1 万字节量级），为整数
- 可配置比例：批内重复、跨批重复（重发之前发过的 event_id）、迟到、未来、非法事件（缺字段、类型错误等）
- 时间戳：正常事件的 ts 为发送时刻往前 0～3 秒的随机值（带乱序）；迟到事件为发送时刻往前 61～120 秒；未来事件为发送时刻往后 6～30 秒。必须避开判定边界（60 秒、5 秒）附近 ±0.5 秒，保证服务按收到时刻判定、精确解按发送时刻判定时结论一致

### 2. 发送

- 多进程：--workers N 个进程，每个进程内 --conc C 个并发连接（aiohttp 客户端，trust_env=False，避免走 WSL 的自动代理）
- 速率控制：--rate 总速率（事件/秒），平均分给各进程，用令牌桶控制；--batch 每批事件数（默认 5000）；--duration 持续秒数；--gzip 是否压缩（压缩级别 1，减少客户端 CPU）
- 请求体在发送前即时生成（时间戳必须是发送时刻），用 orjson 序列化
- 收到 503 时按 Retry-After 等待后重发同一批（同样的 event_id），重试次数可配置
- 每秒向标准输出打印一行 JSON：本秒发送、被接受（202）、被拒绝（503）、其他错误的事件数，以及请求延迟的 p50、p95、p99；结束时打印一行汇总 JSON。T10b 和控制台都会读取这些输出
- 记录客户端自身的 CPU 占用，写进汇总，用来判断压测工具是否成了瓶颈

### 3. 存档

- --archive DIR 时，把每个被服务接受（202）的批次的事件存档，只存整数列：event_id（int64）、ts（int64）、url 编号（int32）、user 编号（int32）、bytes（int32）、sent_ms（int64，该批的发送时刻）、事件类型（int8：正常、迟到、未来、非法）
- 按时间切分成多个 .npz 文件；附一个 meta.json，记录种子、分布、全部参数，以及生成 key 的规则版本
- 被 503 拒绝的批次不存档（服务没有接受它们）；重发成功时按重发那一次存档

## 二、离线精确解：tools/exact.py

- 读入存档，按服务的规则得到"被接受的事件集合"：去掉非法与未来事件；按 sent_ms 判定迟到并去掉；按 event_id 去重（保留第一次出现）
- 按 ts 排序后建立索引，支持任意毫秒区间 [from_ms, to_ms) 的查询：
  - topk(by, from_ms, to_ms, k)：精确的前 k 名及次数，并列时按 key 字典序（与服务一致）
  - distinct_users(from_ms, to_ms)
  - quantile_bytes(from_ms, to_ms, q)：精确分位数，口径与 DDSketch 的定义一致（按秩取值，写清楚用的是哪种定义）
- 提供 compare(service_answer, exact_answer) 辅助函数，计算：召回（并列不算错：返回的 key 的真实次数不小于精确答案第 k 名的次数即算命中）、计数相对误差、真实值是否落在 [lower, upper] 内
- 命令行：给定存档目录和区间，打印精确答案

## 三、边界用例（题目要求的自测脚本）

两种形式，用例相同：
- tests/e2e/test_boundaries.py：进程内启动服务，pytest 运行
- tools/selftest.py：对一个正在运行的服务地址（--url）逐项检查，打印"用例 / 期望 / 实际 / 通过与否"的表格，最后给出通过数；任何一项失败时退出码非 0

至少覆盖以下用例：
1. 空数组：202，各计数为 0
2. 非法 JSON：400
3. 顶层不是数组：400
4. 部分事件非法：202，invalid 计数正确，其余事件被接受
5. 批内重复：deduped 计数正确
6. 跨批重复：第二次全部计为 deduped
7. 迟到事件：late 计数正确
8. 未来事件：计入 invalid
9. gzip 请求体：正常写入
10. 解压炸弹：413
11. Content-Length 超过 4 MB：413，且服务端不读取请求体
12. 不支持的 Content-Encoding：415
13. at 早于保留期：422
14. 参数越界（k=0、k=101、window=700s、by=foo）：400
15. 对 /v1/topk 发 POST：405，响应体是 JSON
16. 不存在的路径：404，响应体是 JSON
17. 区间内没有数据时 /v1/stats：approx_p95_bytes 为 null，响应能被严格的 JSON 解析器解析
18. SSE：收到格式正确的帧；带 Last-Event-ID 重连后 id 连续

## 四、工具自身的测试（tests/test_tools.py）

- 生成的确定性：同一种子两次生成的结果完全相同
- 分布特征：长尾下前 10 个 URL 的占比明显高于均匀；全随机下没有重复
- raw_of 的归一化：对大量随机样本，flowlens.model.normalize_url(raw_of(i, rng)) 都等于 key_of(i)
- 迟到、未来事件的时间戳都避开了判定边界附近 ±0.5 秒
- 存档的写入与读取结果一致
- 精确解的正确性：在一份小数据上，与最朴素的逐条计数实现逐项比较 topk、distinct_users、quantile_bytes，包括带毫秒边界的区间
- compare 的召回口径：构造并列的情况，验证并列不算错
- 发送器：用测试里启动的服务，验证 503 后按 Retry-After 重发、重发成功的批次被存档、每秒输出的 JSON 格式正确
