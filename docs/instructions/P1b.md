## 二、已知结论（不需要重新验证）

检查点一（提交 627b206）已审查通过：解析进程池、引擎写入核心拆分、写入信号量、块大小 2000。

S1 多核对照（服务用逻辑核 0,2,4,6，压测用其余 8 个逻辑核，默认额度：在途 4 MB、原始请求体 8 MB）：

| 发送率 | 池开 接受率 | 池开 主进程 CPU | 池关 接受率 | 池关 主进程 CPU |
|---|---|---|---|---|
| 4 万 | 98% | 26% | 100% | 43% |
| 6 万 | 96% | 35% | 约 99% | 61% |
| 8 万 | 80% | 39% | 87% | 97% |
| 10 万 | 56% | 64% | 75% | 95% |

结论（由审查方给出）：
- 用"主进程 CPU ÷ 实际接受条数"计算主进程每条开销：池开约 6.3 μs（4 万、6 万两档），池关约 10.5 μs。进程池把主进程每条开销降低了约 40%，有正收益
- 池开时主进程 CPU 从未跑满，却在拒绝请求，原因是额度：请求在等待解析结果、等待写入信号量期间一直占着额度，同时在途的请求数 = 每秒到达的请求数 × 每个请求占额度的时长，超过了额度上限。被拒后 loadgen 按 Retry-After 等 1 秒，发送速率塌陷
- 上一次统计拒绝来源的运行中，全程累计：在途额度拒绝 455 次、原始请求体额度拒绝 173 次。两个额度都在拒绝请求
- 该次运行的逐档数据不可信：出现"每秒接受 0 条"、计数器增量为负数，说明测量脚本有缺陷（可能每档重启了容器导致计数器清零，或采样窗口没有对齐）

## 二点五、审查方的代码分析与实测（重要，决定下一步怎么做）

审查方在本地逐项实测了进程池模式下每一步的耗时（长尾，每批 5000 条）：
- 解析进程 parse_body：3.4 μs/条
- 主进程把请求体 pickle 发给子进程：0.01 μs/条；反序列化解析结果：0.09 μs/条。跨进程传输可以忽略，不是瓶颈
- 主进程 ingest_parsed 的耗时严重依赖块大小（每块有按秒分组、逐维度去重统计、numpy 调用、筛选候选等固定开销）：

| 每块条数 | 每条耗时 | 单块同步耗时 |
|---|---|---|
| 1000 | 4.44 μs | 4.4 ms |
| 2000（当前） | 2.98 μs | 6.0 ms |
| 5000 | 2.16 μs | 10.8 ms |
| 10000 | 1.88 μs | 18.8 ms |
| 20000 | 1.69 μs | 33.8 ms |

按用户机器约慢 1.35 倍换算，块 2000 时主进程每条约 6.2 μs（写入 5.2 + tick 与 HTTP 约 1），与容器实测的约 6.3 μs 吻合。块改为 10000 后主进程每条约 3.5～4 μs，上限约 25～28 万条/秒。有写入信号量，同一时刻只写一块，查询最多等一块（块 10000 约 25 ms），仍在 50 ms 以内。

所以进程池路径的块大小改为 10000（新增常量 POOLED_CHUNK_EVENTS = 10000，只用于进程池路径；单进程路径的块大小另行决定，本任务不改）。

## 三、要做的事

### 1. 修好测量方法，并用已知结果校验
- 整个爬坡过程只启动一个容器，不在档位之间重启
- 在每一档开始与结束的时刻各读一次 /healthz，用差值计算该档的接受条数、在途额度拒绝次数、原始请求体额度拒绝次数；同时用 loadgen 每秒输出的数据计算该档的发送与接受，两者交叉核对（差别超过 5% 时在汇报中说明）
- 每档的主进程 CPU、解析进程合计 CPU、压测进程合计 CPU 用该档时间窗口内的 CPU 时间增量计算（/proc/<pid>/stat），不要用瞬时值
- 先用"池关、默认额度"跑一遍（4 万、6 万、8 万三档即可）作为校验：结果应与上表池关列接近（6 万档接受率约 99%、8 万档主进程 CPU 约 97%）。不接近就先修脚本，不要继续
