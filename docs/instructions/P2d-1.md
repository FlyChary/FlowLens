# P2d-1：前端进程架构（第一步：进程模型、写入通道、转发）

## 目标

把主进程身上"不必由单写者来做"的工作全部搬走：多个前端进程共同监听对外端口，自己接收并解析写入请求，把紧凑的结果发给引擎进程；其他请求原样转发给引擎。引擎进程只负责去重、写入统计结构、tick、降级控制与查询计算。

本任务分三步，这是第一步。第二步（P2d-2）做快照广播、前端直接回答默认窗口查询、前端分块解析；第三步（P2d-3）做完整验证。

依据（docs/lanes/P2-notes.md）：P2c 中 512 MB、20 万条/秒、10 分钟，主进程 CPU 约 95%，因在途额度占用升高进入第 1、2 级降级；可持续约 18.7 万条/秒。P2b 剖析中主进程有约 12% 在进程池通信、约 12% 在 HTTP、约 15% 在事件循环。

## 规则

- 不修改冻结的基础模块（dedup.py 已重新冻结）
- 必须保持的语义：在途额度在解析之前预留；去重只在引擎里做；第 4 级在读取请求体之前拒绝；单条不合法只计入 invalid；所有对外的 HTTP 语义（状态码、错误格式、头部）与单进程模式完全一致
- 前端数为 0 时（单核、内存上限不足、非 Linux、或用环境变量禁用），行为与现在的单进程模式完全相同
- 每完成一节就提交一次；结果与决策追加进 docs/lanes/P2-notes.md 的新一节"P2d-1"

## 一、进程模型（flowlens/__main__.py、新建 flowlens/supervisor.py）

1. 主进程就是引擎进程。启动顺序：计算前端数 → 用 spawn 上下文启动前端进程（在创建引擎之前，避免继承大块内存）→ 创建引擎与引擎的 HTTP 应用 → 开始监听写入通道与内部查询套接字 → 等待各前端报告就绪
2. 前端数的计算（新函数 resolve_front_count）：
   - 非 Linux（没有 SO_REUSEPORT）→ 0
   - 可用核数（沿用 parse_pool 中按 sched_getaffinity 与 cgroup cpu.max 计算的方法）小于 2 → 0
   - cgroup 内存上限低于 384 MB → 0（依据：P2c 第四节，256 MB 下多进程反而更差）；没有上限时视为足够
   - 否则 min(3, 可用核数 − 1)
   - 环境变量 FLOWLENS_FRONTENDS 可覆盖（0 表示禁用）
   - 启动日志中打印前端数及其原因
3. 前端数大于 0 时，不再使用 ParsePool（前端自己解析）。parse_body 等解析函数保留，供前端调用；ParsePool 的进程池部分如果不再被任何代码使用，就删除，并删除对应的测试
4. 进程管理：引擎每秒检查一次前端进程，意外退出的就重新拉起；收到 SIGTERM 时，先向所有前端发送 SIGTERM 并等待其退出（最多 3 秒，超时则 SIGKILL），再关闭自己。前端发现与引擎的连接断开时，立即退出

## 二、写入通道（新建 flowlens/ipc.py、flowlens/frontend.py、引擎侧的通道处理）

1. 每个前端与引擎之间一条 Unix 域套接字的长连接（套接字文件放在临时目录，路径由引擎传给前端）。消息格式：4 字节长度 + 1 字节类型 + 负载（pickle 协议 5）。类型至少包括：
   - BATCH（前端 → 引擎）：请求编号 + 解析结果
   - ACK（引擎 → 前端）：请求编号 + accepted、deduped、late、invalid，或一个错误码
2. 解析结果的编码：ts、nbytes、三列哈希为 numpy 数组；url 与 user 各自只传本批中不重复的字符串列表，再加一个 int32 下标数组。前端用字典完成本批去重。引擎收到后只对不重复的字符串做驻留，再用下标数组还原出每条事件对应的字符串对象
3. 引擎侧：每条连接一个读取协程，在事件循环中读取（不使用额外线程）。收到 BATCH 后，在现有的写入信号量保护下，按 POOLED_CHUNK_EVENTS 分块调用写入核心（与 ingest_parsed 共用同一份代码，不要复制），块间让出事件循环，完成后回复 ACK
4. 前端处理 POST /v1/ingest 的顺序（与单进程模式一致）：
   - 读取共享的降级级别，第 4 级时在读取请求体之前返回 503
   - 原始请求体额度（总额度按前端数平均分配）→ 读取请求体 → 解压
   - 在途额度（总额度按前端数平均分配；第 3 级时减半）→ 预留不到则 503
   - 解析（load_array、validate、三列哈希）→ 发送 BATCH → 等待 ACK → 释放在途额度 → 返回 202 与计数
   - 与引擎的连接异常时返回 503（此时尚未去重，重试安全）
5. 共享状态（multiprocessing 的 Value 与 Array，由引擎创建并传给前端）：
   - 降级级别、是否收紧额度：引擎写，前端读
   - 每个前端当前已预留的在途字节数、原始体字节数，以及两种拒绝的累计次数：前端写，引擎读。引擎的降级控制器用各前端在途字节之和计算占用率；/healthz 中的拒绝计数为各前端之和加引擎自身

## 三、转发（flowlens/frontend.py）

1. 前端收到 POST /v1/ingest 以外的任何请求（包括不存在的路径、不支持的方法），都原样转发给引擎：引擎额外在一个 Unix 域套接字上运行现有的 HTTP 应用（web.UnixSite），前端用 aiohttp 的 UnixConnector 连接它
2. 转发时保留方法、路径与查询参数、请求头（至少 Last-Event-ID、Accept）；返回时保留状态码与响应头（至少 Content-Type、Retry-After、Cache-Control），响应体边收边发，不缓存整体
3. SSE：前端用 StreamResponse 逐块转发；客户端断开时关闭对引擎的连接；引擎结束流时前端也结束
4. 引擎的 HTTP 应用在前端模式下不对外监听，只在内部套接字上服务；单进程模式下照常对外监听（包括写入路由）

## 四、测试

1. 单元测试：消息分帧的编解码（含被拆成多段到达的消息）；解析结果的编码与还原（不重复字符串加下标，还原后与原始列表逐项相同）；resolve_front_count 的各分支
2. 端到端测试（非 Linux 平台跳过），用子进程启动真实服务、2 个前端：
   - 写入后，/healthz 的 events_ingested 正确
   - 同一组请求分别写入"前端模式"与"单进程模式"的服务，同一区间的 topk（url 与 user）、stats 逐项相同
   - 状态码与错误格式：400、404、405、413、415、422、503 与单进程模式一致
   - SSE 经过前端转发：能收到帧；断开后带 Last-Event-ID 重连，id 连续、不重发
   - 第 4 级时前端在读取请求体之前拒绝（用可控的内存读数让引擎进入第 4 级）
   - SIGTERM 后几秒内全部进程退出，没有残留；杀掉一个前端后，引擎在几秒内重新拉起它，写入恢复正常
3. 用 tools/selftest.py 对前端模式的服务运行全部边界用例，必须全部通过

## 五、初步性能检查（不是验收）

512 MB、3 个前端、两个额度 16 MB，快速压测模式，tools/s1_measure.py 跑 12 万、16 万、20 万、24 万四档（每档 20 秒）。s1_measure 需要能统计引擎进程与各前端进程的 CPU（前端是引擎的子进程，沿用按父进程号查找的方法，排除 resource_tracker）。每档报告：接受率、引擎进程 CPU%、引擎每条 μs、前端合计 CPU%、工作集峰值、最高降级级别；与 P2b 第四节（进程池）的同档数据对照。另报告空闲时引擎与每个前端的 RssAnon。
