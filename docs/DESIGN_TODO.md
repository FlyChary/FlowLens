# 设计文档待改项（最终测试完成后统一修改）

1. 写入上限（§3.1、架构图左栏"gzip 解码"一步）：压缩体与解压后上限由 8 MB / 64 MB 改为 4 MB / 4 MB。在途预留改为按解压后字节数（上限 4 MB），在解析和去重之前完成。原因：orjson 解析后的对象约为原始 JSON 的 3.4 倍，64 MB 的请求解析后约 215 MB。
2. 降级触发条件（§3.6 表格）："在途事件"改为"在途字节"。
3. 内存预算（§5）："在途写入（上限 10 万条）约 20 MB"改为"在途写入（解压后 4 MB，解析后约 14 MB）约 20 MB"。
4. 回放的 Top-K（§3.5、图 4 下半部分）：实现已不再做门槛剪枝，改为按点估计选出前 K 个，只对它们用 Count-Min 收紧上界。门槛剪枝的论证保留，作为"为什么其余候选不必精算"的说明；图 4 下半部分的标题相应修改。
5. 快照与 tick（§3.5、架构图"运行模型"卡片）：tick 分为定稿与刷新快照两段，快照按维度分段，段间让出事件循环。
6. 性能数据（§4、§8）：用最终压测结果替换"单核约 25 万条/秒"等估算，补充快照与定稿耗时。
7. 实验结果（§7 待补实验表）：T10 完成后填入。
8. 原始请求体（压缩后）上限（§3.1、§5 内存预算）：原始请求体额度定为 8 MB，而非第 1 条的 4 MB。这会抬高写入路径的最坏内存：从约 20 MB 增到约 28 MB（+8 MB 压缩体）。
9. Expect: 100-continue 拒绝（§3.1 写入路径）：DESIGN 未描述 Expect 处理。实现为 POST /v1/ingest 注册自定义 expect_handler：Content-Length>4 MB 直接回 413、RawBudget 预留不下回 503+Retry-After:1，两种情况都不发 100 Continue，客户端在发送请求体前就被拒，避免超大请求体在途。建议在设计里补一句"大请求体可先经 Expect: 100-continue 在发体前拒绝"。
10. lingering_time 与连接关闭（§3.1 写入路径/运行模型）：DESIGN 未描述服务端关闭连接的行为。实现定为 `lingering_time=1`：413/503 响应在关连接前已发出，lingering 只控制关连接前是否读完在途请求体。定为 0 时，"不发 Expect 直接灌大请求体"的客户端会偶发收到 RST 而非 413（服务端发完 413 立即关连接、客户端还在发送）。建议在设计里补一句"超限请求的 413 立即返回；服务端 linger 1 秒读完在途体再干净关连接，避免 RST"。
11. 保留期判定口径（§3.1 保留期、§3.5 回放查询）：DESIGN 只说"at 早于保留期 422"。实现把"可查范围"定为 `now − retention − 迟到上限`（`engine._plan`，`LATENESS_MS` 常量），而非 `now − retention`：线段树保留"最新定稿秒往前 retention 秒"，最新定稿秒约 now−迟到上限，所以能查到比 now−retention 更早的数据。若按 now−retention 判定，window=600s 的查询与 SSE 长窗口帧会大量误报 422。建议在设计里把"可查范围"明确写成"最新定稿秒（约 now−60s）往前 10 分钟"。
12. SSE 帧 data.to 与 id 的关系（§3.7 SSE）：帧的 id 是帧时刻 T，但 data 是 `topk(at=T)` 的结果，其 to 等于实际计算那一帧的时刻。interval 大于等于 1 秒时每帧都重算，`data.to == id`；interval 小于 1 秒时同一秒的多个帧复用上一份计算结果（只更新帧时刻、不重算），`data.to` 可能比 `id` 早不到 1 秒（from/to 保持实际计算时的值，不改写）。建议在设计里注明"SSE 帧的 data.to 不一定等于 id，最多差 min_recompute（默认 1 秒）"。
13. 第 3 级降级动作（§3.6 表格"内存 > 200 MB → 缩短历史保留，收紧并发"）：实现改为**收紧额度（Admission 4→2 MB、RawBudget 8→4 MB）+ 拒绝新 SSE 订阅 + 清一次结果缓存与 URL 归一化缓存**，不做"缩短历史保留"。原因：保留时长由冻结的 `segtree.py` 在构造时确定（`TreeConfig.retention_sec`），运行期无法动态调整；且缩短保留会直接丢历史数据，比降精度更伤，不适合放在"过载降级"这一档。建议设计把第 3 级动作改成"收紧在途/原始体额度、拒绝新 SSE 订阅、清缓存"。
14. 采样期间上下界不再是严格保证（§3.6 第 2 级、§4 误差表）：第 2 级起 Top-K 名单与 url p95 按 `1/sample_weight` 采样、每条以权重 `sample_weight` 计入，是无偏估计（期望 = 真实值），但**单个 key 的上下界在采样下不再严格夹住真实次数**（采样方差可能让加权估计偏离真实值）。建议在设计里注明：采样生效时（`sample_rate < 1`，见 `/v1/topk` 与 SSE 帧的 `sample_rate` 字段）返回的 `count`/`err` 为加权估计、上下界为近似，非采样时（`sample_rate` 缺省）为严格保证。HLL 去重人数与 event_id 去重不受采样影响、始终全量。
15. 第 3 级期间 2~4 MB 请求返回 503 而非 413（§3.6 第 3 级、§3.1 写入错误码）：第 3 级把在途上限从 4 MB 收紧到 2 MB，这期间解压后 2~4 MB 的请求在**预留阶段**就放不下、收到 503 + Retry-After，而不是超过单请求上限的 413。这是**有意的、暂时性的**：退出第 3 级后额度恢复、同样大小的请求即可成功。503 的错误信息说明"降级期间单个请求的上限暂时为 2 MB，请稍后重试"，让调用方知道是临时限制、该重试而非拆小。建议在设计里注明第 3 级的这个语义（"超限"与"过载"两码并存：>4 MB 恒 413；2~4 MB 仅在第 3 级时 503）。
16. `/v1/stats` 支持 `at` 参数（§3.5、§6）：原实现 `/v1/stats` 只接受 `window`（默认窗口恒读快照）。实现改为与 `/v1/topk` 同口径：不带 `at` 且 window=60s 时读快照；带 `at`（或非 60s 窗口）时走回放合并概要，`at` 早于保留期同样 422、第 1 级降级同样暂停。原因：边界用例"区间内没有数据时 approx_p95_bytes 为 null"需要对**已运行（默认窗口有数据）**的服务验证，必须能指向一个无数据的过去区间；/v1/topk 本来就支持 at，两者口径保持一致。建议在设计里给 /v1/stats 补一句"同样支持 at 回放"。
17. 边界用例从 14 条扩为 18 条（§7）：T10a 指令列出的 18 条全部实现（14 条 + gzip、解压炸弹、SSE 重连、区间无数据 p95 为 null 等），两种形式（pytest 进程内 / selftest 对运行中服务）共用同一套用例定义（tools/boundary_cases.py）。建议把设计文档"自测脚本覆盖 14 个边界用例"更新为实际条数。
18. 离线精确解的迟到判定口径（§7）：exact.py 按存档里的 **sent_ms**（该批的发送时刻）判迟到（ts < sent_ms − 60s），而不是存档读取时刻。loadgen 的时间戳已避开判定边界 ±0.5 秒（迟到 61.5~119.5s、未来 5.5~30s），"服务按收到时刻判定、精确解按发送时刻判定"两种口径结论一致。建议在设计里注明离线对照的这条口径。
19. 内存读数改用工作集（§3.6 降级阈值、§5 内存预算）：降级判断与 `/healthz` 的 `memory_bytes` 改为**工作集** = `memory.current` − `memory.stat` 的 `inactive_file`（cgroup v1 为 `memory.usage_in_bytes` − `total_inactive_file`）；`/healthz` 另加 `memory_current_bytes` 保留原始读数。原因：实测容器（--memory=256m）空闲 `memory.current` ≈ 169 MiB 里约 60 MiB 是不活跃页缓存（可被内核优先回收、不致 OOM），原口径让降级控制器虚高（空闲即 66%，稍有负载就进第 3 级）。改后口径与 docker stats、K8s 驱逐判断一致，空闲工作集 ≈ 108 MiB（42%）、5 万/秒写入 30 秒后 ≈ 184 MiB（72%）。建议设计把 §3.6 的"内存 > 200/230 MB"阈值与 §5 预算里的"内存"明确为**工作集（扣除不活跃文件缓存）**，并说明 `/healthz` 两个字段的口径。
20. 持续写入下的内存增长超预算（§5 内存预算、§3.6 降级）：T10b 端到端（Docker 256 MB）实测，**内存随持续写入填满 600s 保留期而增长、且不回落**——3 万/秒×5 分钟（累积 588 万条）后工作集 ~218 MiB、服务长期贴在第 3~4 级（进 3 级 @90s、进 4 级 @200s）。**已由支线 C2（调查）+ C3（加固）解决**：原因是"分配器保留已释放页（碎片）+ 并发瞬时峰值叠加"（非泄漏），用 malloc_trim + 字符串驻留 + glibc mmap/trim 阈值固化（ENV）后，3 万/秒满载全程第 0 级、接受率 100%（见第 24 条）。**§5 内存预算需据实重写**（见第 22 条）。
21. 写入接口同时接受 JSON 数组与 NDJSON（§3.1、§6、§7）：题目 1.1 节写"事件格式（NDJSON，每行一条）"、1.2 节写"body 为事件数组"，评测方压测脚本可能直接把 NDJSON 文件作为请求体发来。实现（F2）改为：跳过开头空白后第一个字节是 `[` 时按 JSON 数组解析（现有路径，行为与性能不变）；否则按 NDJSON 解析（按换行切分、跳过空行、每行 orjson 解析一个元素、行尾 `\r\n` 兼容），某一行不是合法 JSON 时放占位值、由 validate 计为 invalid 不影响其他行；整个请求体既不是数组、也没有任何一行是合法 JSON 时才返回 400。**单个 JSON 对象不再是 400**（按一行 NDJSON 处理，字段不全则计 invalid）。建议在设计里把"请求体格式"明确写成"JSON 数组或 NDJSON（每行一条）"。
22. 内存预算按实测重写（§5，C1 账本 + C2/C3 容器实测）：设计 §5 的逐项估算与实测偏差较大（C1-report §3）：① "字符串表上限 13 MB"是伪命题——没有独立字符串表，key 字符串分散在各名单（长尾满载约 2~4 MB，T10b 后 url 共享），且写入端已有驻留表（见第 25 条）；② "在途写入 20 MB"低估了 orjson 解析的**瞬时膨胀**（实测单 4 MB 请求解析峰值 +60~67 MB、请求结束即释放）——这是"满载 + 单个 4 MB 大请求在途"最坏瞬时压到 78% 第 3 级阈值的主因；③ 线段树低估了 HLL（759 实例 × 16 KB = 11.9 MB，叶子 600 + 各层节点 + 构建中，与流量无关、不可压缩）。C2 把"容器里 3 万/秒满载 256 MiB 工作集"拆成实测分量（空载基线 ~83 + 存活结构 ~40 增长 + 非存活 churn 保留 ~100，见 C2-report §3），建议按此替换"估算 195 MB"的逐项数字，并标注测量方法（`tools/mem_probe.py` 容器 256 MB 实测）。
23. §3.6/§3.7 过载降级：满载 + 32 连接时工作集 ~89%、长期贴 3~4 级，**是预期行为（自我保护），不是故障**（C1 §2 的"最坏瞬时"被 C2 证实）。加固（C3）后 g5 组合全程第 0 级；但"负载后常驻高水位不回落"（碎片）需靠定期 `malloc_trim` 削（负载回落后的常驻会下移 ~60 MiB）。建议补一句说明。
24. glibc mmap/trim 阈值固化进镜像（§3.1/§5/部署说明，C3 实测）：C3 实测 `MALLOC_MMAP_THRESHOLD_=131072` + `MALLOC_TRIM_THRESHOLD_=131072` 使满载峰值 −57.7 MiB（−24%）、从"贴 3/4 级"变**全程第 0 级**。机制：glibc 默认每次归还大块后自动调高"大块"门槛，几轮后 ~650 KB 请求体改从普通堆分配、用完变碎片；固定 128 KB 门槛让这类大块走 mmap、free 即还 OS。已批准在 Dockerfile base 阶段加这两个 `ENV`（`docker run` 不显式 `-e` 也继承、评测容器自动生效）。建议设计补一句"部署时固定 glibc 大块/trim 门槛为 128 KB（Dockerfile ENV）"及依据。
25. 字符串驻留表（§3.1 写入路径、§5 内存预算，C1/C3）：把 §5"字符串表 13 MB"（伪命题，见第 22 条）改为"**有上限、满则整体清空**的驻留表（user 8192 / url 32768，`flowlens/intern.py` 的 `Intern`），写入端驻留（user 在 `engine.ingest` 写秒桶前、url 在 `model.normalize_url` 返回前）、不进 config.py"。与归一化缓存分工：归一化缓存命中时已复用同一 url 对象，驻留补齐"缓存未命中（新路径）"的部分；表自身内存被 cap 钉死（对抗性流量下内存有界的一环）。另：`/healthz` 响应字段清单补 `malloc_trim`（call_count / last_ms / total_freed_mb 等）。
26. 容器部署与信号处理（对应运维章节/§6，B1b）：容器 PID 1 是服务进程（`CMD ["python", "-m flowlens"]`）、`__main__.py` 已处理 SIGTERM/SIGINT（`loop.add_signal_handler`）、`docker stop` 干净退出（退出码 0）；Docker 用 `pip install -c constraints.txt .` 装完删源码、运行时从 site-packages import（与 CWD 无关）、非 root、`HEALTHCHECK` 用标准库。建议补"容器部署与信号处理"一节。

29. 进程池与单写者（§3.2 运行模型，P1/P1c）：补"解析进程池"——**统计状态仍只在主进程（单写者、无锁不变）**，可并行的纯计算（validate 含归一化、三列 64 位哈希，约 9.5 μs/条）放进 `parse_pool.py`（spawn 上下文、每请求一个 ParsedBatch、主进程按块串行写引擎）。worker 数默认 `min(2, 可用核数−1)`（`FLOWLENS_PARSE_WORKERS` 覆盖、夹 [0,3]）；核数 <2 自动退回单进程路径（单核实测解析进程数 0）。主进程保留 classify/Bloom 去重/采样/写桶/tick（约 3.5 μs/条）。依据与实测见 P1-notes §4–§6。
30. 在途额度与写入块大小（§3.1 写入路径）：在途额度分两档——**单进程路径 4 MB（不变）；进程池开启时默认 8 MB**（`ingest.POOLED_PENDING_BYTES`，`FLOWLENS_MAX_PENDING_BYTES` 可覆盖两者；依据：10 万条/秒约 20 个在途请求 × 占额度 0.2~0.3 秒 ≈ 3~5 MB，8 MB 留余量；实测 6 MB 与 8 MB 效果无差别，见 P1-notes §6.8）。写入块大小两档：单进程 2000（`CHUNK_EVENTS`）、进程池 10000（`POOLED_CHUNK_EVENTS`；块越大主进程每条越省，2000→10000 约 −12%（1.99→1.75 μs/条），单块同步耗时相应 6.6→26.3 ms）。原始请求体额度仍 8 MB（第 8 条）。
31. 进入第 3/4 级立即 malloc_trim（§3.6 降级）：降级控制器 on_change 中，级别**升到 ≥3 的那一刻**（`old<new and new>=3`，含 3→4）立即调一次 `ticker.malloc_trim()`（非 Linux 无操作），把 glibc 碎片页立刻归还。与 Ticker 的 10 秒周期 trim（第 23 条）互补。依据：第 4 级拒写不降内存、负载不撤就退不出（P1b §4"降级棘轮"），实测一次 trim 回收数十 MiB（S4 10 分钟累计 30 MiB/57 次）。
32. 内存预算按 P1c 实测重写（§5）：256 MB 下**主进程统计状态满载常驻约 200 MiB 工作集，本身就贴在 L3 线（256×0.78≈199.7 MiB）上**，是 256 MB 下的真约束（池关 8 万档 200.6 MiB 即碰线 + 主进程 CPU 87%）。每个解析 worker 空闲约 19 MiB、满载约 54 MiB；池省不掉主进程统计状态内存，2 worker 把工作集顶高 ~50 MiB（222~245 vs 单进程 169~205 MiB），接受率反而最低。单进程 256 MB 最大可持续 ≈6 万/秒；池 1w 为 6 万 100% L0、8 万 98.8% L3。空闲内存（256 MB 容器）：池关 70.2 / 池开 2 为 121.2 / 池开 3 为 139.8 MiB。建议 §5 内存表按此分"空闲/满载"两列重写，并注明 256 MB 与 512 MB 下结论不同（见第 34 条）。
33. 实验结果（§7）：补 P1c 的 256 MB 实验表（P1-notes §6 全文可引用）——四项内存调整（worker 默认 2、池开在途 8 MB、进 3/4 级立即 trim、OpenBLAS/OMP/MKL 线程=1）；S1 六档（池 2w 最高档 4 万 95%、进 3 级）；S4（30k/s 全随机 10 分钟，10.7%、9/10 分钟卡 4 级、平台 ~213 MiB）；S3（池关：召回 1.000、计数误差 0.35%/0.48%（因本机 256 MB 也进 L3 采样，参照 0.05%/0.09%）、落界 100%、去重 0.98%、p95 0.10%；池 1w 进 4 级拒写、无有效样本）；单核对照（解析进程 0、4/6 万 100% L0）；S2 混合负载（p99 50~95 ms，比已提交版 160~173 ms 明显降低）。
34. 吞吐取舍的说法（§8）："进程池 2× 吞吐"要写成**有条件的**：512 MB 下池 3w + 16 MB 额度可持续约 12 万/秒（瓶颈在主进程单写者事件循环，每条 5.7~8.6 μs）；**256 MB 下 2× 买不到**——统计状态常驻内存（~200 MiB）贴 L3 线，池省不掉它、worker 反而顶高水位，单进程本身也内存受限。256 MB 下池配置里 1 worker 最好（6 万 100% L0、8 万 98.8% L3），仍不达"9 万/2×/全程 0 级"验收线。
35. 去重的哈希个数与实测误判率（§3.1 去重、§4 误差表，P2b 二）：`BloomConfig` 新增 `k` 字段，**默认 k 从公式值 12 改为 6**。依据 `tools/bench_bloom.py` 实测（标准镜像 numpy 2.5.4，per_gen 200 万、写满一代后查 100 万未写入 id）：k=12 误判率 0.030% / 1.33 μs/条，k=8 0.044% / 0.88，k=6 0.075% / 0.66，k=4 0.197% / 0.45——在"误判率 ≤0.1%"约束下 k=6 耗时最低（比 k=12 省 0.676 μs/条、~51%）。§3.1 去重一节需写明"k 个点位、默认 k=6、误判率 ~0.07%（per_gen 满载一代时）"，§4 误差表补一行"event_id 去重误判率（k=6，满载一代）~0.07%"。`BloomConfig.k` 为 None 时仍按公式（默认配置=12）；为整数时直接取用。
